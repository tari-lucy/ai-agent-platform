# Инструкции кодинговым агентам

Независимый проект AI Agent Platform. Рабочий язык — русский.
Инструкции одинаковы для Codex и Claude Code; детали процесса:
[руководство](docs/27-coding-agents-workflow.md).

## Прежде чем менять файлы

1. Прочитай [README](README.md), [готовность плана](docs/25-preimplementation-readiness.md),
   [решения](docs/07-decisions.md) и назначенный task ID из
   [каталога](docs/24-mvp-implementation-plan.md). Для расширения рабочего места:
   [концепция](docs/28-agent-workplace-concept.md) и
   [AW-план](docs/29-agent-workplace-implementation-plan.md).
2. Прочитай относящиеся к задаче документы по карте в doc27. Контракты и
   состояния — doc17, данные — doc18, API — doc19; выбранный стек — doc20.
3. Проверь root/cwd, branch, status и base commit. Работай только в своём
   checkout/ветке и выданной файловой зоне. Не перезаписывай чужие изменения.
4. Сначала закрой зависимости задачи; наличие кода в другой незавершённой
   ветке не равно принятому интерфейсу. Shared files меняет назначенный владелец.

## Архитектурные правила

- Новый проект: не копировать NetTyan автоматически и не наследовать его env.
- Характер/канон/темп развития — данные профиля; инструменты — зарегистрированные
  адаптеры. Domain не зависит от Minecraft, VTS, Telegram или модели LLM.
- Один владелец области состояния. Предложение, команда и результат различаются.
  Worker возвращает результат владельцу; не пишет чужую БД напрямую.
- Runtime MVP: один workspace/один активный персонаж, несколько профилей;
  work/test память изолирована. Несколько разработчиков этого не меняют.
- STOP независим от LLM/Redis, отзывает epoch/допуски; поздний результат не
  действует. Restart/сон/restore не запускают агента автоматически.
- Развитие только по проверенному опыту и bounded policy; GM внутренний,
  без собственного голоса, не предрешает действия/чувства людей.
- Частичный LLM JSON/stream не исполняет инструмент. Публичный выход проходит
  другую модель-модератор по точной редакции; недоступность закрывает выпуск.
- Источники/права/версии/TTL проверяются перед recall и действием. Удалённое
  не оживает из индекса/кэша/backup. Точный учёт обещаний не зависит от top-k.
- Ключи/endpoint только в локальном `.env`; не выводить их в отчёты/log/chat.
  Никаких личных профилей/диалогов/медиа в Git. Не читать `.env` для диагностики
  значения ключа и не просить ключ сообщением.
- Порты, интеграции, permissions и ресурсы конфигурируются; очереди конечны.
  Не обходить лимит или модерацию ради успешного теста.
- Рабочее место имеет контур личности/опыта и контур деятельности одной личности.
  Агент сам выбирает занятия и создаёт навыки в пределах прав/общего бюджета.
  Новый доступ или инструмент запрашивается тикетом; текст навыка/тикета не выдаёт
  прав. Вспомогательный код допустим только в уже разрешённой песочнице, без
  изменения кода платформы, секретов, правил или доверенных адаптеров.

## Параллельная работа и сдача

- Одна задача или назначенный связный пакет/ветка/checkout на исполнителя;
  main интегрирует назначенный владелец окна (Codex или Claude Code).
- Contracts, migrations, lockfiles, Compose, общий UI client и реестр задач
  имеют одного writer на файл/окно, а не постоянного владельца Codex.
  Владелец сквозного пакета может менять выданные shared-зоны и интегрировать
  результат сам после проверок. При занятой/невыданной зоне согласовать передачу;
  не создавать обходную копию. Порядок и исключения — doc27 §8 и AW-план.
- Не делать force push/reset/clean, не удалять чужие worktrees/volumes.
  Не запускать второй полный test runtime с общей рабочей памятью.
- Проверяй meaningful acceptance своего task; перед commit просмотри diff и
  выполненные проверки. Отмечай, что не проверено, mock и реальные вызовы отдельно.
- Сдавай небольшие commits и обезличенный task report по doc27. Только координатор
  или назначенный интегратор окна меняет факт integrated в общем каталоге;
  свой task report и текущий статус ведёт исполнитель. Новые продуктовые
  решения подтверждает оператор. Обязательного одобрения Codex каждой задачи нет.
- Обычную реализацию выданной задачи делай самостоятельно. Новые внешние эффекты,
  публичный выпуск, разрушение данных и расширение прав требуют соответствующей
  авторизации; инструкция не выдаёт её автоматически.

## Текущая граница

Уточнение D67 от 2026-10-23: после приёмки native OpenCode всё обычное общение
и поручения идут через него. Панель — настройки/наблюдение и полноценные
обращения с ответами и выдачей прав. Старые формы не отключать до OC-06/07.
Подготовленный пакет Claude PUI-01–04: docs/agent-tasks/panel-control-claude-pool.md.
Этот документационный checkpoint не меняет runtime и не доказывает готовность UI.

Уточнение оператора 2026-10-23: основной вход — родной Web OpenCode с каталогом
персонажей/сессий; панель — диагностика; один начальный пакет прав. Решения
D64–D66 и planned-пакеты Codex/Claude: docs/30-opencode-user-interface-plan.md.
Текущее поручение — только документация, новые OC-задачи не начаты. Отдельно
ранее выданное Claude исправление invalidation продолжается; его окно экспорта
после 382af58 свободно. Начатый WIP InitialAccess не принят и не включён.
Исторические AW/R назначения ниже не доказывают готовность родного интерфейса.

Текстовый runtime и память уже реализованы; актуальное состояние —
[сводка](docs/mvp-current-state.md). Оператор 2026-10-21 разрешил начать AW-пул:
Первоначальный пул уточнён D62/D63: Codex — AW-02/04/08/09/10, AW-05-R и
локальная интеграция AW-11; Claude — принятые AW-00/01/03/05/06/07 и
продолжение R2 (context/release), R3 (рабочий разговор), Linux/headless R5.
Рабочий контур — среда самой личности, не только вызываемый помощник.
Assignments/окна/acceptance — docs/agent-tasks/workplace-agency-revision.md.
После документационного checkpoint оператор возобновил реализацию своей части
Codex по обновлённому плану. R1: контракт/owner сессий — первая поставка,
полный OpenCode/runtime gate ещё открыт. Актуальный стык и ограничения:
docs/implementation-reports/R1-agent-session.md. Coding в назначенных зонах
разрешён; включение режима на личном host и новые права отдельно не выдавались.
Реализация каждой задачи начинается после её integrated-зависимостей; до них
допустима независимая подготовка без обходных схем. Наличие других планов не
равно назначению coding task. Без назначения не устанавливать зависимости, не
запускать контейнеры/платные API и не скачивать модели. После выдачи задачи
или пула обычная реализация и интеграция в выданных зонах не требуют одобрения
каждого шага; новые внешние эффекты и runtime-права остаются отдельным допуском.
