# Рабочее место агента: постоянная папка (W2) и интернет (W3)

У каждой личности свой Docker volume, смонтированный в контейнер хода как
`/workspace`. Файлы, заметки, проекты и инструменты, которые агент там создаёт,
сохраняются между ходами и перезапусками. Внутри контейнера агент работает
свободно: `bash`, поиск, чтение и правка файлов без согласования шагов.
Граница — сам контейнер: корень только для чтения, сеть только через шлюз
платформы и по разрешению, компьютер оператора и другие агенты недоступны. План и решения: [doc31](31-agent-workspace-v2.md).

## Что видит агент

```
/guide/AGENTS.md          правила оператора (только чтение, обновляются каждый ход)
/guide/connections.md     устройство среды и занятое место (пишет платформа)
/guide/skills.md          оглавление навыков агента: skills/<имя>/SKILL.md → description
/workspace/README.md      порядок папки; ведёт сам агент, начало подаётся в каждый ход
/workspace/playbook/      приёмы
/workspace/skills/        навыки
/workspace/projects/      проекты
/workspace/inbox/          файлы оператора (кладёт оператор из окна OpenCode)
/workspace/share/          то, что агент отдаёт оператору
```

## Что видит оператор (W4)

В окне OpenCode → дерево файлов → раздел **workspace**: вся папка личности
только для чтения (каталоги и файлы; ссылки и особые файлы не открываются,
бинарные показываются карточкой, текст — до 1 МиБ). Чтение идёт через
короткоживущий контейнер без сети, том на хосте не монтируется.

Чтобы передать файл агенту в его папку: прикрепить файл к сообщению и выбрать
область `workspace` — файл ляжет в `/workspace/inbox/` (до 32 МиБ, существующий
файл не перезаписывается). В сообщение попадает пометка с путём.

`/guide/AGENTS.md` берётся из файла хоста `<root>/guide/AGENTS.md`. Файла нет —
используется короткое правило по умолчанию. Правка файла действует со следующего
хода, перезапуск не нужен.

## Как включить на Windows

1. Обновить checkout до main с W2.
2. Пересобрать доверенный harness поверх pinned-образа (зависимости не ставятся,
   сеть при сборке выключена):

   ```text
   python scripts/refresh_opencode_harness.py --base-image sha256:<64 hex> --tag ai-agent-platform:opencode-w2
   ```

   Скрипт печатает новый image ID; образ несёт метку
   `ai-agent-platform.workspace.protocol=1`.
3. При остановленном сервере:

   ```text
   python -m ai_agent_core.local_host enable-work-sessions --root <root> --image-id sha256:<новый ID> --area ... --output-area ... --home
   ```

   Пропущенные параметры сохраняют прежние настройки. `--home-quota-mb N` задаёт
   порог предупреждения о размере папки (по умолчанию 4096). `--no-home` выключает.
4. По желанию положить свои правила в `<root>/guide/AGENTS.md`.
5. `serve`, START, разговор в OpenCode.

Проверка: попросить агента «создай в /workspace/projects/test/ файл с заметкой и
покажи `ls -la` этой папки», затем в следующем сообщении «прочитай эту заметку».
Шаги bash видны в окне (журнал W1). После перезапуска сервера заметка на месте.

## Интернет через шлюз (W3)

Включается отдельно: `enable-work-sessions ... --internet` заводит возможность
`workplace.internet`. Пользоваться ей персонаж может только после разрешения
оператора: в панели → **Обращения** → запрос на `workplace.internet` → **Разрешить…**.
Без разрешения ход идёт как раньше, без сети.

С разрешением на каждый ход поднимается отдельная внутренняя Docker-сеть и
контейнер-шлюз (HTTP/HTTPS-прокси и SOCKS5 на том же порту, W3b). У контейнера
агента нет DNS и маршрута наружу,
кроме шлюза. Шлюз:

- пускает только на публичные адреса; локальная сеть, компьютер оператора,
  адрес Docker-хоста, другие агенты, адреса метаданных (169.254.x.x) и
  почтовые порты (25, 465, 587) закрыты; `--egress-deny CIDR` добавляет свои;
- ограничивает объём за ход (`--egress-max-mb`, по умолчанию 256), за сутки UTC на
  личность (`--egress-daily-mb`, по умолчанию 2048; `0` — без суточного лимита;
  отказ `EGRESS_DAILY_LIMIT`) и число соединений (`--egress-connections`, 32);
- пишет журнал: `<root>/data/egress/ГГГГ-ММ-ДД.jsonl`. Для HTTP — полный URL,
  для HTTPS — только `сайт:порт` (без подмены сертификатов, решение оператора
  2026-10-26). Журнал может содержать личное: только локально, не в Git и отчёты;
- удаляется вместе с ходом; STOP и отзыв разрешения рвут соединения.

`pip`, `npm`, `curl`, Python `urllib` и `webfetch` OpenCode работают через
переменные `HTTP(S)_PROXY`. Установленное (`pip --user`, `npm -g`) и кэши
сохраняются в `/workspace`. Прогретый контейнер с интернетом не используется:
такой ход стартует холодным.

Журнал виден в панели: **Работа** → блок **Интернет** → «Показать журнал»: итог
за сутки (запросы, отказы, объём и лимиты) и последние 200 запросов; «Раньше» и
«Позже» листают дни (до 30 назад).

### Образ «руки» (W3b)

Отдельный образ поверх проверенного harness-образа добавляет инструменты для
работы агента: git, curl/wget, jq, zip, ssh-клиент, dig/nc, ffmpeg, ImageMagick,
Java 17, Node.js/npm, Chromium и Python Playwright (без скачивания браузера —
системный `/usr/bin/chromium`). Сборке нужна сеть (apt/pip), это ~1,5 ГБ:

```powershell
python scripts/build_hands_image.py --base-image sha256:<ID harness-образа> --tag ai-agent-platform:opencode-hands
docker image inspect --format '{{.Id}}' ai-agent-platform:opencode-hands
python -m ai_agent_core.local_host enable-work-sessions --root <root> --image-id sha256:<ID hands> ...
```

Скрипт проверяет, что слои и метки базы сохранены, и ничего не включает сам.
Изоляция та же: корень только для чтения, uid 65532, без capabilities; свои пакеты
агент ставит в `/workspace`. Список инструментов агент видит в `/guide/tools.md`.
После обновления harness (`refresh_opencode_harness.py`) его можно применить и
поверх образа «руки».

Проверка: разрешить интернет, попросить агента «установи через pip пакет
`requests` и скачай заголовок example.com»; в журнале `data/egress` появятся
строки `pypi.org:443`, `files.pythonhosted.org:443`, `example.com:443`.

## Долгоживущий контейнер (W5)

`enable-work-sessions ... --resident` (`--resident-idle-seconds`, по умолчанию 1800)
оставляет контейнер личности между ходами. Фоновые процессы агента (`nohup …&`,
сборка, рендер, бот) продолжают работать после ответа. Каждый ход по-прежнему
получает **новую** сессию OpenCode с контекстом от платформы: переписка внутри
контейнера не накапливается, забывание и права работают как раньше.

- Между ходами модель и инструменты платформы контейнеру недоступны (403).
- Контейнер закрывается: по STOP, после простоя, при любом неуспешном или
  отменённом ходе, при смене личности, если пропал процесс платформы
  (перезапуск или сбой) — фоновая работа заканчивается вместе с ним.
  Сам он после перезапуска не поднимается: только после START и первого хода.
- С разрешением на интернет контейнер создаётся вместе со своим шлюзом:
  фоновые процессы тоже ходят в сеть через него, журнал пишется с пометкой
  `attempt: resident`, лимит объёма — на всё время жизни контейнера. Отзыв
  разрешения закрывает контейнер в течение нескольких секунд, даже между ходами.

## Профиль рабочего места одним решением (W6)

Если хост подготовлен с потолком (`--ceiling-days N`, до 365), всё рабочее место
выдаётся одним решением: панель → **«Обзор и права»** → карточка **«Начальный доступ»**
→ **«Подготовить начальный доступ»** → проверить план → выполнить. В набор входят
рабочий разговор (с ним — папка, shell и долгоживущий контейнер), Python-контейнер,
интернет, знания и навыки — то, что включено на этом хосте. Права действуют весь
выбранный срок (до 365 дней) до отзыва; отзыв — по отдельной возможности.
Новое подключение, добавленное позже, этим решением не выдаётся — для него обращение.

Пример подготовки хоста со всем рабочим местом:

```text
python -m ai_agent_core.local_host enable-workplace-files --root <root> --ceiling-days 365
python -m ai_agent_core.local_host enable-work-sessions --root <root> --image-id sha256:<ID> ^
  --area projects --area inbox --output-area projects --ceiling-days 365 ^
  --home --resident --internet --helper --wall-seconds 600 --helper-wall-seconds 300
```

## Самостоятельная работа (W7)

`enable-work-sessions ... --self-work` разрешает агенту ставить себе будильники:
операция `wake_me` (через сколько минут, до 7 суток, и что сделать). В назначенное время
платформа пишет в разговор **«Самостоятельная работа»** (создаётся сам) сообщение с
пометкой ⏰, и агент продолжает там — с журналом шагов, как в обычном разговоре.

- Срабатывает только когда агент запущен (START) в **автономном** режиме, в рабочей
  памяти. Пока STOPPED — ничего; после перезапуска — только после START.
- Не чаще `--wake-max-per-hour` (по умолчанию 4) в час; `--quiet-hours 23-8` — тихие
  часы по времени хоста. Ход тратит тот же бюджет активности, что и остальные.
- Не больше 16 ожидающих будильников. Закрытый оператором разговор отменяет их.
- Будильник — данные: прав не выдаёт, текст хода и память переносятся только через
  текст будильника и файлы `/workspace`.
- **По окончании фоновой работы** (W7b, нужны `--home` и `--resident`): агент
  запускает долгую команду так, чтобы в конце она записала файл
  `/workspace/.platform/done/<имя>`, и ставит `wake_me` с `when_done=<имя>`. Будильник
  срабатывает, как только файл появился (платформа смотрит раз в минуту коротким
  контейнером только для чтения), или через `minutes` — что раньше. Файл старше
  будильника не считается. Сообщение говорит, что именно случилось.
- **Суточный бюджет процессора** (W7b): `--cpu-daily-minutes` (по умолчанию 240,
  `0` — выключен). Каждый ход сообщает, сколько CPU потратил его контейнер (счётчик
  cgroup самого контейнера; у долгоживущего — включая фоновую работу с прошлого хода).
  Учёт — локально в `<root>/data/usage/ГГГГ-ММ-ДД.jsonl`. Исчерпав бюджет, будильники
  агента ждут следующих суток UTC; разговоры, которые начинает оператор, не блокируются.
  Фоновая работа после последнего хода долгоживущего контейнера (до его закрытия по
  простою или STOP) в учёт не попадает.

## Ограничения и риски

- **Без разрешения `workplace.internet` сети нет.** Установленное из локальных
  файлов сохраняется в `/workspace/.local` и `/workspace/.npm-global`.
- **Размер volume не ограничен Docker'ом.** Порог — только предупреждение агенту
  в `/guide/connections.md`. Следите за диском: `docker system df -v`.
- **Фоновые процессы** без `--resident` завершаются в конце хода.
- **Папку видно, но не публикуется.** Оператор видит `/workspace` в окне;
  в управляемые области платформы файл попадает только через `outputs/`.
- **Журнал хода — наблюдение, не доказательство.** Внутри контейнера агент
  управляет своими процессами и в принципе может исказить свой след; хост
  по-прежнему проверяет всё, что выходит за контейнер.
- **Забывание разговора не трогает volume.** Это собственность агента; удалить
  её может оператор: `docker volume ls --filter label=ai-agent-platform.home=1`,
  затем `docker volume rm <имя>` при остановленном сервере. Имя volume —
  `aw-home-` и хэш раздела личности (work и test — разные папки).
