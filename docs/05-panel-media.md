# Веб-панель, вводные и медиапроизводство

Статус: устройство вкладки развития, матрица прав и отдельные управления
остановкой согласованы. Панель MVP открывается только на этом компьютере.
Шесть областей и полный текстовый сценарий приняты в D34, один активный
экземпляр — в D35; отдельный дашборд «LLM и расходы» добавлен в D43.
Точные экраны, метрики и будущие медиапроцессы ещё
проектируются. UI не создан.

## Панель первой версии

Доступ первой версии согласован как локальный: оператор открывает панель
в браузере на том же ПК. При реализации Docker публикует порт панели/API
на Windows только на loopback; внутренний адрес контейнера выбирается для его сети.
Порт настраивается;
публикация панели в интернет или доступ из домашней сети не включаются
автоматически. Локальный доступ не заменяет проверку операторской сессии
для административных команд. Способ входа и запуск на Windows ещё проектируются.
Базовое развёртывание — Docker по D36; выбранные Redis Streams, три сервиса
и связь с Windows-исполнителями описаны в [плане Docker и очередей](15-docker-queues.md).

Рекомендуемые разделы:

| Раздел | Что делает оператор |
| --- | --- |
| Обзор | Видит выбранного персонажа, режим, текущую задачу, состояние и расходы |
| Персонаж | Редактирует профиль, сравнивает версии, проверяет примеры реплик |
| Диалог | Общается текстом, видит статусы реплик, начинает/завершает сессию |
| Память | Ищет воспоминания, видит источники, исправляет/удаляет/экспортирует записи |
| Люди и отношения | Видит собеседников, встречи, разговоры, обещания и основания дружбы/конфликтов |
| Сюжет и развитие | Видит линии, путь персонажа, основания изменений и сюжетные ограничения |
| Вводные | Задаёт цель, событие или контекст с областью действия и сроком |
| Испытания | Запускает сценарии, подаёт тестовые события, сравнивает реакции |
| Журнал | Разбирает причины действий, ошибки, отмены и состояние адаптеров |
| LLM и расходы | Видит модели по ролям, задаёт тарифы, отслеживает токены, расходы и неполный учёт |

Вкладка «Сюжет и развитие» согласована с четырьмя представлениями: обзор,
линии, изменения и границы. Согласованы карточка изменения, пауза/интенсивность
драйвера, отмена испытания, пауза линии, решения по изменениям, исправление
интерпретации и откат с показом последствий. Визуальные детали ещё обсуждаются
в [плане контроля развития](09-development-oversight.md).

Для независимой модерации предусматриваем очередь спорных случаев, причины
блокировки, версии правил и состояние другой модели. Подробности и границы
проверки живого эфира — в [плане модерации](10-moderation.md).

Выбор рабочего пространства, личности и активного экземпляра определяет,
какие задачи, память, линии и подключения показаны. Сборка наборов инструментов
описана в [плане рабочего пространства](11-agent-workspace.md).

Остановка видна постоянно. Смена профиля показывает, создаётся ли новый
персонаж или новая редакция существующего; переключение имени не должно
неявно объединять разные биографии. Для тестов можно создать изолированную
копию состояния и явно применить одобренные результаты в основной профиль.
Такой перенос касается проверенных настроек профиля/политик; искусственные
встречи, отношения и события не импортируются как прожитая рабочая биография.

Редактирование памяти хранит автора правки и версию. Важно различать исправление
факта, добавление канона, снижение уверенности и полное удаление записи.
Интерфейс не выдаёт недостоверное воспоминание за наблюдение.

Память показывает хронологию опыта, дневник, находки и собственные выступления/
публикации. Для Markdown доступны просмотр, правка/импорт, различия версий
и статус применения; конкретный объём файлового редактора согласуем отдельно.
Полный текст разговоров хранится согласованные 30 дней, далее — значимые
фрагменты и сводки. Предлагается показывать доступность исходника, срок,
область исправления/удаления и состояние резервных копий.
Подробности — в [политике памяти](03-character-memory.md).
Карточка человека связывает источники, отношения и открытые темы. Ошибочное
узнавание или связь аккаунтов исправляются явно, с пересмотром зависимых записей.

В этом разделе видны также зрители и комментаторы, их аккаунты/источники,
обсуждения под постами и история между эфирами. Фильтр площадки меняет
представление доступных данных, но не обнуляет отношения. У каждой записи
видны канал/ветка и основания связывания с человеком.

Панель сообщает понятное состояние: «обдумывает ответ», «ожидает действия»,
«память недоступна», «задание отменено». Подробные trace ID, очереди и схемы
относятся к техническому журналу и не перегружают основной рабочий экран.

### Согласованные области MVP

Таблица выше описывает функции, а не обязательные верхние вкладки.
К шести согласованным рабочим областям добавлен отдельный дашборд;
теперь предусматриваются семь областей:

| Область | Состав |
| --- | --- |
| Диалог | Разговор, текущая цель/краткое основание, ожидающие дела, сводка сессии и подача вводной |
| Персонаж | Создание, версии, канон, стиль и границы развития; новая личность отличается от редакции существующей |
| Память и люди | Поиск/хронология, источник и уверенность, карточки людей, ответы/обещания, исправление/удаление |
| Сюжет и развитие | Согласованные обзор, линии, изменения и границы, решения и управления развитием |
| Лаборатория | Изолированные сценарии, виртуальные собеседники, прогон и отчёт о результате |
| Рабочее пространство | Подключения, права, бюджеты, модерация, резервирование и доступ к техническому журналу |
| LLM и расходы | Модели/роли, ручные тарифы, история попыток и usage, графики токенов и расчётных расходов |

Для очередей в этой области предусматриваем готовность брокера/работника,
число и возраст ожидающих заданий, текущие попытки, отказы и причины задержки.
Повтор неуспешного задания проверяет свежесть и права; не возобновляет
отменённые воздействия автоматически.

Дашборд LLM имеет отдельные представления обзора, моделей/ролей, цен,
истории и аналитики. Предусмотрены фильтры по периоду, сессии, личности,
роли, модели и подключению; рабочие и тестовые вызовы различимы, но оба
входят в общий расход. Цена задаётся с валютой, единицей и датой действия;
неизвестные цены или usage не изображаются нулём. Полные приватные тексты
и секреты для статистики не нужны. Подробности — в [плане LLM и расходов](16-llm-dashboard.md).

В приватном операторском диалоге текст появляется по мере генерации
с отметкой завершения/отмены. Публичный выход ожидает модерации точной редакции;
незавершённый поток не исполняет инструменты и не возобновляет действие после STOP.

Постоянная верхняя область показывает выбранную личность, рабочую/тестовую
сессию, режим и состояние основных служб. STOP доступен с любого экрана.
Отключение голоса появится с голосовым этапом; пауза гейммастера доступна
при его включении. Ожидающее решение содержит конкретный результат и область.
Активная рабочая сессия и открытый тест различимы; просмотр лаборатории
не меняет владельца памяти действующего агента. При согласованном лимите один
активный экземпляр запуск теста требует явного завершения/приостановки рабочего
запуска. Возврат к рабочей деятельности тоже явный; параллельный запуск нескольких
экземпляров не входит в согласованный объём MVP.

## Согласованный полный сценарий первой версии

Базовый цикл и области приняты в D34–D35. Подробности экранов, числовые
критерии и технические контракты ещё выбираются; реализация не начата.
Первая версия остаётся текстовой: персонаж, память и панель без игры;
реальные голосовые, игровые, эфирные и публикационные подключения идут позднее.

### 1. Подготовить личность

Создать профиль из пустой формы или шаблона: идентичность, ценности, интересы,
манера общения и правила развития. Конкретные черты остаются данными.
Предпросмотр показывает неполные поля и примеры ожидаемого поведения.
Сохранение создаёт версию, а применение показывает активный профиль.
Создание новой личности явно отличается от правки существующей.

В MVP согласованы один workspace, один активный экземпляр и несколько
сохранённых личностей. Подключения показывают
готовность; значения API-ключей остаются локально в `.env`.

### 2. Начать текстовую сессию

Выбрать личность и рабочую либо тестовую сессию. В рабочем диалоге оператор
общается от собственного имени; виртуальные собеседники задаются в тестах
с отдельными идентификаторами и пометкой происхождения.
Панель показывает ответ, текущую деятельность и понятные статусы ожидания.
Сессия не обнуляет биографию, отношения и открытые обещания личности.

### 3. Подать вводную

Выбрать тип: контекст, цель, операторское утверждение/правка канона либо
тестовое событие. Указать область действия и срок, если они нужны.
Панель различает принято, ожидает, выполнено, отклонено, отменено и истекло.
Сценарная вводная имеет собственное происхождение и не выдаётся за наблюдение
реального внешнего мира. Отмена снимает связанные ожидающие действия.

### 4. Посмотреть память и отношения

Открыть эпизод, исходный диалог, краткую интерпретацию и связанные источники;
при необходимости исправить конкретную запись с понятным типом коррекции.
Карточка собеседника показывает обсуждённые темы, известные ответы,
обещания, совместный опыт и основания изменения отношений.
В повторной встрече эта история влияет на выбор темы и действий.
Срок полного текста согласован: 30 дней с дальнейшим сохранением значимых
фрагментов и сводок. Стартовые правила остальных данных, исправлений,
экспорта и резервирования согласованы в D30; точные квоты, сроки медиа/тестов
и механизмы удаления/восстановления ещё выбираются.

### 5. Проверить развитие и вмешаться

Перейти в согласованную вкладку развития: проследить линию, увидеть изменение
и его основания, проверить позднее проявление. Разрешённое изменение может
примениться автоматически; существенное изменение идентичности/опорной
ценности ждёт решения оператора. Доступны согласованные управления.
После коррекции или отката прежнее событие сохраняет своё происхождение.

### 6. Завершить и продолжить позднее

После завершения сохраняются подтверждённая история, отношения, открытые
темы/обязательства, версии профиля и развитие. Предлагается показывать
краткую сводку сессии и незавершённых дел; сводка не заменяет источники.

После перезапуска выбирается личность, восстанавливается контекст и
проверяется актуальность незавершённых задач. Предлагается явное возобновление
деятельности; прежние отменённые команды и поздние ответы не запускаются.
Внешний результат с неизвестной доставкой не превращается автоматически
в подтверждённое действие или повод повторить отправку.

### Сквозной сценарий приёмки

Предлагаем один сохранённый сценарий, который проходит через все перечисленные
экраны. Его персонаж, собеседники, сообщения и события — тестовые данные,
а не выбранный характер будущего персонажа или реальные сведения о людях.
В рабочей сессии собственное общение оператора имеет обычное происхождение;
виртуальные встречи проверяются только в лаборатории.

1. **Подготовка и начало.** Выбрать профиль и разрешённые подключения моделей,
   проверить готовность памяти/модерации и бюджет, начать изолированную сессию.
   Отсутствующая зависимость имеет понятный статус; запуск не создаёт пустую
   замену потерянной биографии и не включает внешние воздействия.
2. **Знакомство.** Собеседник с устойчивым тестовым ID рассказывает, например,
   о проекте обсерватории и отвечает на вопрос о нём. Персонаж реагирует
   в соответствии с выбранным профилем. В карточке человека появляются
   источник разговора, известный ответ и актуальная тема; объявление о проекте
   остаётся сведением со слов человека, а не подтверждённым посещением мира.
3. **Открытое дело.** Собеседник просит вернуться к теме при следующей встрече.
   Если персонаж принимает просьбу, сохраняется обещание с условиями, адресатом
   и статусом; согласие не выдаётся за уже выполненный результат. Отказ тоже
   допустим и не создаёт ложного обязательства. Для прогона обязательства
   выбирается допустимая просьба, которую профиль готов принять.
4. **Повторная встреча.** Завершить сессию, перезапустить её и вернуть тот же ID.
   Ожидаются узнавание, доступ к прежнему ответу и учёт принятого обещания.
   Дословное повторение реплик не требуется. Другой ID с тем же отображаемым
   именем не получает эту историю автоматически; известный ответ защищает
   от повторного расспроса при отсутствии нового основания.
5. **Изменившиеся сведения.** Собеседник уточняет, что пока только задумал
   обсерваторию. Текущее представление обновляется с источником, исходная
   реплика сохраняет своё происхождение. Оператор может исправить факт,
   интерпретацию, уверенность либо удалить запись с предпросмотром области.
6. **Возможность развития.** Гейммастер предлагает допустимую возможность
   на основе темы. Персонаж может принять, отложить или отказаться. Симулятор
   подаёт результат принятого действия; результат не сочиняется персонажем
   как факт. Рефлексия может сохранить вопрос/вывод или предложить изменение.
   Изменение не обязательно для каждого эпизода: устойчивость тоже оценивается.
   Существенная правка ядра ждёт оператора; принятую обычную правку позднее
   проверяют по проявлению в новой ситуации, а не только по карточке значений.
7. **Остановка и продолжение.** Подать вводную с областью и сроком, затем
   отменить её либо нажать STOP при ожидающем ответе. Поздний результат
   не запускает воздействие. Сохранить состояние, открыть его снова и явно
   возобновить: история/ответы/обязательства восстановлены, отменённые команды
   не повторяются, истёкшие цели переоценены.

Отчёт прогона показывает ожидаемое/наблюдённое поведение, ссылки на источники,
статусы обещаний/изменений и причины неуспеха. Одно прохождение не доказывает
устойчивость личности: сценарий повторяется в серии сессий, с вариациями
контекста и разными персонажами. Конкретные метрики и пороги ещё согласуются.
При ошибке памяти ответ не должен утверждать, что сведения надёжно сохранены;
при отказе модели панель сохраняет состояние и предлагает допустимые действия.
Эти проверки — будущие критерии, сейчас приложение и тесты не реализованы.

### Согласованная граница объёма

Первый результат — работающий текстовый цикл: профиль → общение → точная память
и отношения → продолжение → возможность/рефлексия → наблюдаемое развитие,
с вводными, лабораторией, правами, остановкой и восстановлением.
Стартовая нагрузка — один workspace и один активный экземпляр,
несколько сохранённых профилей (D35).
Новая сессия той же личности использует её историю; переключение личности
показывает другую область памяти. Полная история не помещается целиком в prompt.

Текстовый модератор другой моделью проверяется здесь на тестовых выходах.
Рабочая панель не становится внешним каналом публикации; пробный материал
помечается своим назначением, а результаты проверки не переносятся на другую
редакцию/назначение. Minecraft, STT/TTS, VTube Studio, эфир, Telegram и монтаж
подключаются по этапам через предусмотренные границы. Их вкладки/адаптеры
не нужны для завершения текстового цикла первой версии.

### Проверочные сцены и управление

Предлагаются сохранённые текстовые сценарии: знакомство/повторная встреча,
неотвеченный вопрос, обещание, конфликт/примирение, поток сообщений,
отказ от возможности гейммастера, остановка, недоступность LLM/памяти
и восстановление после перезапуска. Повторный прогон использует изолированное
исходное состояние; точного совпадения слов LLM не требуется.

Остановка доступна с любого экрана. Отдельная пауза гейммастера оставляет
обычную разрешённую деятельность. Ошибка зависимости видна и не выглядит
как успешный ответ или исчезновение всей памяти.
Критерии связываются с [планом проверки](06-roadmap-validation.md).

## Типы вводных

Вводная содержит автора, цель, тип, приоритет, область, срок, условия завершения
и статус применения. Подтверждение приёма не означает выполнения.

Различаем:

- факт/канон, который оператор явно добавляет в профиль;
- контекст текущего разговора или эфира;
- цель/задание с критериями результата;
- сценарный стимул или тестовое событие;
- изменение режима и разрешений, доступное только оператору.

Пример: «Сегодня исследуем заброшенные места; уделяй внимание архитектуре»
действует в текущей сессии, не переписывает основные ценности и не создаёт
воспоминаний об уже состоявшемся исследовании.

В будущем вводные могут планироваться по времени и условиям. Для ранней версии
достаточно немедленного применения, отмены и истечения. При изменении вводной
система проверяет активную цель; не каждое уточнение должно прерывать речь
или навигацию.

## Доступ и конфигурация

Первый режим панели — локальный, с аутентификацией оператора. Локальный адрес
не отменяет проверки Origin, защиты управляющих запросов и WebSocket-сессий.
Внешний доступ, дополнительные роли и облачное размещение — отдельное решение.

Профили, политики, доступные адаптеры и параметры транспорта — разные виды
конфигурации. Применение валидируется и версионируется. Безопасные изменения
могут вступать в силу сразу; изменение адреса адаптера или модели требует
управляемого переподключения/перезапуска. Панель показывает это заранее.
Секреты не возвращаются frontend; она видит только факт настройки и проверки.

На голосовом этапе STT и TTS отдельно показывают режим local/API, выбранную
модель/голос, готовность и нагрузку. Оба способа запуска предусмотрены для
каждого направления; переключение и правила резервного провайдера задаются явно.

## Скриншоты и медиаархив

Capture-адаптер сохраняет реальный кадр из игры или разрешённого источника OBS.
Для исследования предпочтителен игровой источник, чтобы кадр не включал
случайные окна рабочего стола. Кадр получает ID, timestamp, привязку к событию,
серверному пространству/миру, месту, автору и статусу проверки.

При появлении интересного места контроллер может запросить снимок, если это
не мешает игре. Инициатива ограничивается cooldown, свободным местом и новизной.
Отбор учитывает качество, повторяемость ракурса и связь с конкретным выводом.
У исходного файла сохраняются checksum и производные превью/кропы.

Модель описывает изображённое только при наличии данных для визуального анализа
или подтверждённых событий, связанных с кадром. Незаметно подменять отсутствующий
скриншот сгенерированной картинкой нельзя. Скрытые личные детали/HUD можно
убрать отдельной производной версией; оригинал и история обработки различаются.

## Telegram

Процесс: конец исследования/важная находка → выбор проверенных эпизодов →
подбор реальных кадров → черновик текста и подписей → проверка источников →
предпросмотр и правки → модерация точной редакции другой моделью →
публикация согласно настроенной политике → запись
результата и ID сообщения.

Подтверждённая публикация создаёт событие для истории персонажа: точная редакция,
канал, время, ID и исходные эпизоды. Неопределённая доставка остаётся неизвестной
и не становится фактом «я уже опубликовал». Правки/удаления обновляют историю
выхода и производные записи по правилам хранения.

Редактор показывает заголовок, текст, альбом, подписи и связь утверждений
с эпизодами. Смена текста после одобрения инвалидирует одобрение этой редакции.
Ручное одобрение оператора и результат модерации — отдельные проверки;
изменение текста или альбома требует повторного допуска.

Предложение для первого этапа публикаций — черновики с ручным выпуском.
Позже оператор может явно разрешить автопубликацию в конкретный канал с
лимитами, расписанием, тематикой и правилами остановки. Это настраиваемая
политика, а не неизменное ограничение ядра.

Telegram-адаптер проверяет полномочия бота, параметры сообщений, частотные
ограничения и ошибки API. Отправка сообщения и альбома поддерживается
[официальным Bot API](https://core.telegram.org/bots/api). Права канала и
параметры доставки проверяются в конкретном подключении.

Комментарии Telegram проектируем как входной адаптер обсуждения, связанный
с опубликованным постом и его веткой. Bot API описывает связанный discussion
chat в `linked_chat_id`; доступ к сообщениям группы зависит от режима/прав бота.
Источники: [Bot API](https://core.telegram.org/bots/api#chatfullinfo),
[Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).
Одних прав отправлять посты недостаточно для обещания чтения всех комментариев;
подключение и полноту доступных событий проверяем до запуска адаптера.

Комментатор, тема и ответы сохраняются в общей социальной памяти. Персонаж
может продолжить обсуждение под следующим постом и учитывать значимую
обратную связь в рефлексии. Возможность отвечать от имени персонажа задаётся
политикой канала; каждый ответ проходит тот же допуск модерации, что и пост.

Публикация — отдельное устойчивое задание. При неопределённом результате
таймаута повторный пост автоматически не создаётся. Нужны проверка доступного
подтверждения/внешнего ID и отображение неопределённости оператору.
Возможности редактирования/удаления учитываются отдельно от гарантии доставки.

## Трансляция

Эфирный workspace позднее показывает: состояние OBS, источники звука,
чат/очередь тем, аватар, текущую игровую задачу, вводные и бюджет ресурсов.
Нужны отдельные действия «остановить агента», «заглушить голос», «завершить эфир».
Предлагаемая аварийная остановка агента отменяет его воздействия и голос,
но сама по себе не завершает трансляцию; это правило нужно согласовать.

Для первой проверки — закрытая/локальная запись, затем тестовый эфир по
явному решению оператора. События OBS, игровые события и речь получают общую
временную привязку, позволяющую восстановить интересный эпизод.

## Отдельный монтажный процесс

Монтаж имеет свой интерфейс, проекты и очередь заданий. Он может существовать
в том же веб-приложении как отдельный workspace, но не входит в цикл решений
агента и не занимает его игровой поток. Отдельный worker обеспечивает отмену,
восстановление задания и ограничение ресурсов.

Процесс:

1. Импорт записи и проверка metadata через ffprobe.
2. Привязка записи к временной шкале сессии. Учитываются начало файла, паузы,
   разрывы и рассинхронизация; время события не равно секунде в файле автоматически.
3. Создание прокси, транскрипта и кандидатов эпизодов по событиям и речи.
4. Предложение монтажа с исходным файлом, in/out, порядком, подписями и аудио.
5. Редактор: предпросмотр, перестановка, обрезка, субтитры, громкость, формат.
6. Проверка проекта → отдельное задание FFmpeg → результат → проверка экспорта.

Исходники сохраняются. Монтажный проект версионируется и содержит ссылки на
источники, временные отрезки, дорожки, субтитры и настройки экспорта. Аргументы
FFmpeg строит приложение из проверенного проекта; LLM не исполняет shell-команды.
Файлы доступны только внутри разрешённых каталогов медиа, а не по произвольным
путям из сообщения зрителя.

Первый объём монтажа: выбрать эпизоды, изменить in/out, переставить клипы,
добавить субтитры/заголовок, управлять громкостью и экспортировать готовый файл.
Сложные эффекты, профессиональные переходы и обмен с другими NLE обсуждаем позже.

OBS API поддерживает запись и сохранение replay buffer
([протокол](https://raw.githubusercontent.com/obsproject/obs-websocket/master/docs/generated/protocol.md));
само наличие buffer не заменяет полноценную запись и точную синхронизацию.
FFmpeg служит механизмом сборки, не готовым интерфейсом видеоредактора
([документация](https://ffmpeg.org/ffmpeg.html)).

Рендер на время эфира по умолчанию приостанавливается либо ограничивается
после нагрузочного теста. Интерфейс монтажа должен оставаться доступным
при выключенном агенте. Автоматическая загрузка готового видео на площадки
не входит в согласованный запрос; её можно отдельно добавить позднее.
