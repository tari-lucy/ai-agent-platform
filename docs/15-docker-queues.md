# Docker, очереди и восстановление

Статус: Docker и очереди для устойчивости — требования пользователя (D36–D37).
Redis Streams и три базовых Compose-сервиса с Windows-адаптерами согласованы
в D38–D39. Библиотека работников, версии образов, fsync и числовые лимиты
ещё выбираются. Compose-файлы и приложение не создаются.

## Граница Docker и Windows

Основная платформа запускается через Docker Compose. Для Windows 11 выбраны
Linux-контейнеры в Docker Desktop с WSL 2 backend. Логические роли не требуют
отдельного контейнера каждая; личность и инструменты остаются конфигурацией.

| Компонент | Предлагаемое размещение и роль |
| --- | --- |
| Ядро/API и панель | Один базовый сервис: сессии, разрешения, память, задания, планировщик, outbox; собранная панель может обслуживаться им же |
| Фоновый работник | Отдельный контейнер для разрешённых вычислений и заданий; раздельные лимиты классов нагрузки |
| Брокер | Один локальный Redis с постоянным томом; Streams для доставки заданий |
| Память и точные журналы | Пока рекомендуются embedded SQLite и заменяемый recall-компонент у владельца памяти; отдельный сервер БД не обязателен |
| STT/TTS, индексирование, монтаж | Подключаемые вычислительные работники/режимы; тяжёлые модели загружаются по нужному сценарию, размещение уточняется по пробам |
| Minecraft, VTube Studio, OBS и аудиоустройства | Приложения/исполнители Windows, подключённые через локальные адаптеры; снятие ввода и watchdog действуют на стороне исполнителя |

Согласованный базовый MVP имеет три сервиса: ядро с панелью, работник, брокер.
Гейммастер, рефлексия и модерация остаются логическими ролями с отдельными
контрактами/контекстами, а не постоянно загруженными локальными LLM.
Модератор по требованию использует другую модель. Дополнительные работники
подключаются по этапам и делят общий бюджет ресурсов.

Windows-адаптер может сам установить аутентифицированное соединение с ядром
через опубликованный локальный порт. Так ядру не требуется прямой доступ
к драйверу VB-CABLE или к игровым клавишам из контейнера. Предлагается
исходящее соединение от адаптера к ядру; другие направления/маршруты
проверяются отдельно при интеграционных пробах.

На Windows порт панели/API публикуется только на loopback; внутри контейнера
адрес прослушивания выбирается для его сети. Redis не публикуется наружу.
Адреса, порты, подключения, ограничения и сопоставления каталогов конфигурируются.
Локальный транспорт проверяет отправителя, область и поколение управления.

## Три класса доставки

| Класс | Примеры | Правило |
| --- | --- | --- |
| Оперативное состояние | Положение, видимые объекты, состояние аватара, статус панели | Ограниченный буфер, объединение обновлений, последнее актуальное состояние; полная история каждого кадра не нужна |
| Сохраняемые задания/значимые события | LLM-задание, рефлексия, индексирование, подготовка публикации, рендер | БД + outbox + брокер, подтверждения, конечные повторы, восстановление |
| Остановка и управление ресурсом | STOP, ручной захват, снятие кнопок, прерывание речи | Прямой путь управления и локальный watchdog; выполнение не ждёт очереди или исправности Redis |

Аудио/видео передаются потоковым каналом или ссылкой на разрешённый артефакт;
крупные бинарные данные и каждое движение не отправляются в постоянную очередь.
Нужные биографии значимые наблюдения записываются отдельно с источниками.

## Выбранный Redis Streams

Для сохраняемых заданий выбран **Redis Streams с consumer groups**.
Они поддерживают подтверждение обработки и учёт незавершённых сообщений;
приложение организует возврат задания после сбоя работника. Обычный Pub/Sub
допустим для необязательных уведомлений, потерю которых исправляет перечитывание
состояния; критичное задание не полагается на такую доставку.

Redis отвечает за доставку. Источник истины о задании, разрешениях и результате
остаётся у владельца состояния в основной БД. Персонаж и гейммастер обращаются
к общему контракту задания, не вызывают команды Redis напрямую. Брокер можно
заменить адаптером, сохранив явно описанную семантику доставки и отмены.

Предлагается AOF на постоянном томе, с исходным кандидатом `appendfsync everysec`.
Это уменьшает потерю очереди при перезапуске, но не означает нулевую потерю
последних записей при аварии. Сохранённые задания и сверка outbox позволяют
переиздать недоставленное из БД. Целевой режим fsync выбираем вместе с дисковыми
замерами. Точная версия/лицензия образа фиксируется до реализации.

## Жизненный цикл задания

1. Владелец состояния транзакционно сохраняет задание и запись outbox
   в основной БД. Приём подтверждается только после устойчивого сохранения.
2. Диспетчер отправляет в поток ссылку на задание с устойчивым ID; при сбое
   доставки запись остаётся для повторной попытки. Redis и БД не считаются
   одной атомарной транзакцией; повторная отправка возможна.
3. Работник получает сообщение и запрашивает у владельца право выполнения:
   статус, разрешения, deadline, актуальный контекст и аренду с номером попытки.
4. Работник выполняет ограниченную операцию и продлевает живую аренду.
   Результат принимается владельцем только для актуальной попытки/поколения.
   Работники не записывают напрямую чужую SQLite/память.
5. После фиксации результата либо терминального состояния работник подтверждает
   обработку через `XACK`. Получение сообщения само по себе не завершает задание.
   Побочные изменения в других хранилищах имеют свои статусы применения.
6. После сбоя незавершённая доставка может перейти другому работнику;
   перед повтором проверяется аренда в БД. Истечение ожидания в Redis само
   по себе не доказывает, что прежний исполнитель прекратил работу.

Один ID задания может приходить несколько раз. Защита от дублей и номер попытки
не позволяют повторно принять один результат; результат старого работника
после смены аренды отклоняется. Публикации дополнительно учитывают внешний ID
и статус «исход неизвестен»: повтор доставки не даёт права повторить пост.
Гарантия однократного внешнего воздействия без поддержки внешнего API
не обещается. Исполнители повторно проверяют отмену перед воздействием.

Отложенное задание хранит время готовности в БД. Планировщик допускает его,
когда наступил срок и есть ресурсы; не полагается на точность Redis TTL.
Повторы ограничены числом/сроком, имеют задержку и случайный разброс.
Исчерпание попыток создаёт видимый терминальный отказ/запись неуспешного
задания. Ручной повтор заново проверяет условия, редакцию и разрешения.

## Приоритеты и ограничение нагрузки

Предлагаются отдельные полосы для актуальных ответов/их модерации и фоновой
работы. Классы, приоритеты и ресурсы задаются описанием возможностей;
платформа не зашивает фиксированный перечень игровых/персонажных задач.
Streams сами по себе не определяют полезность, приоритет, дедлайн или отмену:
это ответственность планировщика и контроллера.

Есть общие и локальные лимиты очередей, числа работ, API/CPU/RAM и времени
ожидания. Просроченный ответ не проигрывается после смены контекста. При
перегрузке телеметрия объединяется, фоновая работа откладывается, а новое
критичное задание явно отклоняется либо остаётся сохранённым в пределах
квоты с состоянием «ожидает доставки». Безграничного буфера в БД тоже нет.

Для Redis предлагаем ограничение памяти и режим `noeviction`: переполнение
не должно молча вытеснять сообщения очереди. Нужен запас на служебные буферы
и AOF; `maxmemory` не равен полному RSS контейнера. Размер потока ограничивается
с учётом подтверждений и зависимых потребителей; не используем слепую обрезку
как гарантию сохранности pending. Остатки доставки можно восстановить по БД.

Очередь содержит преимущественно ID и минимальные метаданные. Текст диалога,
секреты и медиа не дублируются в AOF ради удобства. Права/удаление/сроки исходных
данных проверяются и при позднем исполнении. Рабочие и тестовые задания
имеют разные области; сообщение из теста не включает рабочий адаптер.

## Хранение, запуск и отказ

Предлагаются отдельные постоянные тома для БД/индекса и Redis; БД принадлежит
одному сервису. Читаемые Markdown, медиа и экспорт могут иметь отдельные
разрешённые каталоги Windows. Они передаются через ID артефакта и сопоставление
путей, а не произвольную общую папку всего диска. Проверка файловой системы
и библиотек памяти теперь проводится в целевом Linux-образе на Windows.

Том переживает пересоздание контейнера, но не заменяет согласованную резервную
копию. Копирование живых файлов SQLite/Markdown без протокола не считается
согласованным backup. Восстановление учитывает D29–D30, поздние удаления,
версию схемы и состояния заданий; восстановленные воздействия не запускаются
автоматически. Перенос с named volumes в экспорт проверяется отдельно.

API-ключи остаются локальным источником `.env`, вне образов и репозитория.
При реализации доступны только нужным сервисам; их не выводят диагностика,
панель и журналы. Рецепт сборки не получает секреты как содержимое образа.

При старте проверяются схема/миграции, готовность хранилищ и подключений.
Используем healthchecks и ожидание готовности зависимостей; отдельно проектируем
повторное подключение и ограниченный перезапуск процессов. Healthcheck сам
по себе не обеспечивает восстановление зависшего приложения. Возвращение
контейнера в running не возобновляет остановленное управление.

Если Redis недоступен, API по возможности показывает состояние и принимает
STOP; новые задания не исполняются в обход политики. Если БД недоступна,
задание/воспоминание не получает ложное подтверждение сохранения. Если ядро
или Docker остановлены, Windows-исполнитель освобождает управление по локальной
остановке/истечению аренды. Восстановление сначала сверяет состояния,
поколения, сроки и неизвестные результаты, затем ждёт разрешённого продолжения.

При 16 ГиБ RAM проверяем весь Docker/WSL плюс ОС и будущие Windows-приложения.
Контейнерные лимиты не описывают весь расход VM. Большая локальная LLM,
постоянно загруженные аудиомодели и кластер брокеров не требуются для MVP.
Числовые пределы ещё не измерены. GPU в контейнере требует отдельной проверки
WSL/драйвера/образа; установленная Windows CUDA/cuDNN не подтверждает зависимости
внутри Linux-контейнера.

## Будущая проверка устойчивости

Обязательные сценарии до признания реализации готовой: сбой работника до/после
фиксации результата и до ACK; повторная доставка; потеря/перезапуск Redis;
зависший работник и смена аренды; недоступная БД; переполнение RAM/диска/очереди;
STOP при заполненном потоке или выключенном брокере; устаревшее одобрение;
сон Windows/остановка Docker; восстановление с истёкшими/удалёнными источниками.
Проверяем отсутствие двойного применения, понятный статус, освобождение ресурсов
и явное возобновление. Эти проверки пока не проводились.
