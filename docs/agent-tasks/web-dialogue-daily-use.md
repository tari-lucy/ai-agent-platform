# Веб-диалог для повседневного использования

Назначение второго агента после интеграции private-dialogue-memory-quality.
Координатор продолжает deployment, live probe и recovery; UI-файлы не меняет.

## База и зона

Fetch origin/main, прочитай AGENTS/README/docs25/07/24/27 и 05/16/19/21,
Integration-private-memory-review и local-host-setup. Проверь root/branch/status,
создай отдельный checkout и ветку codex/web-dialogue-daily-use от текущего
проверенного origin/main, укажи base SHA. Старую feature-ветку не продолжай.

Владеешь apps/panel/src/ui/dialogue/**, tests/dialogue.test.ts внутри apps/panel,
новыми dialogue-specific UI/browser tests, своим отчётом
Integration-web-dialogue-daily-use.md. В shared/api.ts передаю только добавление
optional cursor к inbound/utterances/deliveries/operations/briefings: существующий
сигнал и валидатор сохраняются, cursor передаётся в существующий #read. Координатор
этот файл параллельно не редактирует. Общие contracts/validation/cache/events,
backend, зависимости/lockfiles/Compose, остальные экраны остаются за координатором.
Нужный shared change — точный запрос, без запасной схемы или копии клиента.

## Результат

1. Пользователь видит переписку за пределами первой страницы. Нет дублей,
   пропусков или смешивания WORK/TEST/личностей, ошибка страницы видна и не
   выдаётся за конец истории. Неполная история помечена честно, память ограничена.
2. Загрузка истории сохраняет видимую позицию. Новый ответ не уводит вниз
   читающего старые сообщения; есть переход к новым. Если пользователь уже
   внизу, лента следует за ответом. Одна временная строка stream, без дубля final.
3. Принято/обрабатывается/готово/ошибка/неизвестный исход объясняются по данным
   ядра. Потеря сети не создаёт повторный message или второй request_id; поле
   ввода не теряется при ошибке. Raw-диалог/черновики в localStorage не добавляй.
4. После переподключения/перезагрузки страницы исходные операции сверяются,
   старые данные не маскируют потерю связи. START не происходит автоматически,
   STOP доступен. Поздний ответ не оживляет остановленный run.
5. ACK только окончательной точной редакции в действительно видимой вкладке
   и viewport. Offscreen/hidden/stream/старая revision/чужой scope не подтверждаются.
   Ручной путь после ошибки сохранён, автоматических повторов мутаций нет.

## Важный API-стык

Не считай opaque cursor или id датой. Сначала проверь реальный порядок выдачи:
общий repository list может идти по id, а не по времени. Если API не даёт
надёжно получить последние сообщения и затем более старые, пришли координатору
минимальный запрос: route/query, сортировка, состав cursor, связь страниц при
новой записи и проверка. Не объявляй полную историю или «старые страницы»
по предположению. Независимо продолжай scrolling/status/reconnect; не внедряй
прямой SQL из панели или второй журнал. Текущий REST/WS route не меняй молча.

## Проверка и сдача

Один affected UI-набор, typecheck/build/lint. Один browser-сценарий на реальном
local host с synthetic/mock provider: больше страницы записей, прокрутка,
новый ответ во время чтения, обрыв/возврат связи, reload, STOP и visibility ACK.
Отдельно перемешай хронологию и id в данных, чтобы не спутать сортировку.
Не запускай полный backend suite, paid API/LLM judge и мутационную кампанию.
Используй проектные версии инструментов, не меняй системный Node молча.

Небольшие commits, push ветки, main не сливать. Сдать base/HEAD, реальные
проверки, ограничения и конкретные запросы владельцам; mock отдельно от live.
