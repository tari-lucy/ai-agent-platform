# Claude: родной OpenCode как одно окно для персонажей

2026-10-23. Продуктовое решение оператора: родной Web OpenCode — основной вход;
панель — диагностика/наблюдение. TUI позже. В основном окне должны быть выбор
любого разрешённого персонажа, его сессии, свободный разговор и работа.

**Сейчас поручено документирование, а не старт нового coding-пула.** Сохраняется
ранее отдельно выданная тебе задача invalidation/revoke; закончи её по исходному
brief. Исходники invalidated_reason в agent_sessions.py/panel.py согласованы,
окно экспорта после main 382af58 свободно. Этот план не отменяет твою поставку.

После отдельного «начинаем реализацию этого пула»:

1. Прочитай AGENTS.md/doc27 и [план OC-00–OC-07](../30-opencode-user-interface-plan.md).
   Сверь origin/main, clean checkout, base, dependencies и конкретные shared-окна.
2. Твой пакет: **OC-02, OC-03, OC-05, OC-06**. Ты владелец вертикального результата,
   самостоятельно реализуешь, тестируешь, коммитишь, пушишь и интегрируешь свои
   пакеты после проверок и сверки main. Одобрения Codex каждой задачи не требуется.
3. Codex делает **OC-00/01/04/07**: проверку native transport, ранний bridge-контракт,
   server/sandbox/gateway, Docker/Windows и личный deployment по отдельному допуску.

## Что сделать

- **OC-02 — та же личность и память.** Используй принятые owners и release/context.
  Разговор и поручение в одной сессии; бриф/состояние/память/обязательства/связанные
  задачи берутся по выбранной личности и её правам. Два вымышленных персонажа,
  разные воспоминания и сессии. Отзыв, TTL, invalidation, ACK/опыт без дублей.
- **OC-03 — родной интерфейс.** Подключи upstream Web UI к опубликованному bridge,
  с минимальным сопровождаемым патчем, если он нужен. Каталог агентов → сессии →
  свободный разговор; материалы, прогресс и ссылки на обращения. Полноценные
  ответы и решения по правам остаются в панели, без второго чата (уточнение
  оператора 2026-10-23). Просматриваемый агент не равен активному исполнителю.
  Нельзя выдавать
  Build/Plan OpenCode за личности платформы или создавать новый основной чат
  вместо нативного UI. Не отключай функции «для вида»: обходные операции должны
  быть закрыты на сервере.
- **OC-05 — один начальный допуск.** Это отдельное структурированное решение
  оператора по настроенному набору, а не серия обращений на знания/навыки/OpenCode.
  Один preview/confirm → атомарные обычные Permissions того же владельца. Пины
  manifest/binding/current-permission/policy, ceiling, сроки, replay и отзыв
  обязательны. Прежние обращения набора завершаются owner receipt; новые tools
  не присоединяются автоматически. InitialAccess-контракты уже в main 382af58.
  Черновик Codex в другом checkout не принят, его перенос не является зависимостью;
  самостоятельная реализация от контрактов допустима. Код черновика не развивают
  параллельно два исполнителя.
- **OC-06 — Linux/headless.** Один meaningful journey через родной UI и production
  owners с синтетической моделью: выбрать A, поговорить/поручить, получить результат,
  ACK/опыт, обращение/ответ, выбрать B и вернуться, reload, revoke, STOP/restart.
  Отрицательная попытка пройти напрямую к модели/терминалу/чужой сессии закрыта.

## Зоны и координация

Твои: agent_experience/context/release, проекции каталога/истории, tickets,
initial-access permission package, минимальная адаптация родного Web UI,
соответствующие unit/HTTP/browser tests и отчёты.

Codex: opencode_ui bridge, agent_harness/sandbox, local_host launcher/config,
deploy/opencode и Windows/Docker. Не менять эти зоны без передачи.

OC-01 сначала публикует wire-контракт. Затем именное окно shared-файлов передаётся
тебе для совместимых добавлений; api.py/catalogue.py/generated — один writer.
Для OC-05 подготовь узкие local_host/service/views/access вставки владельцу окна,
не делай вторую схему прав/владельца или обходную копию конфигурации.
До integrated-зависимостей — независимая подготовка, не вымышленный работающий bridge.

Нет новой личности OpenCode, собственного архива памяти, отдельного ключа,
неограниченного home mount, прав из текста навыка/сообщения. Несколько личностей
в каталоге не дают нескольких одновременно работающих runtime: F7 отдельно.

Один affected gate на пакет; после падения повторять только затронутое. Никаких
платных API, личных данных или Windows-обещаний из Linux. Изменение enforcement
прав/удалений/STOP требует узкого перекрёстного просмотра по doc27 §8 до включения
на личном host, а не повторного тестирования всего проекта Codex.

Сдача: commit/base, changed files, результаты, mock/real отдельно, ограничения,
запросы владельцам только с конкретным gap. Не объявлять native UI готовым,
пока работает лишь экран «Работа» старой панели.

## Уточнение панели — 2026-10-23

Общение и поручения — только в OpenCode после готовности нового входа.
Панель — настройки/наблюдение и полноценные обращения. Подготовленный отдельный
пакет Claude: [PUI-01–PUI-04](panel-control-claude-pool.md). Он уточняет ранние
формулировки о решениях по обращениям в основном окне; второго редактора прав
в OpenCode не требуется. До переключения старый вход сохраняется временно.

## Ранняя поставка OC-01

Опубликован [bridge `aw-opencode/1`](../protocols/opencode-bridge-v1.md): точные
маршруты, directory/SessionBook ID, прежние команды/receipts, transcript/release,
ACK, прямой STOP и текущий WS-стык. Можно готовить OC-02/03 от этого интерфейса,
не ожидая OC-04 целиком. Это не готовый native API и не generic reverse proxy:
адаптация upstream SDK остаётся OC-03, изоляция/native transport — OC-04.
Scopes/cursors конечны, выбранный профиль не равен активному runtime; endpoint
активации другого исполнителя пока не опубликован. Показать честное ожидание.

До включения на личном host нужен узкий просмотр нового dispatch и разрешения
metadata intake в неактивной уже авторизованной области (m3_composition/access.py).
Новые grants/runtime права не выдаются. Контракты api.py/catalogue.py/generated
эта поставка не меняет; своё окно shared-экспорта всё равно согласовать.

Оператор дополнительно хочет независимо назначать доступ к модели рабочему
OpenCode (желателен аккаунт ChatGPT) и API-модели автономному контуру. Поддержка
аккаунтного транспорта ещё не доказана; OC-03 не добавляет прямой OAuth/provider
обход. Это отдельная проверка Codex OC-04, не новая личность или память.
