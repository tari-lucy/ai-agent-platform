## Действия на рабочем host после интеграции

1. **Этап 2:** при остановленном сервере `python -m ai_agent_core.local_host
   enable-social --root <host>`. До этого диалог работает анонимно, как сейчас:
   обновление кода ничего не ломает. Команда переприменяет текущую матрицу прав work
   scope. Других грантов там нет: их выдаёт только `init`. Проверьте это на копии, если
   на хосте что-то выдавалось вручную.
2. Пересборка панели (`npm run build`) — этапы 2, 4, 5 меняют UI.
3. Остальное подхватывается само: retention-sweep, `tick`, контекст.

## Узкие места и на что смотреть

1. **Права (этап 2, авторизовано оператором).** SOCIAL получил запись своих записей и
   чтение MEMORY/CHANNEL; оператор — чтение SOCIAL с `api_transfer`; social-принципал
   добавлен в `record_readers()` (только чтение). Старые источники ACL для SOCIAL не
   получают: основанием обещания будут только новые сообщения.
2. **Shared contracts (этап 2, авторизовано):** `EditCommand.type` += `promise.close`,
   `PromiseCloseArguments`, перегенерированы schema/OpenAPI/TS (`export --check` OK).
   Других изменений контрактов в пуле нет. `TaskInput` (m3 schemas) расширен на
   этапах 6 и 7 — это composition, не contracts.
3. **Порт storage (этап 1):** `RecordRepository.recent(cites=…)` — необязательный
   параметр, единственная реализация — SQLite-адаптер. Если считаете порт общим,
   примите как shared change.
4. **Политика хранения (этап 3):** выдержки живут 365 дней от события и наследуют права
   разговора на момент выдержки; пока разговор жив, отзыв и удаление следуют на выдержку.
   После истечения разговора выдержкой управляют как обычным Source (план удаления в
   панели). `retain_lead` = 7 дней, `excerpt` = 365 — в `RetentionPolicy` (код).
5. **Автономные задачи (этап 7):** `authorize_submission` теперь допускает автономный
   `consolidate`, но **только** с `digest_of` и при `memory_processing`. Это расширение
   автономии в рамках того же резерва памяти.
6. **Продление аренды (этап 2, `67cd515`):** найдена реальная причина отмены ответов на
   долгих сессиях. Проверка политики живёт 2 с (`policy.py`), медленная запись SQLite
   её просрочивала. Теперь тот же запрос продления повторяется до 3 раз только при
   `STALE_CONTEXT`. Посмотрите, не лучше ли поднять TTL проверки в `policy.py` (не трогал).
7. **Межзапусковый scope.** Записи хранят `agent/run/session` того запуска, где созданы,
   а `unit.put` сравнивает scope целиком. Исправлено в social (`_write`) и memory
   (`_transition`, ссылка противоречия в `record_claim`). Другие владельцы могут иметь
   тот же дефект при правке записи прошлого запуска — стоит проверить GM/persona/channel.
8. **Индекс claim→source.** Фоновые задачи памяти теперь пишут связи в индекс (этап 2).
   На рабочем host старые claims в индексе связей не имеют до `reindex_scope`. Этап 1
   использует авторитетные `source_links` и от этого не зависит.
9. **Шумные/базовые падения** (есть и на чистом `638162c`, проверено):
   - `tests/memory/test_recall.py::test_conflict_ids_follow_the_readers_access_to_the_claims`;
   - `tests/m3_runtime/test_http_laboratory.py::…[False]`;
   - `tests/m3_runtime/test_workflows.py::test_post_session_uses_existing_extractor…`.
10. **Окружение Linux этой машины:** venv привязан editable-установкой к старому worktree
    `m4-02`, поэтому тесты шли с `PYTHONPATH` на src checkout. `test_guards::
    test_import_has_no_effects` (запускает `python -I`) здесь падает только из-за этого.
    Модули с одинаковыми именами в разных каталогах тестов нельзя собирать одним
    процессом pytest. Под двойной параллельной нагрузкой падали `test_live[lifetime]` и
    `test_panel` smoke; отдельно проходили. Windows не проверялся вовсе.
