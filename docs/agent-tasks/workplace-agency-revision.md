## 2. Целевой путь

1. Оператор обсуждает поручение с тем же персонажем в панели. Вход связывается
   с проектом/задачей/сессией и имеет стабильный request_id. Просмотр и отправка
   в STOPPED возможны, но исполнение ждёт явного START.
2. При действующем допуске агент получает личность, релевантную память,
   обязательства, карту пространства, текущие дела и manifests доступных tools.
   Это ограниченный, проверенный контекст, не весь архив в каждом prompt.
3. LLM в рабочей среде разбирается, уточняет, планирует и выбирает действия.
   Может заниматься своим делом, сменить метод, подождать или отказаться.
   Scheduler ограничивает время/очередь/повторы и выдаёт допуск, но не выбирает
   содержание занятия. Не нужен новый предписанный сценарий для каждой профессии.
4. Все инструменты проходят existing capability/binding/permission/admission.
   Все внутренние LLM-вызовы/повторы/сжатие контекста — общий gateway и бюджет.
   Лимиты и резервы — конфигурация, не обход через собственный ключ OpenCode.
5. Недостающий доступ порождает тикет. Ответ оператора — информация, а выдача
   права — отдельная структурированная команда. Разрешённые шаги согласовывать
   по одному не требуется. Блокируется зависимое дело, не весь агент.
6. Файлы/версии/результаты сохраняются владельцами; подтверждённый исход с
   receipts становится основанием опыта. Фраза «я сделала» не заменяет receipt.
7. Новое сообщение, ответ на тикет или пробуждение продолжают допустимую работу.
   STOP отзывает допуски; поздние ответы не применяются. Restart/restore STOPPED,
   продолжение после START начинается со сверки unknown, а не повтора вслепую.

Разговор и работа используют одну идентичность и существующие owners сообщений.
Нужны явные правила маршрутизации и прерывания/возвращения к занятию: одно
входящее событие не запускает два независимо отвечающих контура. Сохранение
старого private dialogue при переходе допустимо; нельзя выдавать его наличие
за готовый новый рабочий разговор. Точный transport выбирается в R1.

Сессия — логическая связь разговоров, задач и checkpoints. Контейнер не обязан
жить постоянно; после его замены можно продолжить допустимое дело. Checkpoint
не источник прав и не бессрочная скрытая память. Session history/summary/cache
проверяют scope/versions/TTL/ledger; недопустимый контекст отбрасывается и
пересобирается. Если нет надёжной выборочной очистки, инвалидируется сессия,
а исходная задача остаётся для безопасного продолжения с новым контекстом.

## 3. Назначения после возобновления coding

OpenCode не требует GUI как продуктового условия. Linux/VPS подходит для
большой части application/API/UI-кода и headless-проверок. Основной интегратор
назначен по доступности целевой Windows/Docker-машины, не по превосходству ОС.
Ниже — полноценные coding-пакеты, не обязательная сдача всей работы Codex.

| Пакет | Владелец / зависимость | Выданная зона и результат |
| --- | --- | --- |
| R1 / AW-05-R + AW-08 | Codex; integrated AW-00/02/03/05/06/07, завершение нужных AW-04 gates | Минимальный session-порт/команды и events; adapter OpenCode; routing и ведение деятельности; `agent_workplace/ports.py`, новые session contracts, `agent_activity`, `agent_harness`, `m3_composition/activity.py`, отдельный session module и узкое service/state wiring. Один совместимый lifecycle contract публикуется первым |
| R2 / AW-06-R + ticket release | Claude; контракт R1 для session-consumer, независимая provenance-часть возможна раньше | `agent_experience`, `workplace_experience`, `tickets/service.py` и owner release module; tests соответствующих областей. Контекст личности/памяти, ответы на тикеты и безопасные исторические SourceRef/ArtifactRef; bridge получает его через owner port |

Рабочий разговор, уточнение цели, ожидающий ответ, продолжение и явное состояние связи/работы без второго login/STOP/клиента |
| R4 / AW-04/09/10 | Codex; session-порт R1, R2 release и AW-08 для полного gate | Общий budget/admission broker, изоляция Windows Docker Desktop, purge session/runner caches, backup/staged restore/switch и production launcher. Не смешивать приватный host с synthetic stack |
| R5 / AW-11 | Codex — итоговый локальный integration gate; Claude — Linux/headless gate | Один journey на общей ревизии с реальным OpenCode, synthetic provider и владельцами. Claude самостоятельно публикует Linux tests/fixes в своей зоне; Codex проверяет Windows/Docker/browser на целевом host |

R1 меняет AW-05 orchestration; R2 не переписывает `activity.py`/`service.py`.
R3 использует отдельный HTTP module; registration/shared-файл передаётся
одним коротким окном после публикации порта. Новые exports/contract schemas
и их генерация принадлежат текущему writer R1, затем передаются R3 для его
совместимых additions. Lockfiles: один writer конкретной зависимости.
Полные modules не закрепляются навсегда за одним агентом.

Общие права/STOP/изоляция/удаление требуют только узкого взаимного разбора
до enable, как doc27 §8.7; R2/R3 не ждут именного одобрения Codex каждого commit.
Одна ветка/checkout на пакет, обычный merge/push, fresh main и affected tests.
Существующую работу Клода не reset/переписывать: если AW-08 уже начат, сохранить
branch/HEAD, перечислить сделанное и передать стык Codex. До явной передачи
занятого файла новый writer не правит его; независимая работа продолжается.

### Первое поручение Клоду после возобновления: R2

Начать от свежего main в собственной ветке, зафиксировать base и ownership.
Исправить release тикетов/истории: учитывать исторические основания и materials,
не терять provenance при ограничении списка refs. Отзыв/TTL/ledger закрывают
выдачу в панель и модель до physical purge. Безопасный первый вариант — скрыть
весь неразделимый body, если закрыто любое основание. Нужный файловый guard
использовать через owner, не копировать его логику. Сессионную часть подключить
после R1; до этого сделать готовый owner-port и его тесты. Не менять sandbox,
BackupService, physical purge или `m3_composition/activity.py`.
Один meaningful affected gate на синтетических данных и отчёт с ограничениями;
реальные API/приватный host не нужны. Затем R3 по опубликованным контрактам.

## 4. Порядок, критерии и незакрытые решения

1. Зафиксировать это уточнение и передать updated brief Клоду. **Сейчас только
   этот документационный шаг.** Новое coding-поручение оператора снимает паузу.
2. Codex публикует минимальный R1 lifecycle/interaction contract. Claude делает
   независимый R2 release/context. Сохраняются current owners, без второго
   registry/jobs/memory store. Нужные shared-окна фиксируются до правки.
3. Codex закрывает broker/gateway prerequisites и запускает настоящий OpenCode
   в sandbox на вымышленных материалах. Claude подключает R2/R3 и Linux gate.
4. Один combined путь: поручение → обсуждение/уточнение → самостоятельный план
   → поиск/чтение навыка → разрешённый helper → сохранённый результат/receipt
   → опыт; отсутствующий инструмент → тикет → ответ/допуск → продолжение.
   Второе содержательно другое занятие выбирается по данным без новой if/else.
5. Проверить: история одной личности, верный request_id/replay, отсутствие
   двойных ответов/действий; budget/reserves для всех внутренних вызовов;
   STOP во время работы, поздний результат, restart STOPPED, продолжение
   после START и unknown reconciliation; revoke/TTL, очистка session/cache и
   restore старой копии без оживления данных. Headless Linux и Windows Docker
   отмечаются раздельно; scripted модель доказывает маршрут, не качество.
6. До полного lifecycle/isolation gate и узкого cross-review режим выключен.
   Перенос пользовательского host и выдача новых прав — отдельное поручение.

R1 должен выбрать/проверить exact OpenCode version/transport, механизм tool
bridge и bounded checkpoint/resume, порядок входящих сообщений/прерывания,
лимиты сессий/контекста/простоя. Это открытые технические решения, а не уже
существующие возможности OpenCode. Если SDK не удерживает нашу границу,
зафиксировать конкретный gap и минимальное решение, не ослаблять права и
не строить молча второй большой harness. Документационное уточнение не
устанавливает программу и не доказывает совместимость выбранного transport.
