# Автономный внутренний GM для приватного MVP

## Цель и приоритет

Следующая задача второго агента после завершения и интеграции
web-dialogue-daily-use. Довести один полезный сквозной путь: подтверждённый опыт
→ ограниченное внутреннее предложение GM → сюжетная проверка → контекст
персонажа → свободное решение персонажа в обычном приватном диалоге.
Одного переключения mock на live недостаточно. Предложение не является
пережитым событием и не даёт основания менять биографию или характер.

Оператор начинает пользоваться MVP сейчас. Не расширять задачу до новых каналов,
публикаций, игры, голоса, универсального планировщика или большой оценки моделей.

- Суточная память и reflection работают отдельно; резерв памяти 8 входит

## Требуемое поведение

1. Явное offline-включение и выключение GM для подготовленного host.
   По умолчанию у прежних host выключен. serve не мигрирует, не меняет bindings
   и не выдаёт Permission. Подготовка использует OS host lock; прерывание закрывает
   serve, повтор завершает операцию. Включение/выключение не ослабляет проверку
   назначения ролей при backup/restore: использовать единое правило bindings,
   несовместимый snapshot закрывать; нужный shared change запросить владельцу.
   Не менять рабочий host пользователя.
2. Настройки GM отдельно от memory_processing: enabled, конечная частота и
   суточный потолок. Разумный старт при явном включении: до 2 предложений/сутки
   и до 4 API-вызовов GM/сутки, интервал не менее 60 минут активного времени.
   Это изменяемые значения конфигурации с валидацией, не продуктовые константы.
   Все вызовы (включая story-screen, неуспешные и неизвестные) входят в общий
   лимит 300 и GM-потолок. Не расходовать защищённый остаток памяти; резерв
   GM не должен обнулять доступный диалог. Общий story-screen используется и
   рефлексией: относить расход к фактической операции, не ко всем вызовам этой
   роли сразу. Без бюджета — пропуск без retry.
3. Запуск только ACTIVE/OPEN/autonomous/WORK, при включённом GM и intensity > 0.
   Диалог и суточная память имеют приоритет. Нет бесконечной очереди, burst после
   простоя или платных повторов failed/unknown после restart. Использовать
   существующие Jobs/owners и durable сведения, не новый сервис расписаний.
4. Нужен доступный подтверждённый опыт и подходящая линия по принятой модели
   GameMaster. При отсутствии основания/линии/допуска — честный no-op с причиной,
   без API-вызова. Проверить штатный путь создания/активации линии из профиля
   или уже существующего управления; не создавать фиктивную линию ради успеха.
5. GM предлагает только доступные приватному MVP ситуации/занятия. Нет обещания
   публикации, мнимой внешней деятельности, предрешённых действий/чувств людей.
   Story-screen проходит до предложения; его недоступность закрывает предложение.
6. Следующий обычный диалог получает только действующее CharacterOffer в рамках
   контекстного бюджета. Персонаж может принять, отказаться или проигнорировать.
   Явный переход состояния проводится владельцем через закрытое валидированное
   решение по точному ID/версии, а не по совпадению слов в reply.
   Если понадобится добавление поля в application DialogueDecision — оно optional,
   старые ответы остаются валидны. Полный текст плана GM в разговор не вставлять.
7. Не добавлять самостоятельную отправку сообщений пользователю без входящей
   реплики. GM здесь внутренний источник возможностей; это ограниченный этап
   автономности. Полноценная инициатива общения без входящего сообщения — отдельно.
8. Принятие предложения не означает его исполнение. Opportunity разрешается
   только по настоящему подтверждённому исходу. Отказ/игнорирование не блокируют
   диалог; действуют TTL, cooldown и существующий отдых после отказов.
9. STOP/pause/отзыв права/смена profile/rules/scope/version во время API-вызова
   исключают применение результата. Restart остаётся STOPPED. Источники,
   доступ/TTL/API-transfer проверяются перед отправкой и применением результата.
10. Использовать существующие проекции GM/jobs/usage для наблюдения: что предложено,
    что отклонено, почему пропущено, сколько вызовов. Не добавлять в логи текст
    диалога/промпты/ответы/endpoint/ключи. Расширение UI в эту задачу не входит.

## Приёмка — экономно и сквозным сценарием

Один production local host с вымышленным разговором и synthetic HTTP provider:
подтверждённый опыт и допустимая линия → автоматический tick → GM + story-screen
→ сохранённое предложение → следующая реплика персонажа видит только допустимую
часть → принятие/отказ по ID → только подтверждённый исход даёт опыт.
Не ограничиваться тестом PrivateLiveProvider в отрыве от runtime.

В том же узком наборе проверить: диалог имеет приоритет; нет пригодного опыта;
нет линии; выключено/paused/STOPPED/TEST; лимит/резерв/cooldown; повтор tick/restart
не списывает повторно; отказ или timeout story-screen; STOP/отзыв источника
во время ответа; истёкшее предложение; отказ персонажа и продолжение разговора.
Показать учёт обоих вызовов и защиту памяти/общего лимита на границе бюджета.

Один целостный affected pytest-набор после реализации, Ruff и mypy по проектному
конфигу. После исправления падения повторять только затронутое. Полный combined,
мутационная кампания, UI suite и платные пробы не нужны. Никаких live API-вызовов,
чтения .env для диагностики, скачиваний, контейнеров и установки глобальных пакетов.
Windows не объявлять проверенным по Linux: дать координатору одну короткую команду
synthetic smoke. Native ACL/host lock/recovery guards сохранить.
