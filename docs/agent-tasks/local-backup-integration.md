# Задача второму агенту: резервирование и восстановление локального host

## Цель и база

Довести существующий M5-02 до воспроизводимой эксплуатации с production local host.
Оператор должен уметь создать и проверить копию, увидеть последствия восстановления
и восстановить подготовленный host без запуска агента и без возвращения удалённых данных.
Это задача для пробного запуска, а не новая реализация backup с нуля.

База кода: `7cf69bec3a9ef3b77975dc339d2dfc5f74ed240e`, проверенный main.
Перед началом fetch и проверка origin/main. Более свежие docs-only коммиты допустимы.
При изменении кодовой базы изучить diff; не откатывать чужие изменения до старой базы.
Ветка: `codex/local-backup-integration`, отдельный checkout. Main не менять.

Прочитать AGENTS, README, docs 25/07/24/27 и относящиеся 03/14/17–20/23;
далее docs/implementation-reports/M5-02.md, README модулей backup,
docs/local-host-setup.md, local_host/layout.py и process.py на текущем main.
Сначала проверить root/branch/status/base и кратко изложить план, затем работать самостоятельно.

## Разделение владения

Первый агент сейчас меняет автономный суточный цикл памяти/рефлексии и его панель.
Его зона: local_host/**, m3_composition/**, development/reflection, extraction,
contracts/exports, storage interfaces, общий UI/API client и scheduler.
Не вносить туда правки и не создавать альтернативные owners, схемы или loopback API.

Твоя зона:

- новый `apps/core/src/ai_agent_core/local_backup/**`: тонкая production composition
  существующего BackupService и отдельный CLI entrypoint этого пакета;
- `packages/application/src/ai_agent_application/backup/**`,
  `packages/adapters/src/ai_agent_adapters/backup/**`: необходимые адресные исправления;
- `tests/local_backup/**`, точечно `tests/backup/**`;
- `docs/local-backup-setup.md`, `docs/implementation-reports/Integration-local-backup.md`.

Не менять зависимости, lockfiles, Compose, миграции, общий реестр решений/задач,
retention owner, local_host CLI/права и общие контракты без принятого запроса координатору.
Публичную фабрику/callback создания копии подготовить для последующего подключения
координатором к суточному циклу; сам цикл, основной CLI и UI сейчас не трогать.

## Результат

1. Тонкая composition существующих BackupService, SQLiteSnapshotter,
   DirectoryBackupStore, staging/ledger/switcher. Никакого второго формата резервирования.
   CLI нового пакета: create, list, verify, preview-restore, restore; пути абсолютные,
   хранилище копий и независимый ledger выбираются явно и не пересекаются с живой БД.
2. Копия согласованна с WAL: SQLite backup API, проверки целостности и манифеста.
   Разрешённый состав файлов задан allowlist. .env, ключи, operator-password.txt/hash,
   логи и личные внешние каталоги не добавлять. Индекс пересобирается при restore.
3. Restore выполняется только offline: существующая OS-блокировка host удерживается
   до конца проверки/переключения, действующий serve отказывает операции. Проверить
   совместимость копии с host.json/профилем/областью текущего host; восстановление одной
   БД не должно оставлять несовместимые назначения live-ролей или настройки host.
   Не объявлять STOPPED только по старой записи RunSession.
4. Перед восстановлением — проверенный preview/digest и явный decision ID, страховочная
   копия; staging → deletion ledger → retention → reindex → integrity → switch.
   Незавершённые задания/outbox не переисполняются, UNKNOWN остаётся неизвестным.
   После восстановления агент сам не запускается.
5. Отсутствующий/подменённый/откаченный ledger закрывает восстановление. Не создавать
   новый пустой ledger взамен истории удалений. Если в production host пока нет принятого
   retention/ledger binding, оформить точный запрос координатору и проверить composition
   на полноценном изолированном fixture. Не маскировать незакрытый production-стык.
6. Ротация/квоты используют существующую BackupPolicy; разрушительную очистку рабочих
   копий автоматически в рамках разработки не запускать. Ошибки безопасные, без путей,
   содержимого памяти и секретов. Подготовить async create callback для координатора;
   callback не стартует Runtime/LLM и не планирует собственное расписание.

## Обязательная узкая приёмка

- Поднять временный host существующим init с синтетическим профилем, получить записи
  через публичные owner-пути, создать копию с WAL, проверить list/verify.
- Изменения после снимка отсутствуют после восстановления в отдельной репетиционной
  области; контрольный сохранившийся факт читается через owner/recall.
- Удаление после снимка не оживает после restore; индекс и сырой текст также проверены.
- Подмена копии/ledger, активный serve, несовместимый host config, смена preview,
  сбой staging/переключения закрыты и не повреждают текущие данные.
- После restore новый serve начинает STOPPED, старые jobs/outbox не исполняются повторно.
- На Linux проверяй реальные файлы/права. Windows ACL/замену открытых файлов не объявляй
  проверенными: передай координатору точную команду одного короткого Windows smoke.
- Один affected pytest-набор после цельной правки, ruff/mypy по правилам проекта.
  Не гоняй полный combined suite и мутационные кампании на каждый коммит.

## Авторизация и сдача

Разрешены код, временные синтетические host, изолированные снимки/репетиции восстановления,
узкие offline/mock проверки, небольшие commits и push своей ветки.
Не использовать рабочую биографию/БД оператора и секреты; не восстанавливать настоящий host,
не запускать платные API, контейнеры или установку зависимостей без отдельной необходимости
и авторизации. Не читать .env. Не сливать в main самостоятельно.

Routine choices внутри зоны решай сам. Недостающий shared interface — точный запрос:
файл/символ, нужная сигнатура/семантика, почему принятый порт недостаточен, минимальная
правка и способ проверки. Продолжай независимую часть, не делай обходную архитектуру.

Сдать: branch/base/SHA, commits pushed, список файлов, реальные результаты проверок,
непроверенное, ограничения Windows, open owner requests. В отчёте отдельно отметить
готовность кода и незакрытые production bindings: тест на fixture не равен готовому recovery.
