# Этап 3 doc33 для Codex: агент учится из разговоров и работает сам

Поручение оператора 2026-10-28. Основа — [doc33](../33-harness-owns-the-turn.md)
(D79–D83). Этап 1 сделан Claude и работает на личном Windows host. Этап 2 (MCP
платформы) делает Claude параллельно. Этап 3 — твой.

## Почему сменили схему (2026-10-28)

Прежняя схема (D67/D73, R1, AW-08) была такой: ход платформы оборачивал цикл OpenCode.
Окно OpenCode → платформа → мост в песочнице. На каждый вызов модели: аренда, допуск,
перепроверка контекста. На медленном Windows host ходы обрывались один за другим:

- 180 с;
- лимит вызовов;
- двойной STOP;
- FAULTED после перезагрузки;
- продление аренды при медленной записи (STALE_CONTEXT — твой отчёт 6796aa3);
- кривой вызов инструмента.

Каждый сбой чинили точечно, а следующий вылезал из того же устройства. Вдобавок через
эту схему не подключить второй мозг на подписке: такой харнес ходит к модели сам.

Решение оператора — doc33, D79–D83:

- **Разговором владеет харнес.** Оператор подключается к `opencode serve` в контейнере напрямую. D73 заменён в части маршрута через платформу.
- **Модель — через шлюз агента.** Он держит ключ, деньги и STOP, но не перепроверяет каждый вызов.
- **Строгие проверки — на границе последствий:** MCP платформы, память, публикации.
- **Платформа учится из сессий харнеса** через его API. Это твой этап 3.

Что это значит для твоих прежних зон:

- **Мост, рабочие сессии, `work_session_*`, тёплая/резидентная песочница** на этом пути выключены. Код не удаляем до приёмки, но и не чиним: сбои старого пути больше не цель.
- **Проверка на Windows** теперь проверка новой схемы. Длинный ход 30+ мин, STOP с первого нажатия, папка с диска, скорость сборки в `projects/`.
- **Отчёты 067a80e / 4ea65c9 / 0329fd3 / 6796aa3** закрыты. Исправления STOP (30 с, позднее подтверждение) и продления аренды остались в ветке и помогают платформе в целом.

## Что уже есть (этапы 1 и 2)

Ветка `claude/harness-stage1`. Она же развёрнута как `claude/personal-diagnostics`.

- **Схема:** START поднимает два контейнера:
  - шлюз агента `aw-hgw-*` (`packages/adapters/src/ai_agent_adapters/sandbox/agent_gateway_proxy.py`);
  - долгоживущий `opencode serve` личности `aw-harness-*` (`agent_gateway.py`).
- **Шлюз агента:**
  - держит ключ, получая его через stdin;
  - подставляет модель;
  - считает расход в `data/usage/harness-YYYY-MM-DD.jsonl` по ставкам `configure-harness`;
  - отказывает после STOP или когда суточный бюджет исчерпан;
  - публикует OpenCode на `127.0.0.1:4096`.
- **Пароль** сервера OpenCode лежит в `data/harness/password`, пользователь `opencode`.
- **Жизненный цикл:** `apps/core/src/ai_agent_core/m3_composition/harness_host.py`. Ход платформы не оборачивается. STOP или смена эпохи закрывают оба контейнера, и прогон ждёт подтверждения их удаления.
- **Пока харнес включён**, старые `autonomous_activity` и тёплая песочница выключены (`Runtime.tick`).
- **Папки:** `/workspace` = `<files-dir>/<persona id>` на диске хоста, `/persist` — том личности (кэши, инструменты, сессии OpenCode).
- **Описание агента** (профиль, память по теме, порядок папок) собирается один раз при START (`local_host/harness.py`, `prompt()`).
- **Этап 2 (MCP платформы):** сервер MCP `platform` — это `/mcp` шлюза агента. Сообщения JSON-RPC идут хосту через stdin/stdout шлюза (`m3_composition/harness_mcp.py`). Инструменты: `persona_brief`, `memory_recall`, `ticket_raise`, `tickets`. Состояние прогона и эпоха проверяются на каждом вызове.
- **Как проверял я:**
  - `tests/harness/test_agent_gateway.py` — секунды;
  - smoke на настоящем Docker: поддельный провайдер в контейнере, ответ через OpenCode;
  - живой Windows: разговор идёт, 1,72 ₽ за первые 11 вызовов.

## Задача

1. **Сбор сессий в память (D82).** Платформа забирает новые сообщения сессий харнеса и пропускает их через обычный путь памяти и опыта. Это Source с правами, извлечение, опыт через существующие владельцы. Харнес ничего не пишет в БД платформы сам.
   - Читать только через `HarnessHost.opencode(method, path, body)`: GET `/session`, GET `/session/{id}/message`.
   - Запоминать, до какого сообщения обработано, чтобы ничего не задвоить.
   - Сообщения инструментов и файлов — данные, не права.
2. **Пометка сессий при удалении (doc33 §6).** Если оператор удалил источник, который попал в открытую сессию, сессию нужно пометить в панели и предложить начать новую.
3. **Автономность (D74/D77).** Планировщик платформы отправляет сообщение в сессию харнеса (POST `/session/{id}/message`) по будильнику, в пределах денег, тихих часов и START/STOP. После restart или restore сам ничего не запускает.
4. **Обновление описания.** Описание при START сейчас статично. Нужно освежать память по теме для новой сессии. Как это делать через MCP (`persona_brief`), согласуем с Claude.

## Правила оператора на эту работу

- Быстрые проверки: целевые тесты на секунды. Без 20-минутных гейтов, пока схема не принята.
- Ключи и личные данные не попадают в Git, журналы и отчёты. Сообщения сессий — личные данные.
- Перед любым изменением на ПК оператора: STOP от оператора и его «обновляй».
- STOP независим от LLM. Restart не запускает агента.

## Приёмка на Windows

- Новое из разговора в OpenCode появляется в памяти платформы, и его видно на экране «Память».
- Повторный сбор ничего не задваивает.
- Без оператора агент продолжает по будильнику в пределах бюджета, после STOP не продолжает.

## Стык с Claude (подтверждён 2026-10-28)

- **Части харнеса.** `HarnessHost.attach(part)`, `part: HarnessPart`:
  - `tick()` — синхронный и неблокирующий, вызывается раз в ~0,5 с только при `host.current()` (готов, ACTIVE, та же эпоха);
  - `close()` ждут (до 10 с) перед удалением контейнеров при STOP, смене эпохи или сбое;
  - после нового START та же часть снова получает `tick`.

  Фоновой работы мимо `tick` нет. Перед каждым эффектом проверяй `host.current()`. API OpenCode: `await host.opencode(method, path, body)`.
- **Подключение.** В `local_host/harness.py` после создания `runtime.harness`: `runtime.harness.attach(<твой модуль>(runtime))`. Это одна строка на модуль, её добавляешь сам.
- **Память (D82):** `m3_composition/harness_memory.py`.
  - Source сообщений харнеса — `source_type` из `SOURCE_TYPES` (`harness-operator-message`, `harness-agent-message`). Записывается через владельца памяти.
  - Episode — `operation_id` начинается с `OPERATION` (`"harness-"`).
  - `memory_cycles.pairs()` для такого эпизода проверяет его источники напрямую: текущая версия, есть content, права api_transfer, тип из `SOURCE_TYPES`. Фиктивных Job не нужно.
- **Панель пометок удалённого:** окно проекции беру я. Опиши мне, какие поля сессии ты отдаёшь (id сессии, затронутые источники), и я добавлю проекцию и экран.
