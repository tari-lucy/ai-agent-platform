# Задание: очистка производных лабораторных файлов

## Зачем и от какой базы

Закрыть запрос №3 из Integration-local-backup: после удаления и restore вне БД
не должны оставаться доступные копии удалённого текста в lab-индексах/reports.
Это важный privacy/recovery gate; существующая проверка на fixture его не закрывает.

Fetch origin, проверь root/branch/status и текущий origin/main. Создай отдельный
checkout и ветку `codex/derived-artifacts-purger` от проверенного origin/main;
зафиксируй фактический base SHA. Не используй незавершённую backup-ветку как
принятую зависимость. Задача опирается на уже принятые DerivedPurger/RetentionService,
RecallIndex и Reports; runtime-подключение сделает координатор.

Прочитай AGENTS, README, docs 25/07/27 и относящиеся 03/14/17–20/23,
M5-01/M5-02, Integration-local-backup и docs/local-backup-setup (если уже в main).

## Твоя файловая зона

- Новый `apps/core/src/ai_agent_core/local_artifacts/**`.
- `tests/local_artifacts/**`.
- `docs/implementation-reports/Integration-derived-artifacts.md`.

Не менять local_host/**, m3_composition/** (включая artifacts.py), contracts,
retention/storage/jobs, зависимости, миграции, Compose, UI и общий реестр задач.
Backup-ветку a253c7e сохранить отдельно для review; не смешивать новую задачу с ней.
Координатор продолжает автономную память, host retention/ledger, расписание и jobs.

## Что реализовать

1. Тонкий adapter существующего порта
   `DerivedPurger.purge_sources(scope, source_ids)` и публичную фабрику для
   подключения к RetentionService. Не создавать второй реестр удалений.
2. Использовать существующие публичные RecallIndex.remove_source/compact,
   а для файлов отчётов — Reports.purge. Не дублировать приватный _path и
   не вычислять отношения между источниками по содержимому/имени файла.
3. Инвентарь открытых индексов/закрытие handle получает от владельца через
   явно описанные аргументы/callback. Не открывать второй runtime и не удалять
   открытый SQLite-файл, рассчитывая только на поведение Linux.
4. Отдельная offline-операция подготовки/проверки очистки производных каталогов
   при restore. Состав и потеря доступности старых отчётов должны быть явными.
   Никаких LLM-вызовов для их восстановления. Интеграцию в switch/host делает
   координатор после принятия интерфейса.
5. Проверь, достаточно ли provenance отчётов связывает их со всеми источниками
   в теле. Удаление только файла по исходному source_id не доказывает очистку
   зависимого report. Если надёжного inventory/owner-порта нет, покажи конкретный
   пробел и минимальную сигнатуру; не создавай фиктивное соответствие и не
   объявляй такую очистку успешной.
6. Ошибка очистки должна распространяться владельцу: источник остаётся
   blocked_pending_purge; повтор безопасен и идемпотентен. Не глотать ошибки
   и не выдавать purged, если marker ещё читается в производных файлах.

Индексы/отчёты считаются производными. Авторитетные Source/Episode/Claim,
профили, usage, секреты, ledger, backup/replaced каталоги не удалять.
Любые файловые операции ограничить проверенными абсолютными целевыми корнями;
symlink/junction/path traversal наружу закрывать. Массовая очистка рабочих
каталогов не разрешена: реализация и проверки только во временном fixture.

## Узкая приёмка

На настоящих временных SQLite/индексах и реальном синтетическом report,
созданных принятыми API владельцев:

- marker есть в источнике, индексе и теле производного отчёта до удаления;
- после ledger→purge marker не читается через recall/download и отсутствует
  в проверяемых файлах, включая относящиеся WAL/SHM; marker не печатать;
- другая память/область и соседние файлы сохранены; либо широкая offline
  инвалидизация явно отражена в preview и выполняется только по его решению;
- повтор, отсутствующие файлы, закрытый/занятый индекс и отказ файловой операции:
  результат честный, без ложного purged; retry завершает незавершённую очистку;
- restore-подготовка не возвращает старые производные файлы и не меняет живую БД;
- выход из корня через symlink/path закрыт, секреты и соседние каталоги целы.

Один affected pytest-набор после цельной правки, ruff/mypy. Полный suite,
мутационные кампании, платный API, контейнеры и установки не нужны.
Windows не объявляй проверенной: дай координатору один точный короткий smoke.

## Самостоятельность и сдача

Обычные решения внутри своей зоны принимай самостоятельно. Сначала кратко
опиши обнаруженные форматы/владельцев и public factory/callback, затем реализуй.
Не жди отдельного согласования имён локальных helper. Shared blocker — точный
файл/символ/сигнатура, семантика отказа и тест; независимую часть продолжай.

Небольшие commits, push своей ветки, без merge в main. Сдать base/HEAD,
список файлов, фактические проверки, ограничения и точное подключение для
координатора. Production gate не закрывать по одному fixture или заглушке.
