# Большой блок: происхождение и выборочное удаление лабораторных отчётов

## Результат для запуска

Закрыть цепочку «источник → опыт лаборатории → ScenarioReport → файл Reports →
удаление/TTL/отзыв передачи». Новый отчёт не должен отдавать удалённый исходный
текст, а purge должен удалять связанные тела, сохраняя посторонние отчёты.
Старый отчёт без доказанной связи нельзя считать безопасным по умолчанию.
Это продолжение важных открытых пунктов из Integration-derived-artifacts.

## Что нужно сделать

1. Полный и детерминированный provenance всех источников, чей текст попадает
   в отчёт: регистрация источников/эпизодов, лог, ScenarioReport, его digest
   и сохранённое тело. IDs/версии/область берутся из owner результатов, не
   сочиняются моделью и не извлекаются из текста. Учти error/partial report.
2. Публичные безопасные Reports.holds и API выборочной очистки
   (purge_for_source или эквивалентный небольшой порт). Не дублируй приватный
   _path в других пакетах. Связи должны переживать restart и purge основного
   источника; checksum/digest и отказ на подмену обязательны.
3. Чтение/download нового отчёта закрывается при удалении, TTL или отзыве
   api_transfer любого текстового основания. Проверяй источник до и после
   файлового IO. Не расширяй права, чтобы чтение снова стало успешным.
4. Селективный DerivedPurger: только зависимые отчёты, идемпотентный повтор,
   честный blocked_pending_purge при оставшемся теле или ошибке. Пока зависимый
   пакет не интегрирован, можно полностью проверить это через RetentionService
   и принятый DerivedPurger protocol, не создавая альтернативной реализации.
5. Обратная совместимость: старый report без lineage не равен «нет источников».
   Сохрани явную preview/decision-инвалидацию как безопасный fallback; не
   реконструируй недоказанную связь из свободного текста. Не переписывай старые
   пользовательские файлы автоматически и не делай массовое удаление.
6. Если metadata хранится в sidecar, это часть жизненного цикла тела:
   атомарность/порядок сохранения, права, checksum, границы каталога, уборка
   неполной записи, отсутствие возрождения после restore. Сам по себе sidecar
   не считается доверенным при подмене. Выбор минимального способа за тобой.

## Приёмка на синтетических данных

Используй настоящие LabRunner, Reports, MemoryService, RetentionService и
независимый ledger во временном host. Без платных API, рабочего host и .env.

- Два отчёта одной области и отчёт другой области; удаление исходника первого
  удаляет только его зависимые тела. Чужие отчёты/секреты/соседние файлы целы.
- Исходный marker до удаления реально есть в report bytes. После ledger→purge
  он недоступен через download и отсутствует в относящихся файлах; не печатай его.
- TTL/отзыв передачи и отзыв во время IO закрывают download, включая restart.
- Частичный/error report тоже сохраняет полный provenance, если в нём есть текст.
- Старый report без lineage остаётся непроверенным и требует явного fallback.
- Подмена lineage/digest, потерянный sidecar, сбой записи/удаления и занятый файл:
  нет ложного purged, повтор завершает незавершённую операцию без дублей.
- Реплей сценария детерминирован; скачивание и проверка digest совместимы с новым
  форматом. Не только mock FileHolds: реальные публичные Reports API в проверках.
- Symlink/junction/path traversal наружу закрыты; Linux и Windows не путать.

Один affected pytest-набор после цельной реализации, ruff/mypy и точечный
Node/build, если менял клиент. Полный combined suite и мутационные кампании
не нужны. Дай координатору один короткий Windows smoke.

## Самостоятельность и сдача

Сначала кратко опиши выбранный формат и public API, потом реализуй без ожидания
подтверждения обычных деталей. Не ослабляй provenance ради зелёного теста.
При shared blocker дай файл/символ, сигнатуру/семантику, минимальный diff и тест;
остальную работу продолжай. Небольшие commits, push своей ветки, без merge в main.
Отчёт: base/HEAD, файлы, реальные результаты проверок, что ещё закрыто gate,
и точный способ подключения для координатора. Рабочие файлы не очищать.
