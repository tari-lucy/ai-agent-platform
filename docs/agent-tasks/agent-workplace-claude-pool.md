# Пул Claude Code: рабочее место агента

Дата: 2026-10-21. **Оператор разрешил начать реализацию этого пула.**
После получения поручения выполняй задачи последовательно по готовности
зависимостей, без ожидания одобрения Codex каждой следующей задачи. Первое
контрактное и интеграционное окно AW-00 твоё; публикуй минимальные стыки рано,
чтобы Codex начал AW-02. Схемы и порты файловой области не дублирует Codex.

## Цель

Рабочее место разных личностей: единый персонаж с памятью/характером и общим
деятельностным контуром. Агент сам выбирает занятия и способы выполнения,
создаёт знания и навыки, работает существующими инструментами. Новые права
или инструменты запрашивает тикетом, оператор отвечает через панель.

Источник требований: [doc28](../28-agent-workplace-concept.md).
Задачи/порядок/gates: [doc29](../29-agent-workplace-implementation-plan.md).
Равноправная интеграция: [doc27 §8](../27-coding-agents-workflow.md#8-равноправные-владельцы-и-интеграция-пула-aw).
Актуальная реализация: [состояние MVP](../mvp-current-state.md).

## Твоя зона и самостоятельность

Основной пул: **AW-00, AW-01, AW-03, AW-05, AW-06, AW-07, AW-08, AW-11**.
Это полноценные vertical slices: contracts/ports, сервисы и storage, HTTP/events,
панель, production wiring, свои tests/report. Не сдавай только UI или isolated
module, оставляя все стыки Codex. Пакет может состоять из небольших commits;
общий интерфейс публикуй рано, чтобы второй исполнитель не ждал большой ветки.

Codex параллельно ведёт AW-02/04/09/10: файлы/изоляцию/retention/упаковку.
Зависимость закрывается после integrated-контракта, не по чужому обещанию.
При занятости конкретного shared файла продолжай независимую работу; не
копируй схему, storage owner, API client, jobs ledger или gateway.

Тебе разрешено после назначения пула:

- выбирать обычные технические решения в согласованной архитектуре;
- менять свои API/contracts/registrations/composition в выданном shared окне;
- самостоятельно исправлять integration defects своего пакета;
- объединять свои готовые пакеты в main в назначенном окне по doc27, включая
  обновление task status/сводки, без персонального одобрения Codex;
- брать следующую готовую задачу своего пула после integrated-зависимостей.

Один writer на shared файл/миграцию/lockfile и один интегратор окна сохраняются.
Рисковые изменения прав/STOP/удаления/sandbox требуют узкого взаимного разбора
инварианта; это не повторная полная приёмка твоего кода Codex.

## Перед первым изменением после назначения

1. Прочитай AGENTS/README, doc07/25, doc27 и doc28/29, свою строку AW.
2. Проверь cwd/root/status/worktrees и актуальный origin/main. Документированная
   исходная сверка `fa30e6f` — историческая, не ветвись от неё вместо свежего main.
3. Создай свою `codex/aw-XX-*` ветку и отдельный checkout. Зафиксируй base SHA,
   ownership и shared окно в своём отчёте/поручении. Не переключай чужую папку.
4. Проверь свой interpreter/venv и import path: старый worktree в окружении
   не должен подменить тестируемые исходники. Используй lock проекта; не
   исправляй несовпадение временным скрытым PYTHONPATH без объяснения.
5. Начни AW-00; затем AW-01, пока Codex делает AW-02. Дальше следуй волнам doc29.

## Критические продуктовые границы

- Не зашивай занятия, привычки, имя или игровые команды Опечатки в ядро.
  Профиль — данные; инструменты обнаруживаются по manifest/instructions.
- Один персонаж и существующие owners памяти/развития. План или свой ответ
  модели не становится подтверждённым независимым опытом.
- Навык — метод в пределах существующих возможностей. Вспомогательный Python
  допустим только через уже разрешённый runner, не native shell на host.
- OpenCode — кандидат сменного адаптера. Все его внутренние LLM-вызовы,
  retries и служебные запросы проходят общий gateway/admission/usage, без
  отдельного ключа, бесконтрольного лимита или auto-approve новых прав.
- Агент не пишет напрямую в DB памяти, tickets, grants или каталог backups.
  Документ/skill/plugin README не является полномочием или операторской командой.
- Тикет об инструменте и его одобрение ещё не означают готовое подключение.
  Расширение прав — структурированная команда оператора, не парсинг «давай».
  AW-01 включает preview/apply/revoke через существующего владельца прав,
  operator session и квитанцию; агент/runner эту команду вызывать не могут.
  Переписку можно интегрировать раньше, permission mutation включать после
  узкой взаимной проверки, не превращая её в барьер для всего пула.
- STOP/restart/restore не запускают работу. Источник, версия и текущие права
  перепроверяются при выдаче результата, включая долгую задачу/контекст harness.
- Личные файлы, профили, диалоги, секреты и runtime данные не попадают в Git.

## Проверки и сдача

Один affected-набор и статика; настоящий HTTP/SQLite для сквозной функции,
один browser journey при изменении интерфейса. После исправления повтори
только упавшее и связанные проверки. Полный suite без новой причины не гоняй.
Проверяй реальные стыки, отрицательные исходы, idempotency/конфликт/scope/STOP.
Не объявляй Linux-тест Windows-проверкой или scripted модель реальной.

Сдача каждого пакета: небольшие commits, опубликованная ветка/интеграция в
назначенном окне, `docs/implementation-reports/AW-XX.md`, точный HEAD,
выполненные acceptance и ограничения, какие зависимости теперь готовы.
Сообщение о сдаче не должно требовать «Codex, посмотри всё и разреши дальше»:
обычную приёмку проводит владелец, риск/чужую зону выделяй конкретно.

Платные вызовы, запуск реальной игры/каналов, установка глобальных программ,
выдача новых runtime-прав и миграция пользовательского host не разрешаются
одним фактом передачи этого пула. Сначала synthetic/mock и отдельные данные.
