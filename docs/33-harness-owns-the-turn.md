# Харнес ведёт разговор, платформа — сервис вокруг него

Решение оператора 2026-10-28 (D79–D83). Продолжение [doc31](31-agent-workspace-v2.md)
и [doc32](32-money-budget-and-standing-access.md). Реализация — Claude Code, проверка на
Windows — оператор и Codex.

## 1. Почему

Живые ходы на личном Windows host обрывались один за другим по разным причинам:

- потолки 180 с;
- лимит вызовов;
- двойной STOP;
- FAULTED после перезагрузки;
- один временный сбой провайдера;
- STOP за 2 с;
- продление аренды на медленной записи;
- один кривой вызов инструмента.

Общая причина — устройство хода. Платформа оборачивает цикл OpenCode в свой ход. В нём аренда продлевается каждые 5 с, допуск живёт 2 с, а контекст перепроверяется до и после каждого вызова модели. Любая неудача обрывает весь ход. На медленном host эти окна по времени постоянно оказываются впритык.

Та же схема мешает и дальше:

- Каждый вызов модели идёт через мост в платформу, и Web OpenCode через платформу работает медленно.
- Файл нельзя просто положить агенту.
- Харнес на подписке (второй мозг) ходит к модели сам, его через шлюз платформы не провести.

## 2. Решения

| ID | Решение | Следствие |
| --- | --- | --- |
| D79 | Разговором, циклом «модель → инструмент» и интерфейсом владеет харнес (OpenCode, позже другие). Он работает долгоживущим `opencode serve` в постоянном контейнере агента. Оператор подключается к нему напрямую: родной клиент `opencode attach` или Web OpenCode этого сервера | Заменяет D73 в части маршрута окна через платформу и запрета прямого подключения; уточняет D67 (родной OpenCode — основной вход). Сервер слушает только 127.0.0.1 хоста и закрыт паролем |
| D80 | Модель харнес вызывает через шлюз модели платформы, без перепроверки контекста на каждый вызов. Шлюз подставляет ключ, считает деньги (D76), отказывает после STOP и при исчерпании суточного бюджета | Ключа в контейнере агента нет. Мост и ход-обёртка с арендами для этого пути не используются |
| D81 | Строгие проверки (STOP/эпоха, права, источники, модерация) — на границе последствий: MCP-инструменты платформы, выдача памяти, публикации, подключения. Сбой без последствий не обрывает работу | STOP по-прежнему независим от LLM: гасит контейнер, рвёт шлюзы, отзывает эпоху. Поздний вызов инструмента платформы получает отказ |
| D82 | Платформа учится из разговора: забирает сообщения сессий харнеса через его API и обрабатывает обычным путём памяти и опыта. Удаление памяти действует при выдаче | Уже открытая сессия харнеса может держать в истории удалённое. Платформа помечает такие сессии, новая начинается без него (§6) |
| D83 | Второй мозг — отдельный харнес, например на подписке, с тем же MCP платформы | Токен подписки живёт внутри его контейнера. Это отдельное решение оператора при подключении |

Без изменений остаются:

- D70–D72: постоянный volume, контейнер как граница, свобода внутри, egress-шлюз с журналом и лимитом;
- D74: самостоятельная работа;
- D75: модерация публикаций;
- D76–D78: деньги вместо потолков, продолжение, бессрочные права;
- правило STOP и правило «restart не запускает агента».

## 3. Схема

```
[opencode attach / браузер] ─ 127.0.0.1:4096 (пароль) ─┐
                                                        ▼
                                       [шлюз агента: платформа]──▶ провайдер модели
                                         │  ключ, деньги, STOP        (ключ только здесь)
             внутренняя сеть без         │
             маршрута наружу             ▼
[контейнер агента: opencode serve, /workspace, /guide ro] ──▶ [egress-шлюз] ──▶ интернет
                         │
                         └── MCP платформы (этап 2): личность, память, тикеты, публикации
[хост: платформа] ── управление шлюзом агента (127.0.0.1): START/STOP, бюджет, расход
```

- **Шлюз агента** — контейнер платформы, подключённый к двум сетям. Во внутреннюю сеть он отдаёт OpenAI-совместимый endpoint модели. На 127.0.0.1 хоста он публикует порт OpenCode для оператора и порт управления для хоста. Агент не может на него влиять: это отдельный контейнер без volume агента.
- **Конфиг харнеса** (провайдер, агент-личность, права OpenCode, MCP) генерирует платформа и монтирует только для чтения. Агент не может переписать себе правила.
- **Сессии OpenCode** живут на отдельном томе: переживают перезапуск контейнера и входят в резервную копию.
- **Рабочая папка агента** — volume D70. На Windows она лежит в файловой системе WSL/Docker, а не на `C:`, потому что так быстрее. Оператор открывает её в Проводнике и кладёт файлы перетаскиванием в `inbox/`. Если перетащить файл в окно терминала, вставится его путь Windows, и в контейнере такой путь не откроется.

## 4. Бюджет и STOP

- Шлюз агента пишет стоимость каждого вызова по usage провайдера и тарифу (doc32 §3). До вызова он проверяет консервативную оценку против остатка суток. Если остатка не хватает или тариф неизвестен, вызов получает отказ с понятной ошибкой для харнеса.
- STOP на хосте:
  1. запоминает эпоху;
  2. переводит шлюз агента в отказ;
  3. останавливает контейнер агента;
  4. рвёт egress.

  Подтверждение не зависит от LLM и Redis. Restart, сон и restore ничего не запускают без START.
- После START хост поднимает контейнер и шлюз заново, сессии и файлы на месте.

## 5. Что не теряется и что откладывается

| Было в платформе | Где теперь |
| --- | --- |
| Личность в контексте | Промпт агента-личности в конфиге харнеса (этап 1), затем MCP «личность и память» (этап 2) |
| Права на возможности | Права OpenCode внутри контейнера свободны (D72); новые подключения — тикетом через MCP (этап 2), одобрение в панели |
| Публикации с модерацией | Только MCP-инструмент платформы (этап 2); токенов внешних сервисов в контейнере нет |
| Журнал хода | Родная история сессий OpenCode; платформа читает её через API (этап 3) |
| Самостоятельная работа | Планировщик платформы отправляет сообщение в сессию через API харнеса (этап 3) |
| Мост, рабочие сессии, ход-обёртка | Выключаются для этого пути и остаются в коде до приёмки; удаляются отдельной задачей |

## 6. Известные ограничения

- **Удалённое в открытой сессии.** Если оператор удалил факт из памяти, а он уже есть в истории открытой сессии харнеса, модель может видеть его до конца этой сессии. Платформа помечает такие сессии в панели и предлагает начать новую. Удаление из истории OpenCode через его API — отдельная задача.
- **Подписка (D83).** Токен внутри контейнера второго мозга доступен агенту. Риск принимается оператором при подключении.
- **Права OpenCode** (`permission`) — подтверждения, а не изоляция. Граница — контейнер (D70/D72).

## 7. Этапы

| Этап | Содержание | Приёмка |
| --- | --- | --- |
| 1. Можно пользоваться | Шлюз агента (модель с ключом, деньги, STOP, проброс порта OpenCode); долгоживущий контейнер с `opencode serve`, volume, том сессий, конфиг только для чтения с агентом-личностью; команды хоста START/STOP; инструкция `opencode attach` | На Windows: разговор 30+ мин без обрывов; STOP с первого нажатия за секунды; при исчерпании бюджета — отказ модели; файл из `inbox/` агент видит |
| 2. Платформа внутри | MCP платформы: личность и память (проверка при выдаче), тикеты на права, публикации через модератора | Память приходит в ответах; тикет одобряется в панели; публикация без модератора невозможна |
| 3. Учится и работает сам | Сбор сессий в память и опыт; автономный режим через планировщик (D74/D77); пометка сессий при удалении | Новое из разговора появляется в памяти; агент продолжает без оператора в пределах денег и тихих часов |
| 4. Второй мозг | Второй харнес с тем же MCP; выбор в клиенте | Два мозга работают с одной личностью и одной рабочей папкой по очереди |

Первым шагом этапа 1 замеряется, сколько времени сейчас уходит на мост и перепроверки, а сколько на интерфейс OpenCode и Docker на Windows. Тот же замер повторяется после перехода на `attach`.
