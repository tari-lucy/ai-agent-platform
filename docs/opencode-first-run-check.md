# Первый проход в родном OpenCode

Подготовленный сценарий OC-06/07, **не отметка об уже пройденной проверке**.
Выполнить после поставки OC-02/03 и cross-review. Сначала на временных
вымышленных профилях и синтетическом провайдере; перенос на личный host —
после этого по [порядку переключения](opencode-deployment-runbook.md).
Сценарий использует только уже разрешённые операции, новых прав сам не выдаёт.

1. **Открыть `/opencode/` и войти.** Загрузились родные assets, каталог и сессии.
   После нового serve состояние STOPPED, без отправки сообщения модель не вызвана.
   Диагностическая панель и «Обращения» доступны на том же origin по `/`.
2. **Выбрать профиль и сессию.** Видна только история выбранной личности.
   На втором вымышленном профиле не появляются сессии/память первого.
   Просмотр второго профиля сам не меняет активного исполнителя и не делает START.
3. **Написать и запустить явно.** До START сообщение сохранено и ожидает работы.
   После START приходит связный ответ той же личности, без внутреннего JSON
   инструментов. В вымышленной fixture проверить известный ей уникальный факт
   из памяти; провайдерный журнал должен подтвердить контекст, а не только слова
   ответа. Повтор отправки с тем же request_id не создаёт второго сообщения.
4. **Попросить создать заметку.** Например: «Сохрани в projects/launch-check.txt
   строку “Проверка рабочего места”, затем прочитай её и сообщи результат».
   Результат виден через владельца файлов, не через произвольный путь Windows.
   Если операция отсутствует, честный отказ не считать успехом; при разрешённом
   запросе нового инструмента появляется обращение в панели. Ссылка ведёт туда,
   ответ оператора продолжает ту же сессию. Для обычного разрешённого чтения и
   записи отдельное обращение не требуется.
5. **Получить ответ и проверить остановку.** Видимая вкладка подтверждает точную
   финальную редакцию через существующий ACK; после reload ответ в истории один,
   без повторного модельного вызова. STOP останавливает работу, поздний результат
   не применяется. После закрытия и нового serve снова STOPPED; reload/reconnect
   сам не делает START.

Если шаг не проходит, записать шаг и фиксированный код/статус операции, без
личного текста, ключей и provider endpoint. Не повторять отправку новым request_id
при неизвестном исходе и не очищать БД ради повторения. Для диагностики достаточно
owner-состояния и сетевого маршрута; полный suite на каждый сбой не нужен.

Родной клиент не хранит частные сообщения, память, ключи или контекст в browser
persistence. Во время общего прохода Claude проверяет это и отсутствие native
API/прямых запросов к провайдеру. Упаковка manifest сама этого не доказывает.
