# Рабочее место агента v2: постоянный дом, свободные руки, самостоятельная работа

Дата: 2026-10-26. Основание: обсуждение оператора с Claude Code. Оператор
подтвердил постоянную рабочую папку в Docker, свободную работу внутри выданных
границ, долгоживущие разрешения, выход в интернет и самостоятельную работу
агента между разговорами. Решения — D70–D74 в [doc07](07-decisions.md).
Это план; coding-пакеты начинаются отдельным поручением (§9).

Сохраняются: личность, память, STOP, изоляция компьютера оператора, секреты
только у платформы, обращения как способ получить новое.

## 1. Почему меняем

Текущая схема (main `b5b7f10`) контролирует каждую файловую операцию внутри
песочницы, хотя граница безопасности и так проходит по контейнеру:

- каждый ход — новый контейнер с tmpfs, после хода всё стирается;
- файлы входят и выходят через владельца хранилища: версии, checksum, `FileWrite`;
- у агента нет shell: в конфигурации OpenCode `bash` запрещён, `read` только
  `inputs/*`, `edit` только `outputs/*`;
- Python — во втором контейнере через MCP `save_script` → `run_script` по
  `file_id`+`version`, до 8 входов, целиком в памяти (base64);
- сеть `none`, кроме шлюза модели;
- из потока событий OpenCode сохраняются только финальный текст и имена
  инструментов с ошибкой (`agent_harness/worker.py`, `parse_events`).

Следствия: любое новое действие требует новой MCP-операции, контракта, правила
владельца, тестов и Windows-gate. Агент не накапливает инструменты и наработки.
Аудит архивного хода ([отчёт](implementation-reports/Tool-guidance-archive-audit.md))
не смог установить, что реально исполнялось: следа инструментов нет.
Это и есть «подтверждённая избыточная сложность» из D69.

## 2. Принцип

Граница — контейнер и выданные ему подключения, а не каждый файл. Внутри
контейнера агент свободен. Платформа владеет тем, что за границей: личностью,
памятью, правами, сетью, бюджетом, STOP, публикациями от имени персонажа.

## 3. Рабочее место (D70)

Один постоянный Docker volume на персонажа. Платформа зашивает минимум,
остальное — порядок самого агента, описанный в его README.

```
/guide/                  только чтение; слой оператора и платформы
  AGENTS.md              правила, границы, как просить доступ (ведёт оператор)
  connections.md         выданные подключения и лимиты (генерирует платформа)

/workspace/              постоянный volume; хозяин — агент
  README.md              как здесь всё устроено (пишет агент)
  playbook/              приёмы и подходы: «как я решаю такие вопросы»
  skills/<имя>/SKILL.md  повторяемые навыки + их скрипты
  projects/<имя>/        любой проект: канал, Minecraft, монтаж, разбор архива…
  inbox/                 файлы оператора (кладёт платформа)
  share/                 то, что агент отдаёт оператору
  scratch/               временное
```

Жёстко зашиты только `/guide`, `inbox/`, `share/`. Остальное агент может
перестраивать. Новое занятие — новая папка проекта и заметки, без разработки.

**Слои инструкций.** `/guide` — доверенный слой оператора, агент его только
читает. `playbook/` и `skills/` пишет агент (оператор может подкладывать) —
это данные, они не выдают прав.

**Контекст хода.** В начале хода модель получает `/guide/AGENTS.md`,
`/guide/connections.md`, `README.md` агента и список навыков «имя — когда
применять» из заголовков `SKILL.md`. Полные тексты агент читает сам по мере
надобности; объём стартового контекста ограничен и не растёт с числом файлов.

**Навыки (D71).** Навыки переезжают в `skills/` volume. Экран «09 Библиотека»
становится просмотром volume; MCP-операции `find_skills/read_skill/save_skill`
замораживаются, а затем удаляются после переноса существующих навыков.

**Память и рабочие заметки.** Память (переживания, отношения, личное) остаётся
во владельцах платформы со своими правилами приватности и забывания. Workspace —
рабочие знания и материалы. Итог хода попадает в опыт через существующий
`ExperienceRecorder`, а не сырыми файлами. Забывание разговора не трогает
volume: файлы — собственность агента, удаляются его действием или явной
командой оператора.

## 4. Свободные руки и сеть (D72)

**Внутри контейнера свободно:** root внутри контейнера (`apt`, `pip`, `npm`,
сборка утилит), headless-браузер (Chromium + Playwright), собственные настройки
прокси (HTTP/SOCKS, цепочки, свой клиент), долгие фоновые процессы, обучение по
документации с записью приёмов в `playbook/`.

**Граница вокруг контейнера:**

```
[контейнер агента] ── внутренняя docker-сеть без маршрута наружу ──▶ [egress-шлюз] ──▶ интернет
                                                                         │
                                  запрещено: LAN, хост Windows, другие агенты, API платформы
                                  (кроме шлюза модели), адреса метаданных
```

- Весь трафик идёт через egress-шлюз платформы: HTTP(S)-прокси и SOCKS5.
  Как бы агент ни настроил прокси внутри, мимо шлюза маршрута нет.
- Шлюз ведёт журнал (полный URL, метод, объём, время; D75), показывает его
  в панели, держит лимит трафика; STOP разрывает его немедленно. Журнал может
  содержать личное — хранится только локально, в Git и отчёты не попадает.
- Без `--privileged`, без сокета Docker, cap-drop, лимиты CPU/RAM/pids/диска,
  user namespace. Root внутри контейнера не равен root на хосте.
- В контейнере нет секретов платформы. Ключи модели — за шлюзом модели.
- Выход в интернет — одно долгоживущее разрешение до отзыва.

**Образ «руки»:** Python, Node, Chromium/Playwright, ffmpeg, JDK, git, сетевые
утилиты. Pinned base; дальнейшие установки агента живут в его volume
(или слое контейнера) и не меняют общий образ.

**Подключения.** Внешние миры (Telegram-канал, Minecraft, аккаунты, платежи,
LAN-устройства) — отдельные подключения платформы, каждое выдаётся обращением.
Работа и знания по ним живут в `projects/`, выход наружу — через подключение.
Публикация от имени персонажа идёт через подключение платформы с модерацией.

## 5. Права и обращения

Профиль рабочего места заменяет Permission на каждую возможность и область:
базовый набор (рабочее место, shell, интернет через шлюз, бюджет) выдаётся
один раз и действует до отзыва. Обращение — только за новым: подключение,
расширение лимита, доступ к устройству/LAN, настоящая неустранимая проблема.
Подтверждение отдельных шагов внутри профиля не требуется.

## 6. Общение (D73)

Основной вход прежний — родной Web OpenCode (D67). Схема: окно OpenCode →
платформа (личность, память, права, STOP, история) → постоянный контейнер
агента с `opencode serve`. Прямое подключение окна к OpenCode в контейнере
не используется: мимо платформы прошли бы личность, память, STOP и забывание.

Новое для оператора: в окне видны шаги агента (команды, файлы, загрузки) —
родное отображение OpenCode; дерево файлов показывает volume. Панель — настройки,
обращения, журнал трафика, бюджет, STOP. Telegram как канал связи с оператором —
будущее подключение, не замена OpenCode.

**Журнал хода.** Каждый ход сохраняет след инструментов: имя, краткие аргументы,
статус, размер и начало ответа. Журнал виден оператору и служит источником
диагностики. В следующий ход модель получает краткие наблюдения прошлого хода,
а не только собственный прошлый текст.

## 7. Самостоятельная работа (D74)

Сейчас ход начинается только по сообщению оператора или ответу на обращение.
Цель — агент работает между разговорами по своему плану в пределах бюджета.

**Поводы для хода:**
- будильник, поставленный самим агентом (инструмент `wake_me(when, why)`);
  таймеры хранит платформа, не контейнер;
- завершение долгого фонового процесса в контейнере (рендер, сборка, бот);
- событие подключения (комментарий в канале, событие в игре) — позже, по мере
  появления подключений;
- сообщение оператора и ответ на обращение — как сейчас.

**План агента.** Агент сам ведёт `projects/*/README.md` и общий
`/workspace/agenda.md`: чем занят, что дальше, когда проснуться. Это данные,
прав не выдают.

**Границы:**
- дневной бюджет: токены модели, трафик, CPU-часы; исчерпание — сон до сброса
  или обращение за расширением;
- не больше N самостоятельных ходов в час, тихие часы — настраиваются;
- STOP останавливает ходы, фоновые процессы и сеть;
- restart/restore не запускают агента автоматически: самостоятельная работа
  возобновляется после явного START оператора (правило проекта).

**Отчётность.** Самостоятельные ходы идут в отдельный разговор «Самостоятельная
работа» в OpenCode — его дневник со всеми шагами. Важное агент сообщает
оператору сам (сообщением в разговор, позже — через Telegram); за новым
доступом — обращение.

## 8. Решённые и открытые вопросы

Решено оператором 2026-10-26 (D75):

- **Модерация сужена:** модератор обязателен для публикаций от имени персонажа
  через подключения платформы; обычная работа в сети — под журналом и лимитами.
  Правило в AGENTS.md обновлено. Оператор пересмотрит его по опыту.
- **Журнал трафика — полные URL.**
- **Известный риск открытой сети** принят вместе с D72: модель может отправить
  в сеть то, что есть в её контексте, включая личное из памяти. Смягчения —
  журнал, лимиты, отсутствие секретов; полностью исключить нельзя.

- **Исполнители.** Все W-пакеты реализует и интегрирует Claude Code, включая
  зоны harness/sandbox/R1-сессий; Codex проверяет поставки на целевой
  Windows/Docker машине.

Отложено: **внешний прокси/VPN на выходе шлюза** — добавляется позже отдельным
решением; W3 оставляет для него точку настройки, настройки хранит платформа.

## 9. Порядок перехода

Каждый шаг — отдельная небольшая поставка с приёмкой. Старый путь не удаляется,
пока новый не принят на личном хосте.

| Шаг | Содержание | Приёмка |
| --- | --- | --- |
| W0 | Диагностика повторного архивного хода: `helper_runs`, `scripts/`, `helpers/*/diagnostics`; сверка утверждений (порт 56733, `/agent/*`, `unionclef.properties`, версия Minecraft) с содержимым JAR | Отчёт: что исполнялось, что из ответа подтверждено/опровергнуто |
| W1 | Журнал хода: след инструментов OpenCode сохраняется и виден оператору; краткие наблюдения подаются в следующий ход | Ход с инструментами оставляет журнал; повторный вопрос модель видит с фактами |
| W2 | Постоянный volume на персонажа, `/guide` только чтение, `bash` и свободная правка внутри `/workspace` при текущем запуске «контейнер на ход» | Файлы и установленное агентом переживают ход и restart; вне volume записи нет |
| W3 | Egress-шлюз (внутренняя сеть, deny-list, журнал, лимиты, STOP) и образ «руки»; разрешение «интернет» | Агент скачивает пакет и читает страницу; LAN/хост/платформа недоступны; STOP рвёт трафик |
| W4 | `inbox/`/`share/` и дерево файлов OpenCode на volume; навыки в `skills/`, Библиотека — просмотр; заморозка `helper_mcp`, staging и base64-входов | Оператор кладёт файл и видит результат агента без публикации через владельца |
| W5 | Долгоживущий контейнер с `opencode serve`; шаги видны в окне | Разговор идёт через платформу, шаги отображаются, STOP останавливает контейнер |
| W6 | Профиль рабочего места вместо Permission на возможность | Базовые права выдаются одним действием и живут до отзыва |
| W7 | Самостоятельная работа: будильники, фоновые процессы, бюджет, тихие часы, дневник | Агент сам просыпается, работает и отчитывается в пределах бюджета; после restart ждёт START |

W1 не зависит от остальных и нужен сразу. Статус W1: реализован на Linux,
проверка образа и окна на Windows — Codex ([отчёт](implementation-reports/W1-turn-journal.md)).
 W3 обязателен до открытия сети.
W7 опирается на W5 (долгоживущий контейнер) и W6 (бюджет в профиле).
