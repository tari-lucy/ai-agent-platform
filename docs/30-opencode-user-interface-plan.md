## 1. Пользовательский путь

Оператор открывает одно окно **родного Web OpenCode**, выбирает персонажа и
разговор, пишет свободным текстом. Агент сам вспоминает, уточняет, выбирает занятие,
читает материалы, применяет инструменты и создаёт навыки в рамках допуска/бюджета.
Человек не выбирает для каждой реплики между «Диалогом», «Работой» и «Поручить».
Не строим вместо OpenCode ещё один самодельный основной чат.

Начальная настройка — один понятный пакет возможностей: точный состав, области,
срок и бюджет видны до подтверждения. Набор не растёт при регистрации новых tools.
Частные Permissions остаются у существующего владельца; текст сообщения не выдаёт
прав. В пределах допуска нет вопросов на каждое применение навыка/файла/сообщения.
Новое право, инструмент/доработка, существенная проблема, необходимость помощи или
идея — обращение. Повтор одной проблемы дополняет существующее обращение.
Уточнение оператора: полноценные обращения остаются в панели — читать, отвечать,
закрывать, просматривать состав допуска и явно выдавать/отзывать права. В OpenCode
достаточны уведомление и ссылка на точное обращение; дублировать редактор решений
не требуется. Это один тикет у прежнего owner, а не два канала задач.

Панель платформы остаётся пультом наблюдения: память/основания, развитие,
расходы, права, операции, отчёты и аварийный STOP. Старые экраны сохраняются
на переходный период как диагностический/совместимый путь, а не обязательный UX.
STOP виден и в основном окне; закрытие окна не останавливает автономную жизнь.
UI может быть доступен в STOPPED; исполнение и модель ждут явного START.

## 1.1. Панель: настройки и наблюдение, без второго чата

Решение оператора 2026-10-23 уточняет D64; реализация ещё не выполнена.

| Оставить в панели | Убрать из обычного пути после готовности OpenCode |
| --- | --- |
| Обзор: выбранный профиль, активный исполнитель, состояние, занятие и препятствие | «Диалог» и редактор «Разговор о работе» |
| Персонаж, канон, настройки развития | Отдельная форма создания поручения |
| Память, происхождение, исправление/удаление через owners | Выбор «поговорить или поручить» перед каждой репликой |
| Полноценные обращения: ответ, закрытие, отказ, preview/выдача прав | JSON, capability ID и версии в обязательных полях обычного ответа |
| Возможности, границы и сроки прав; расходы/лимиты | Дублирующие управления одним действием в разных контурах |
| Библиотека файлов/навыков для просмотра и контроля | Общение с агентом через формы диагностических экранов |
| Диагностика: задачи, сессии, операции, ошибки, отчёты/лаборатория | Новые самостоятельные истории диалога в панели |
| Явные START/STOP с указанием исполнителя | Автозапуск при просмотре или открытии ссылки |

Технические ID/версии остаются в API и раскрываемых деталях. Диагностический
просмотр старых разговоров допустим без поля отправки. Лаборатория и служебные
настройки не удаляются автоматически: их можно перенести в расширенную область.
Панель не создаёт второй модельный разговор; ответ в обращении остаётся событием
существующего тикета и может штатно пробудить прежнюю рабочую сессию.

**Переход без потери доступа.** Пока native UI не прошёл OC-06/07, существующий
панельный разговор остаётся временным входом с явной пометкой. Сначала готовим
навигацию/разделы, затем переключаем основной вход и убираем формы отправки.
Истории, Source, задания и receipts не удаляем и не переносим копированием.
Скрытие кнопки не заменяет серверные права; owner API и ACK остаются действующими.
При неготовности нового входа старый путь не отключаем. Обычное использование
OpenCode не требует постоянного просмотра диагностики; переход в панель нужен
для осознанного решения по правам, ответов на обращения и управления платформой.

## 2. Несколько личностей: заложить сейчас

- Каталог доступных оператору агентов и список сессий выбранного агента — часть
  основного входа. Названия/характер/интересы/инструменты берутся из данных.
  Опечатка — один профиль; никакого фиксированного адресата в UI или bridge.
- Идентичность обращения: workspace_id + persona_id + memory partition +
  логическая session_id. Отдельно — активный run/epoch и технический OpenCode ID.
  Входящий ID OpenCode не доказывает право видеть/исполнять эту сессию.
- Список строится проекцией существующих Workspace/Profile/Session owners,
  без второго реестра личностей. Недоступные области не перечисляются.
  Выбор переживает reload; нельзя молча подставлять последнего активного агента.
  Каталоги и история постраничные, с конечными настраиваемыми пределами.
- Видимый собеседник, просматриваемая сессия и активный исполнитель различаются
  явно. Просмотр истории не делает START, не меняет активного агента и не
  повторяет старые команды. STOP однозначно называет останавливаемого исполнителя.
- Новое сообщение неактивному агенту сохраняется в его области и честно ждёт
  допуска/активации. Явное переключение исполнения проходит через supervisor,
  отмену прежних допусков и согласованную инициализацию нового runtime.
  Если существующего owner API переключения не хватает, OC-01 публикует gap
  и минимальный контракт; UI не симулирует доступность другого исполнителя.
- В первой поставке сохраняется **один активный runtime-агент**. Одновременная
  автономная работа нескольких агентов — отдельный F7; каталог и просмотр сессий
  любого разрешённого агента не должны зависеть от реализации F7.
- Новый агент получает собственные память, задачи, файлы и связи. Чужая память
  не копируется автоматически; совместные знания требуют явных прав и provenance.
  Добавление профиля не означает развернутый/активный runtime: это видно в каталоге.
- Встроенные Build/Plan и другие режимы OpenCode не являются личностями платформы.
  Их выбор не может подменять профиль, модельное назначение или привилегии агента.

Приёмка с самого начала — **две вымышленные личности** с разными каноном,
памятью и сессиями. Проверять только Опечатку недостаточно.

## 3. Реальная исходная точка

Проверенная база реализации — c966401; документация deployment — 80206d0.
В main 382af58 опубликованы совместимые контракты InitialAccess и команды
workplace.access.preview/execute. Это ещё **не работающий единый допуск**.

Уже есть: владельцы профиля/состояния/памяти/социальных связей/файлов/навыков,
jobs, supervisor, общий gateway, тикеты, SessionBook, выпуск контекста и ACK,
staged restore. OpenCode 1.19.3 проверен как CLI-исполнитель внутри Docker с
owner MCP и синтетическим провайдером, в том числе через браузер панели.

Сейчас worker запускается на один ход, затем контейнер/локальный кэш OpenCode
удаляются. Родной UI и его server API к этим владельцам не подключены.
Истории «Диалога» и «Работы» раздельные; общий профиль не означает одинаковый
контекст каждого запроса. Нельзя объявлять общий разговор готовым по одному
persona prompt или просто загрузить весь архив в OpenCode.

Личный deployment закреплён на c966401 с раздельной выдачей прав. Его настройка
и данные в этом checkpoint не меняются. Начатая серверная реализация InitialAccess
сохранена незакоммиченной в прежнем checkout runtime/development/r1-agent-session;
она не проверена, не установлена и не является принятой зависимостью. Будущий
владелец пакета сначала разбирает/принимает передачу, не копирует её как готовое решение.
Claude вправе реализовать OC-05 самостоятельно от принятых контрактов; доступ
к локальному черновику Codex не является условием начала или зависимостью.

## 4. Интеграционная граница

Дополнение оператора: назначения моделей двух контуров должны быть независимы.
Для рабочего OpenCode желателен доступ через аккаунт ChatGPT, для автономного
персонажа/каналов/памяти — настраиваемые API-модели, как сейчас. Личность, память
и опыт общие; API billing и ограничения аккаунтного транспорта учитываются
раздельно, недоступный usage не равен нулю. Такой вход через аккаунт ещё не
проверен/подключён. OC-04 проверяет совместимость с admission/STOP/budget и
безопасное хранение credentials до включения; raw native auth и обход gateway
не разрешаются. OC-01 не зависит от способа доступа к модели.

Предпочтительный путь: родной Web-клиент → аутентифицированный локальный bridge
→ существующие владельцы платформы и контролируемый OpenCode server/harness.
Конкретная топология утверждается результатом OC-00, не этим рисунком.

```text
Родной Web OpenCode: персонажи → сессия → разговор/материалы
                         ↓ ссылка на обращение → панель: ответ/решение
                  ↓ один проверяемый вход оператора
Bridge: маршруты, ID, события, auth и совместимость протокола
                  ↓
Workspace/Profile + SessionBook + Source/Memory + Jobs/Supervisor
                  ↓ допуск текущего epoch, права и общий бюджет
OpenCode в песочнице ↔ model gateway / owner MCP
                  ↓ проверенный результат / доставка / ACK / опыт
          Существующие owners и диагностическая панель
```

Bridge переводит транспорт, а не становится новым владельцем памяти/сессий/jobs.
Все пути UI к моделям, tools, файлам, терминалу, настройкам провайдера и
OpenCode permissions перечисляются и закрываются по умолчанию. Неподдерживаемое
действие получает честный отказ. `remember/allow` OpenCode не расширяет Permission
платформы; ключ провайдера, основная БД и диски Windows в контейнер не попадают.
Нельзя публиковать весь нативный server API обычным reverse proxy без контроля.

История в родном UI — разрешённая проекция owner history. Native DB, summaries,
compaction, logs и checkpoints — производные данные с lineage, сроком и очисткой.
При отсутствии безопасной выборочной очистки кэш/техническая сессия сбрасываются,
а разрешённая логическая задача сохраняется. Restore/restart остаются STOPPED.
SSE/WS/частичный текст не означают доставку или право исполнить инструмент.

UI, постоянное соединение и автономная жизнь — разные lifecycle: вкладка не
должна удерживать незавершённую модельную аренду, а её закрытие не даёт новый run.
Инструменты обнаруживаются по manifests и областям; содержание занятий не
выбирается if/else по профессии или тексту поручения.

## 6. Зоны и окна, без центральной очереди одобрения

**Codex:** native bridge/контракты, agent_harness и sandbox, Docker/Windows,
local_host launcher/config, deploy/opencode, scripts запуска, OC-00/04/07 tests.
Предлагаемая новая зона bridge: apps/core/src/ai_agent_core/opencode_ui/.
Владельцы существующих WorkSession, Source, Permission и Job сохраняются.

**Claude:** agent_experience/context/release, проекции каталога/сессий и history,
ticket lifecycle, единый initial-access permission package, интеграция родного
клиента/его минимальные патчи и Linux/headless journey. Не трогает Docker runner,
Windows launcher или кодек model/tool broker без отдельного окна.

Для OC-01 writer contracts/api.py, catalogue.py, exporter/generated и wire-стыков
— Codex. После ранней поставки передаётся именованное окно Claude для его
совместимых добавлений; не держать shared-файлы до конца OC-04. Пока окно занято,
ни второй writer, ни второй экспорт не допускаются. Существующее окно Claude
для invalidated_reason после 382af58 свободно и данным планом не отзывается.

Для OC-05 передаются Claude m3_composition/initial_access.py и permission decision
стык, workspace proof storage и tests. Узкие local_host конфигурационные вставки
он публикует отдельно для владельца Codex; service/views/access shared-wiring
включается в раннее окно OC-01 либо передаётся коротким списком файлов.
WIP в старом checkout не развивают одновременно два исполнителя.

Каждый владелец делает вертикальный пакет и сам интегрирует после acceptance,
сверив remote main. Для enforcement/изоляции/выдачи прав нужен узкий перекрёстный
просмотр инварианта вторым агентом до включения на личном host (doc27 §8),
а не обязательное одобрение Codex всей работы Claude. Результат review пишется
в отчёте. Полный suite не повторяется после каждого коммита.

## 7. Критерии сдачи и открытые вопросы

Готовность — один реальный путь в **родном** OpenCode Web, с owners платформы,
двумя вымышленными профилями и проверенным native transport. Mock доказывает
маршрут, не качество модели. Красивый UI поверх независимого OpenCode с отдельной
памятью/ключом не принимается. Приватные/платные пробы, новые установки/образы,
изменение сети и перенос личного host требуют соответствующего допуска.

OC-00 обязан решить: доступны ли локальные UI assets выбранной версии без
обращения к внешнему UI-сервису; какие native routes нужны; возможен ли нужный
bridge с ограниченным патчем; как связать transport с admission/lease; где живёт
server/кэш и как обеспечиваются изоляция/пределы. Браузер не обращается к
provider или незащищённому native server напрямую. Топология приватной связи
контейнера с bridge проверяется на Windows; публичный listener/LAN не вводится.

Протокол добавления/активации нового профиля в каталоге, перенос выбранных старых
разговоров и правила старых view обсуждаются/версионируются отдельно до изменения
данных. История не переписывается, повторные ответы при миграции не создаются.
Кэш, которого нельзя проверить/очистить после revoke/restore, не сохраняется.

## 8. Источники проверки возможностей, не proof версии

Официальные документы проверены 2026-10-23:
[Web](https://opencode.ai/docs/web/) описывает браузерный вход;
[Server](https://opencode.ai/docs/server/) — HTTP API/OpenAPI и события;
[Permissions](https://opencode.ai/docs/permissions/) — собственные allow/ask/deny.
Это основания для проверки OC-00, не доказательство совместимости 1.19.3,
поставки assets offline или соблюдения нашей политики. Документы другой ветки
OpenCode (включая v2) нельзя смешивать с закреплённым binary/API.
