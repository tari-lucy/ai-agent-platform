## 2. Первый полезный результат и границы объёма

Первый сквозной выпуск: агент после явного START выбирает разрешённое файловое
занятие, находит материал, создаёт результат/навык, проверяет его, учитывает
опыт и при препятствии открывает тикет. Оператор отвечает через настоящую
панель, агент продолжает зависимую задачу. STOP/restart и удаление сохраняют
прежние гарантии. Командный runner допускается только после своего gate.

Сначала читаемые файлы и ограниченный поиск, обычные task plans, явные
инструменты и один активный агент. Не добавляем обязательные LightRAG,
распределённую multi-agent систему, второй dashboard, собственный маркетплейс,
автоустановку инструментов или новую тяжёлую framework-платформу.

Новые возможности выключены по умолчанию и не получают grants через обычный
serve. Старый host продолжает прежний диалог; обновление само не включает
самостоятельные файловые занятия. Первые поставки проверяются на synthetic
данных. Допуск к личным данным ждёт соответствующего lifecycle/прав/изоляции
gate; наличие merged-кода или красивой формы не означает разрешение включить
непроверенный режим. Перенос рабочего host выполняется отдельным поручением.

OpenCode — приоритетный кандидат адаптера; не утверждаем выбранной конкретную
версию до короткой проверки AW-00. Запрещён fallback «запустить с полными
правами ради демонстрации». Если STOP/gateway/изоляция несовместимы, исполнитель
фиксирует точное препятствие и минимальный вариант решения; независимые
тикеты/файлы/панель продолжаются. Не строит второй большой harness молча.

## 3. Распределение ответственности

Claude Code (Клод) ведёт большую часть продуктового кода **сквозными пакетами**:
свои contracts → application/storage → HTTP/events → panel → composition →
целевые проверки → интеграция. Codex ведёт файловые гарантии, sandbox,
retention/backup и упаковку. Это роли в этом пуле, не постоянный запрет
Клоду менять shared files и не обязательное одобрение Codex каждой задачи.

Назначенный владелец вправе сам принимать обычные технические решения,
исправлять свой стык, публиковать контракт и объединять свой пакет после
gate [doc27 §8](27-coding-agents-workflow.md#8-равноправные-владельцы-и-интеграция-пула-aw).
После выдачи пула отдельное разрешение на каждую следующую готовую задачу
не требуется. Передача новых runtime-прав пользователем от этого не следует.

## 4. Задачи и критерии приёмки

Пути новых модулей ниже — целевые зоны, создаваемые при реализации.
Существующие общие файлы выдаются по протоколу §5, а не редактируются параллельно.
Все задачи должны работать на синтетических данных и существующих owners.

AW-00 фиксирует только минимальные общие стыки первого пути. Полные схемы всех
будущих экранов заранее не проектируются: совместимые feature-добавления
публикует их сквозной владелец по мере необходимости. Это короткая стартовая
зависимость, а не новый длительный архитектурный этап перед кодом.

### AW-00 / Claude

**Зависимости:** Актуальный main, эта документация.

**Результат и зона:** Малый общий контракт: capability manifest/binding, task/attempt, managed artifact/skill/ticket и порты runner/gateway. Новые модули `packages/contracts/.../agent_workplace*`, application ports; exports/registry по §5. Проверка официального API выбранной версии OpenCode, отмены, отсутствия скрытых LLM-вызовов/установок. Короткий decision note в своём отчёте

**Приёмка:** Контракты подключены к текущим CommandBase/Scope/SourceRef/CAS/idempotency/owner/export; consumers могут работать независимо. Нет второго jobs/permissions ledger; у каждого состояния один назначенный owner. Явно описаны границы harness, недоступные возможности и проверка общего бюджета. Только тестовые transports; версия/транспорт — решение исполнителя, не продуктовая догадка

### AW-01 / Claude

**Зависимости:** AW-00.

**Результат и зона:** Обращения от storage до панели: `application/.../tickets`, свои adapters/HTTP module, `panel/.../Tickets*`, tests/workplace_tickets; actual host wiring. Две малые поставки: переписка, затем structured permission decision через existing owner

**Приёмка:** Создание агентом/службой, список «Нужен мой ответ», ответ оператора, четыре состояния/чей ход, дедуп повторов, unread/reopen и связанные задачи. Настоящий HTTP/SQLite + один browser journey. Повтор команды не дублирует сообщение; чужой scope/авторство и устаревшая версия отклонены. STOPPED позволяет ответить без автозапуска. Текст тикета не выдаёт grants. Отдельные preview/apply/revoke конкретного права от operator session через текущего владельца прав, с CAS/receipt, проверкой максимального допуска и недоступностью agent/runner. Новое подключение остаётся pending до фактической готовности; перед включением permission mutation — узкий разбор риска по doc27

### AW-02 / Codex

**Зависимости:** AW-00.

**Результат и зона:** Managed filesystem/catalogue/knowledge IO: `application/.../workspace_files`, `adapters/.../workspace_files`, tests/workplace_files; переиспользование Artifact/SourceRef

**Приёмка:** Изолированные WORK/TEST/persona roots, чтение/запись/поиск/версии, атомарный commit и квоты; отказ на traversal/link/reparse/path race и чужую область. Agent не открывает DB/secrets/backup. Проверка на обычных файлах, конкурентной версии и превышении квоты; источник и производные связи фиксирует владелец

### AW-03 / Claude

**Зависимости:** AW-00, AW-02.

**Результат и зона:** База знаний и библиотека навыков: `application/.../agent_knowledge`, `.../agent_skills`, adapters/HTTP и свои UI-компоненты, tests/workplace_skills

**Приёмка:** Агент создаёт/находит/читает/улучшает навык с версиями, grounds и экспериментальным/проверенным статусом; документ ≠ гипотеза ≠ метод ≠ опыт. Два разных метода без persona-specific if/else. Текст навыка не расширяет tools/rights; без AW-04 скрипт только файл, не скрытый запуск. FTS/файлового поиска достаточно

### AW-04 / Codex

**Зависимости:** AW-00, AW-02.

**Результат и зона:** Ограниченный task runner и broker вызовов: `adapters/.../sandbox`, `core/.../workplace_runner`, свои runner templates, tests/workplace_sandbox

**Приёмка:** Реальный контейнер получает только task staging; no-root/read-only/ограничения/no Docker socket/secrets/host mounts. Сеть по умолчанию закрыта, gateway не даёт raw network/ключ/произвольный core API. Таймаут/PIDs/output/disk/STOP/watchdog, source revoke и поздний commit проверены. Дисковый предел действует и на записи произвольной команды, не только файлового API. Удалённое/подменённое основание закрывает выдачу результата. Каждый LLM attempt проходит текущий общий admission/usage до отправки, включая retry и внутренние вызовы harness

### AW-05 / Claude

**Зависимости:** AW-00, AW-01, AW-02, AW-03.

**Результат и зона:** Контур деятельности: `application/.../agent_activity`, свои core workplace routes/service и tests/workplace_activity

**Приёмка:** Поручение и собственная цель → план → разрешённый tool call → проверяемый результат/ожидание. Агент выбирает инструменты по manifest; нет списка занятий Опечатки в ядре. Бюджет/резервы/очереди/retries/cooldown задаются конфигурацией. NO_WORK не вызывает модель в цикле. При нехватке возможности тикет, блокируется только зависимая задача. Restart STOPPED, unknown сначала сверяется. Скрипты допускаются только с AW-04

### AW-06 / Claude

**Зависимости:** AW-05 и действующие memory/persona owners.

**Результат и зона:** Связь деятельности с личностью и опытом: отдельный `core/.../workplace_experience`/application port, tests/workplace_experience

**Приёмка:** Контекст содержит разрешённые интересы/обязательства/память; характер влияет на цель и метод. Факт результата с receipts становится основанием эпизода; план/выдумка/собственная интерпретация не выдаются за независимый опыт. Retry/replay не удваивает основания, TEST не попадает в WORK. Нет прямой записи executor в память/характер и обхода bounded development

### AW-07 / Claude

**Зависимости:** AW-01, AW-03, AW-05, AW-06.

**Результат и зона:** Workspace UI: текущая цель/причина/прогресс/ожидания, проекты/файлы/навыки, ссылки на опыт и обращения; общая shell/API по §5

**Приёмка:** Реальные owner reads/commands вместо UI-only/mock projections. Видны выбор, результат, расход, неполнота/unknown и чей следующий ход. Повтор после обрыва с тем же request_id, конфликт версии, reconnect/reload без START. Существующий прямой STOP доступен во всех новых экранах

### AW-08 / Claude

**Зависимости:** AW-00, AW-03, AW-04, AW-05.

**Результат и зона:** Сменный OpenCode execution adapter: `adapters/.../agent_harness`, integration wiring и tests/workplace_harness

**Приёмка:** Реальный выбранный harness внутри sandbox, синтетический LLM transport через общий gateway: выбрать/прочитать skill, выполнить ограниченный helper, сохранить проверенный результат. Нет ambient developer config/plugins/автозагрузок/прямых ключей/обхода лимита. Permission ask преобразуется в ticket, а не auto-approve. Запрет, STOP, отмена и очистка сессии проверены. Одни scripted ответы без запущенного harness не закрывают этот gate

### AW-09 / Codex

**Зависимости:** AW-01, AW-02; для полного покрытия AW-03, AW-06, AW-08.

**Результат и зона:** Lifecycle новых файлов/skills/tickets/контекстов/сессий: существующие retention/ledger/local_backup/local_artifacts ports и tests/workplace_lifecycle

**Приёмка:** Marker из источника попадает в производные; revoke сразу закрывает чтение/выдачу, purge удаляет все копии и индексы, включая runner/harness/session caches. Restore старой копии не оживляет удалённое, версии skills/файлов не обходят ledger. Новые записи/файлы входят в согласованный backup manifest. Нет второго реестра удалений

### AW-10 / Codex

**Зависимости:** AW-04, AW-05, AW-08, AW-09.

**Результат и зона:** Полная production Compose упаковка текущего host + workspace + runner; `deploy/**`, доверенный launcher/конфигурация и tests/workplace_deploy

**Приёмка:** Собирается настоящая панель и рабочий runtime вместо M0 scaffold; явный одноразовый init/upgrade, запуск STOPPED, host API опубликован только на loopback. Runner не управляет Docker; доверенный launcher ограничен проверенными шаблонами. Linux volumes, backups, reload/restore и Windows Docker Desktop проверены на отдельном synthetic stack; native host не мигрируется автоматически

### AW-11 / Claude; Windows пробы Codex

**Зависимости:** AW-01–AW-10 на общем main.

**Результат и зона:** Один короткий общий acceptance journey, setup/runbook и отчёт `AW-11.md`; общий статус обновляет интегратор окна

**Приёмка:** START → самостоятельное занятие → знание/навык/helper → результат/опыт → нехватка возможности/ticket → ответ панели → продолжение → STOP/restart STOPPED. Отдельные узкие пробы revoke/delete/restore/no budget/cross-scope. Отчёт разделяет Linux/Windows/mock/реальную модель; не закрывает старый M5/F gate автоматически

Каждый владелец ведёт `docs/implementation-reports/AW-XX.md`: base/HEAD,
выполненные критерии, команды/исход, ограничения, изменённые порты и следующую
доступную зависимую задачу. Незавершённый gate не маскируется зелёными unit tests.

## 5. Shared zones без постоянного координаторского ожидания

| Shared зона | Порядок и полномочие |
| --- | --- |
| Новые feature contracts/ports/routes/tests | Владелец AW-пакета делает их сам вместе с consumers; нет обязательного запроса Codex |

| Migrations | Автор нуждающегося пакета — владелец своей миграции. Номер/head проверяет от актуального main перед интеграцией; один writer окна, без расходящихся heads. JSON-record reuse проверяется до введения таблиц |
| Manifests/lockfiles | Один назначенный writer конкретного изменения, по умолчанию владелец нуждающегося пакета. Не ждать Codex как постоянного владельца. Только необходимые зависимости/проверка lock |
| Общие panel API/shell | AW-01/03/07 — Claude; узкая регистрация остальных модулей в отдельных согласованных окнах. Один existing API client/login/STOP |
| `m3_composition/service.py`, local_host cli/serve/layout/rights, auth/control registries | Узкое wiring feature владелец вправе менять сам в своём окне. Основная новая логика в отдельном модуле. Не объявлять весь composition вечной исключительной зоной Codex |
| Supervisor/permission enforcement/retention/runner/deploy | Основной writer Codex для AW-02/04/09/10. Изменения другими авторами допустимы после явной передачи файловой зоны, а не через обходной слой |
| Task statuses и docs | Автор пакета обновляет свою строку и отчёт; интегратор окна — факт integrated и актуальную сводку. Новые продуктовые решения требует оператор, обычные технические заметки пишет владелец |

Окно фиксирует задачу, writer, точные shared файлы и base; завершается
публикацией принятого контракта/пакета и передачей зоны. Выдавать следующие
окна можно заранее в brief: отдельного «посмотри и разреши» не нужно.
При пересечении правок остановить только конфликтующий файл, продолжить своё.
Отсутствие сообщения другого исполнителя не считается передачей занятой зоны.

## 6. Параллельные волны и интеграция

1. **Основа:** Claude AW-00. Codex сверяет существующие файловые/lifecycle
   порты и готовит независимые acceptance fixtures, не дублирует новые схемы.
2. **Первый видимый результат:** Claude AW-01, параллельно Codex AW-02.
   Обращения сразу принимаются через настоящий host/panel, не откладываются
   на финальную ручную сборку координатором.
3. **Обучение и исполнение:** Claude AW-03, параллельно Codex AW-04.
4. **Самостоятельность:** Claude AW-05 → AW-06; Codex AW-09 начинает lifecycle
   файлов/обращений, затем добавляет skills/experience/harness по готовности.
5. **Рабочий интерфейс и harness:** Claude AW-07 → AW-08. Codex готовит AW-10,
   финальный gate которого ждёт AW-08 и полного AW-09.
6. **Общий запуск:** Claude AW-11 как интегратор; Codex выполняет узкий
   Windows/Docker gate. Live качество оценивает оператор при использовании;
   платные пробы только по отдельному конкретному разрешению.

Внутри назначенного пула Claude сам берёт следующую готовую задачу после
integrated-зависимостей. Очередь интеграции не закреплена за Codex: оба могут
объединять свои пакеты; одно окно/один интегратор, без force push. Изменение
main другим агентом требует сверить новую базу и затронутые стыки, а не
заново проверять весь проект. Подробный протокол — doc27 §8.

## 7. Экономные проверки

- На задачу — один затронутый набор и статика по изменённым зонам. Для чистой
  документации — diff, ссылки, согласованность; runtime suites не нужны.
- Для vertical slice — один настоящий HTTP/SQLite путь; браузер только если
  изменено поведение панели. Без бесконечных повторов полного suite.
- После исправления повторить упавший и зависимый набор. Перед merge сравнить
  исходники с протестированной ревизией; docs-only commit не обнуляет результат.
- В общей точке AW-11 один combined journey с существующими регрессиями
  dialogue/memory/STOP; не дублировать все предыдущие gates без нового риска.
- STOP/revoke/unknown, выход за каталог, секреты, scope и восстановление
  проверяются реальными отрицательными случаями: их не заменяет линтер.
- На Linux/VPS не объявлять Windows проверенной. Тяжёлый browser/container
  slot локальной машины один; разные hosts используют свои synthetic данные.
- Known baseline failure документируется с воспроизведением на базе; новое
  падение/неустановленный prerequisite не выдаётся за passed.

## 8. Открытые технические решения и условия допуска

AW-00/04/08 выбирают совместимую версию/транспорт harness, способ общего LLM
gateway и защищённой конфигурации. AW-02 задаёт форматы catalog/file IDs и
квоты. AW-01 уточняет ticket transition/API; AW-10 решает конкретную контейнерную
топологию без выдачи runner Docker socket. Их выбор не меняет D53–D60.

Каналы/сервисы уведомлений вне панели, публичные действия, новые реальные
аккаунты, перенос private host и расширение runtime permissions требуют своих
поручений. Оператор разрешил начать coding-пулы; этот план не отправляет
сообщение Клоду автоматически. Поручение для передачи человеком:
[пул Claude](agent-tasks/agent-workplace-claude-pool.md).
