# Минимальные поля и операции API текстового MVP

Дата: 2026-10-13. Статус: согласовано в D46 на основе
[контрактов модулей](17-module-contracts-state.md) и [модели данных](18-data-model.md).
Это описание, не код, OpenAPI-файл или SQL-миграции. HTTP JSON/WebSocket
и семантика приняты; code schemas/маршруты создаются M1-01. Бизнес-семантика
не зависит от конкретной библиотеки, поискового движка и модели LLM.

## 1. Граница API

Панель читает разрешённые проекции и отправляет команды соответствующим
владельцам. Внутренний API служит адаптерам/worker с отдельными полномочиями.
Рабочие сообщения игроков/зрителей — входные данные, не административные команды.
Текст оператора в диалоге тоже не меняет права; управление имеет явные операции.

Предлагается HTTP JSON для чтения/команд и WebSocket для событий/приватных
streaming-порций. Версия внешнего API — отдельная от версии записи/схемы.
API панели публикуется на Windows loopback; внутренние endpoints не доступны
пользователю только потому, что он может открыть панель. WebSocket не заменяет
БД/outbox и не является единственным путём STOP.

Область включает workspace, личность, пространство рабочей/тестовой памяти;
агента, запуск и сессию — когда они относятся к операции. Сервер проверяет
область, владельца, состояние и права, а не доверяет переданным клиентом ID.
Просмотр другого профиля не переключает действующего агента.
Фиксация входного сообщения и запуск ответа — отдельные результаты. В STOPPED
разрешённое сохранение/чтение данных не запускает автономную генерацию;
для ответа нужен действующий допуск запуска и режима. При ошибке сохранения
API не сообщает, что сообщение уже надёжно записано.

## 2. Общие поля, ответы и типы

| Объект | Минимальные поля | Значение |
| --- | --- | --- |
| Запись | `id`, `schema_version`, `scope`, `created_at`, необходимые ссылки | ID не зависит от имени/модели; время UTC, область проверяется владельцем |
| Изменяемая запись | Общие поля, `version`, `updated_at` | Версия используется при конкурентной правке |
| Команда | `request_id`, `type`, `scope`, `target`, `arguments`, `expected_version` при правке | ID логической операции и точный адресат; отдельные команды имеют дополнительные поля |
| Квитанция | `request_id`, `status`, `resource_id`/`operation_id`, `version` при наличии | Принятая команда ещё не означает завершённое действие |
| Ошибка | `code`, безопасное описание, `request_id`, состояние/версия при допустимости, `retryable` | Машинный код и понятное оператору объяснение, без секретных request dumps |
| Список | `items`, ограниченный `limit`, `next_cursor`, сведения о полноте | Пагинация и стабильный порядок в своей области; нет чтения всей памяти одним запросом |
| Событие панели | `event_id`, `type`, `schema_version`, `scope`, ID/версия ресурса, время, причинный/операционный ID | Минимальный сигнал изменения; доступ и обновлённая запись проверяются отдельно |

Обязательность поля задаётся конкретной операцией; отсутствующий/неизвестный
результат отличается от пустого и от нуля. Расширяемые свойства/аргументы
имеют зарегистрированную схему и предел размера. Числа токенов неотрицательные;
денежные ставки/суммы предлагаются десятичными строками с валютой/единицей,
не двоичным float. Таймеры/сроки и версии назначает владелец, не модель LLM.

Повтор той же команды с тем же ID и аргументами возвращает известную операцию.
Тот же ID с другим содержимым — `IDEMPOTENCY_CONFLICT`. Область и тип участвуют
в проверке; чужой ID не открывает чужую квитанцию. Обработка повтора сверяет
актуальный допуск и не превращает отменённое задание в новое исполнение.

Квитанции различают принято/завершено/ожидает/отклонено; подробное состояние
долгой операции соответствует [жизненному циклу](17-module-contracts-state.md).
При timeout клиент сначала читает статус по ID; повтор HTTP-команды не должен
создавать второе смысловое задание. Внешние API по-прежнему могут иметь
неизвестный результат и отдельные реальные оплачиваемые попытки.
Генерация, индексация и другие долгие операции выполняются отдельными
заданиями. Обработчик команды фиксирует задание и возвращает его ID/статус;
он не удерживает управление API до окончания LLM. Клиент читает результат
или получает событие; остановка остаётся доступной независимо от такого ожидания.

| Отношение | `persona_id`, область памяти, `person_id`, версия, аспекты по схеме, основания изменений |
| Тема/обещание | Участники, `topic_id`, ID реплик/источников, состояние ответа/резерва либо содержание обещания, срок/критерий выполнения, результат закрытия |
| Реплика/доставка | `utterance_id`, редакция, содержание, аудитория/каналы, статус проверки; доставка — канал, попытка/статус, время и внешний ID при наличии |
| Линия/возможность | `arc_id`, основания/эпизоды, границы/статус; предложение — применимость, срок, возможности, выбор и фактический исход |
| Изменение | `proposal_id`, адресат-владелец, базовая версия, конкретная правка, доказательства, интерпретация/неопределённость, проверки, решение, новая версия и ожидаемое проявление |
| Задание/попытка | `operation_id`, цель/команда, тип/версия возможности, статус/deadline/условия, поколение; попытка — ID/аренда, время, прогресс, результат |
| Назначение LLM | Роль, подключение, модель/параметры, capabilities и их статус проверки, версия, разрешённый резерв |

| Тариф/расчёт | Подключение+модель, версия, единица, валюта, ставки/особые категории, дата действия; расчёт — тарифная версия, сумма/полнота, происхождение оценки |

Ссылки на удалённые/истёкшие источники показывают статус доступности.
Редакции и `expected_version` не обходят правила удаления старых текстов.
Пароли/ключи/значения endpoint из `.env` отсутствуют в DTO; подключение
возвращает имя, ID, безопасные ссылки-настройки и факт конфигурации/проверки.
Полные prompt и ответы не требуются для дашборда расходов.

## 4. Семейства операций панели

Ниже карта операций, а не окончательный список маршрутов. Базовый префикс
предлагается `/api/v1`; область workspace проверяется для всех ресурсов.
Создание/изменение вызывает владельца; прямого API произвольной записи в таблицу нет.

| Область | Чтение | Команды |
| --- | --- | --- |
| Диалог | Сессия, реплики и статусы доставки, текущая цель, источники доступных ответов | Начать/завершить сессию; отправить текст; добавить/исправить/отменить вводную |
| Персонаж | Профили, принятые версии, текущее состояние, сравнение редакций | Создать новую личность; подготовить/проверить/применить правку профиля; копировать профиль с явной областью |
| Память и люди | Поиск/recall, эпизод/источники, люди/встречи, отношения, темы/обещания | Исправить факт/интерпретацию, снизить уверенность; подготовить/выполнить удаление; экспорт; подтвердить/исправить связь аккаунтов |
| Сюжет и развитие | Линии, возможности, предложения изменений, основания/проверки, версии/проявления | Пауза/интенсивность гейммастера; отмена возможности/пауза линии; решение оператора; исправление интерпретации; подготовка/применение отката |
| Лаборатория | Каталог сценариев, тестовые запуски, события, результаты и отчёты | Создать изолированную тестовую область; подать сценарий/событие; запустить/остановить тест; перенести проверенные настройки по явной операции |
| Рабочее пространство | Активный экземпляр, состояние/здоровье, подключения/права, задания/ошибки/очереди, экспорт/копии | Запуск/пауза/возобновление/STOP; изменить права/привязки; отменить допустимую операцию; подготовить резервирование/восстановление |
| LLM и расходы | Роли/модели, безопасное состояние подключений, попытки/usage, тарифы, агрегаты по валютам | Изменить назначения/параметры; создать тарифную версию; подготовить/выполнить пересчёт; настроить уведомления/допустимые лимиты |

Создание теста и просмотр отчёта не запускают второй активный экземпляр.
Смена рабочей/тестовой сессии соблюдает согласованный лимит один активный агент.
Экспорт/резервирование возвращают локальный артефакт/задание; это не публикация.
Операции будущего голоса/игры/каналов добавляются через возможности и отдельные
привязки, не требуют переноса характера/памяти в код адаптера.

Примеры адресации: чтение `GET /personas/{id}` и `GET /operations/{id}`;
команды `POST /sessions/{id}/messages`, `POST /agents/{id}/stop`,
`POST /changes/{id}/decision`. Пути условные; они не являются готовыми endpoints.

## 5. Чтение, поиск и правки

Чтение возвращает версию и доступные ссылки. Список использует серверный
лимит/курсор, фильтры по области/времени/типу; курсор не выдаёт дополнительных
прав. Порядок задаётся сервером для списка, а не считается общим порядком
всех событий системы. Проекция панели указывает отставание/неполноту при наличии.

Recall получает запрос, предел результатов/контекста, проверенную область
и цель использования. Возвращает фрагменты, ID/версии источников, атрибуцию,
конфликты и полноту/состояние индекса. Перед включением в контекст владелец
заново проверяет доступность/права источников; старый индекс не оживляет
удалённый текст. Имя движка/его score не превращается в гарантию истинности.

Правка указывает `expected_version`, вид исправления и основание.
`VERSION_CONFLICT` возвращает текущую допустимую версию и требует явного
пересмотра; автоматическое затирание новой правки исключается. Применение
изменения/одобрения проверяет актуальную редакцию, источники, правила и допуск.

Удаление/откат/восстановление/пересчёт сначала показывают план последствий
и область; исполнение связывается с его ID/версией/сроком. Изменение области
или зависимостей требует обновить план. Кнопка решения по развитию не
является разрешением публичной публикации или расширением прав персонажа.

Отмена задания возвращает фактический статус. Завершённое воздействие не
выдаётся за отменённое; OUTCOME_UNKNOWN требует сверки. Применённое изменение
откатывается отдельной операцией с историей. Сроки/критичность уточняются по стеку.

## 6. Поток событий и streaming

Подписка авторизуется по операторской сессии и разрешённым областям. Предлагаемые
события: изменение запуска/задачи, реплики/доставки, памяти/отношения, линии/
развития, проверок, состояния подключения и usage. Payload по умолчанию
минимален: ID/версия/статус; приватный текст передаётся только разрешённому
потребителю в нужной области. Переключение вкладки не расширяет подписку молча.

Streaming-порция содержит ID логической генерации/реплики, ID попытки,
порядковый номер, тип, данные и признак предварительности. Терминальное
событие описывает завершение/отказ/отмену/неполноту и ID сохранённого результата.
Повтор порции не удваивает текст; финальный usage не прибавляется к локальной
оценке второй раз. Новый резервный вызов имеет отдельную попытку и расход.

При обрыве панели состояние читается из владельцев и итоговых результатов.
Повтор подписки не повторяет команду генерации. Оперативные порции могут
быть утрачены; интерфейс показывает неполноту и получает доступный итог,
а не запускает LLM заново для восстановления картинки. Разрешённый replay
ограничен окном/областью; при пробеле требуется новая проекция.

Старые события после смены сессии/запуска проверяются по ID/версии. Это не
один глобальный атомарный snapshot: ресурсы имеют собственные версии.
Частичный текст/JSON не исполняет инструмент; публичный шлюз ждёт проверки
точной редакции. Поздний usage после STOP допустим для учёта, поздняя реплика
не возобновляет действие.

## 7. STOP и внутренние исполнители

STOP адресуется выбранному агенту в проверенной области. Он не требует
старой версии профиля и не ждёт брокер/LLM. Supervisor отзывает допуск,
меняет поколение, вызывает прямую отмену и возвращает действующее состояние:
например, STOPPING и ещё не подтверждённые ресурсы. STOPPED показывается
по согласованным квитанциям/арендам, а не только по успешному HTTP-ответу.

При отказе БД/Redis остаётся прямой канал управления и локальный watchdog.
Детали аутентификации/квитанций этого канала выбираются при реализации;
блокировка обычных команд не означает отключение локальной остановки.
Возобновление — новая явная команда с проверкой текущего контекста/прав.
Команды паузы гейммастера, отключения голоса и управления эфиром отдельны.

Worker/адаптер имеет собственную служебную идентичность и ограниченные операции:
получить/захватить допущенное задание, продлить аренду, передать прогресс,
сдать результат или подтвердить отмену. Нужны ID задания/попытки, токен/номер
аренды, область и поколение; владелец проверяет их перед коммитом. Исполнитель
не выдаёт права самому себе и не пишет напрямую в БД чужих владельцев.

Истечение аренды Redis само по себе не доказывает смерть worker. Повтор,
outbox и восстановление следуют [плану очередей](15-docker-queues.md).
Финансовые квитанции и сведения об уже случившейся доставке обрабатываются
отдельно от допуска нового воздействия.

## 8. Доступ и диагностика

Операторский доступ проверяется для чтения, команд и подписок; управляющие
запросы защищаются от чужого сайта, проверяются Origin/сессия и разрешённый
адрес. Способ входа/защиты определён в [doc23](23-project-delivery-operations.md). Localhost не
считается основанием доверять любой странице/процессу или служебной операции.
Роли worker/адаптера не наследуют все полномочия оператора.

Коды для понятной панели: `ACCESS_DENIED`, `VERSION_CONFLICT`,
`IDEMPOTENCY_CONFLICT`, `STALE_CONTEXT`, `EXPIRED`, `INVALID_ARGUMENTS`,
`CAPABILITY_UNAVAILABLE`, `MODERATION_UNAVAILABLE`, `RESOURCE_BUSY`,
`SERVICE_UNAVAILABLE`, `OUTCOME_UNKNOWN`. У ошибки есть действие оператора
или конечный повтор по политике; она не создаёт бесконечный цикл запросов.

Ограничиваются тело запроса, выдача поиска, подписки/буферы и число заданий.
Диагностика связывается с trace/request ID; возвращает безопасные метаданные,
не `.env`, заголовки авторизации, полные prompt или сырые ошибки провайдера.
Реальный тестовый API-вызов виден в общем расходе, исходные тестовые эпизоды
остаются в тестовой памяти. Эти ограничения — часть уже согласованных прав/
данных, не отдельная публикация или новое внешнее действие.

## 9. Критерии проверки при реализации

Проверить: повтор команды после потерянного ответа; ID с другими аргументами;
устаревшую правку/план удаления/одобрение; обращение к чужой области; попытку
превратить чат в административную команду; обрыв streaming и повтор подписки;
поздний результат после STOP; отказ БД/брокера при остановке; недоступного
модератора; отсутствие usage/тарифа; повторы финансовых квитанций; отсутствие
секретов в ответах/ошибках; ограничения размера/нагрузки. Проверки ещё не выполнялись.

Stack/recall — [doc20](20-stack-recall-selection.md), задачи —

### Laboratory Job control и наблюдения — 2026-10-15

GET /api/v1/laboratory-runs — bounded paginated LaboratoryRuns, обычные scope
query fields родительского runtime, limit 1..200/cursor. Каждый item содержит
actual Job operation_id/version/status/full run scope и pinned lab_scope,
scenario ID/version. ready/virtual_time/accepted_events доступны только для
живого разрешённого раннера; после закрытия отсутствующие значения — null,
не ноль. Read использует operator Job read+api_transfer grant/ACL; session
должна разрешать также каждую возвращённую TEST область. Это проекция JobOwner,
а не второй сохранённый Job state в LaboratoryReport.

EditCommand laboratory.stop: target=laboratory, schema=laboratory.stop-args,
data={operation_id,lab_scope}, scope=точный parent Job.scope (включая run),
expected_version=Job.version. Контроллер сверяет исходный TaskInput и TEST
partition, JobOwner — current operator/Job CAS. SQL ACL повторно проверяется
при входе в Jobs UoW, до синхронного retire только выбранного admission.
QUEUED/WAITING отменяется; RUNNING становится OUTCOME_UNKNOWN, пока настоящий
executor не сдаст factual result. Async cancellation не выдаётся за квитанцию.
Late owner writes закрыты прежними admission/epoch fences; прямой общий STOP
не зависит от нового HTTP/Jobs пути и не меняет своих гарантий.

EditCommand laboratory.event: schema=laboratory.event-args, те же IDs/scope/CAS
и text 1..2000. Принимается только готовым активным раннером, до 32 событий
на job. Наблюдение регистрируется существующим MEMORY owner в точной TEST
partition, provenance=simulation, api_transfer/public_disclosure=false.
Пустой/secret-like ввод отклоняется. Это вход наблюдения, а не канон, обещание,
ответ модели или утверждение об уже пережитом событии. LLM не вызывается.
Commit проверяет текущие Job ACL/CAS, Permission/config/admission/lease.

Request fingerprint/receipt принадлежат соответствующему owner (MEMORY для
события, JOBS для отмены). Повтор не создаёт новый Source или отмену другой
попытки. Source содержимое не копируется в report: только ссылки/sequence;
summary operator_events отличает интерактивный запуск от seed-only replay.
Список событий/их время нужен для воспроизводимости интерактивного прогона;
панель не объявляет его воспроизводимым по одному seed.

Панель читает Job state после reload, посылает canonical команды и не повторяет
неизвестный исход автоматически. Host явно выдаёт минимальные Job API ACL;
default остаётся закрытым. [Приёмка](implementation-reports/Integration-laboratory-control.md).


### Ручное управление развитием — 2026-10-15

Все команды проходят прежний authenticated Origin/CSRF boundary. `target` — ID
реального StateChange/Opportunity/StoryArc, `expected_version` — версия этой
записи. GM configure использует `target=gm-runtime`, GmRuntimeState.version и
числовую intensity 0..1, а не версию RunSession или строку low/high.

- `change.decision` + `change.decision-args`: decision accept/reject, обязательная
  reason 1..1000. PERSONA сохраняет operator_reason и operator_decision_id.
- `change.interpretation` + `change.interpretation-args`: interpretation 1..1500,
  reason 1..1000. Допускаются READY/AWAITING_APPROVAL/APPLIED; pending вновь
  требует одобрения. APPLIED сохраняет накопленное состояние/new_version.
  Это новая версия интерпретации, не изменение события или его оснований.
- `opportunity.cancel` + `opportunity.cancel-args` и `arc.pause` + `arc.pause-args`:
  пустой data; идентификатор находится в target. GM сохраняет состояние штатным
  owner методом. Пауза линии и отмена её неразыгранных возможностей атомарны.
- `change.rollback.preview` + `change.rollback-args`, data={}: возвращает
  ConsequencePlan resource ID/version. В нём цепочка компенсаций/число ожидающих
  предложений, последствия и зависимости. Private RollbackProof привязан к
  оператору/изменению/текущим версиям/источникам/правилам; TTL пять минут.
- `change.rollback.execute`: arguments={plan_id,plan_version}, expected_version
  плана, target того же изменения. Создаёт компенсирующие StateChange и новую
  CharacterState; зависимые pending предложения становятся CONFLICT в одной
  PERSONA транзакции. Предыдущие версии, опыт и отправленные реплики сохраняются.

SQL reservation повторно проверяет operator read/api_transfer/ACL, версии,
источники, configuration и control_epoch. Новые permissions/grants эти маршруты
не создают. GM pause синхронно закрывает выдачу до записи; ошибка сохранения не
означает, что пауза автоматически снята.

GET `/api/v1/owner-operations` и `/{id}` — обычные scoped read models с текущими
WORKSPACE read/api_transfer/ACL. OwnerOperation — технический fingerprint,
планируемые result IDs, подтверждённые result IDs и квитанция; это не Job и не
копия состояния PERSONA/GM. Идентичный completed request возвращает точную
квитанцию. После потери ответа существующий owner result сверяется без нового
применения; rollback recovery не зависит от истёкшего preview TTL. При отсутствии
доказанного результата остаётся planned/reconciliation_required и OUTCOME_UNKNOWN;
слепого повтора нет. Другой payload/оператор с тем же request ID конфликтует.

Host init должен явно подготовить нужные owner grants/record ACL; синтетический
fixture не заменяет проверку host wiring. [Приёмка](implementation-reports/Integration-development-controls.md).


### Prepared TEST configuration — 2026-10-15

`init --operator-controls` — явная локальная подготовка нового runtime. Отдельная
TEST settings partition содержит профиль/свежее состояние/GM без рабочей памяти;
пустой лабораторный pool не используется как конфигурация. Обычный init остаётся
узким. Serve не выдаёт grants, не переносит состояние и не включает режим по
одному изменённому флагу config.

Ручные persona.apply, GM intensity/rules и development controls принимают
partition-only scope без вымышленного RunSession. Для неактивной области runtime
проверяет её наличие в подготовленных scopes и authority, отсутствие agent/run/
session, тот же workspace и действующую operator authority над текущим host.
Это только явно перечисленные операции данных. Start/STOP/dialogue/laboratory
control по-прежнему требуют текущего владельца run; inactive mutation не
перенаправляет запрос в WORK. GM pause из TEST запрещена. Изменение TEST profile/
rules не переводит независимый рабочий run в FAULTED. Текущие SQL grants/ACL и
operator session проверяются прежними owners.

Редактор существующего профиля использует `persona.validate-args` с полным
Markdown и POST personas/{id}/validate; apply повторяет тот же документ/digest и
CAS профиля. Definitions/initial values/bounds сохраняются при правке текста.
Сравнение начальных и текущих значений показывает только отличие, его причина
не выдумывается. Создание новых persona scopes/профилей из старой формы — другой
путь; их provisioning и canonical feature wiring этой приёмкой не закрываются.


### Уточнение интеграции повседневного диалога

Коллекции `sources`, `utterances`, `deliveries`, `operations` принимают
`order=desc`: по `(occurred_at, id)` для источников и `(created_at, id)`
для остальных, от новых к старым. `next_cursor` — непрозрачная пара времени
и ID, связанная с ресурсом, partition и фильтром; максимум 512 символов.
Курсор не выдаёт прав: ACL, TTL и разрешение передачи проверяются заново.
Вставка новой записи перед границей не сдвигает следующую страницу.
Обновление ленты начинается заново с первой страницы, чтобы получить новые записи.
Без `order` сохраняется прежний порядок по ID и прежний курсор.

`deliveries?order=desc&utterance_id=<id>` фильтрует до пагинации.
Это позволяет проверять доставку конкретного ответа, не перечитывая всю
историю доставок. Фильтр не выдаёт доступ к записи или чужой области.
Неподдерживаемые порядок, фильтр или несоответствующий курсор дают 400.
