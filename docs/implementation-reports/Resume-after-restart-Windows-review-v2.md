## P1: нестеревшийся маркер переживает последующий STOP

Место: `local_host/resume.py:179–193`, `authorizes()` и `consume()`.

Воспроизведение с настоящим Windows CreateFileW, FILE_SHARE_READ без
FILE_SHARE_DELETE, на временном файле:

1. Первый процесс штатно закрыл ACTIVE/autonomous/WORK и сохранил маркер.
2. На следующей загрузке файл читается, но os.replace запрещён Windows.
   Resume.run корректно пишет «marker could not be consumed: no resume».
3. Оператор делает STOP; супервизор STOPPED, журнал явно flush-нут.
   При закрытии остановленного runtime файл не меняется.
4. Блокировка файла снята. Третья загрузка принимает тот же старый маркер
   и переходит в ACTIVE, несмотря на завершённый STOP.

Тест: `test_unconsumable_marker_cannot_survive_a_later_operator_stop`.
Это не случай потери ещё не сохранённого STOP: flush выполнен.
Отказ consume предотвращает запуск только в текущем процессе, а не повторное
использование разрешения при следующей загрузке. Нужна необратимая проверка
актуальности маркера относительно последнего решения владельца, без возврата
синхронной записи файла на путь STOP.

## P1: ошибка чтения файла отменяет блок восстановления

Место: `local_host/resume.py:61–66`, `Resume.run():183–184`.

`_load()` возвращает один и тот же пустой словарь и при отсутствии файла, и при
PermissionError/ошибке JSON. Пустой словарь разрешает продолжить незавершённый
ACTIVE из журнала, как будто blocked_before никогда не существовал.

Тест `test_unreadable_restore_block_denies_resume`: установлен настоящий
block_resume; для старого запуска authorizes(..., прочитанный блок) == False.
Затем CreateFileW с share=0 запрещает чтение файла. Следующий Supervisor
восстанавливает журнал, а Resume запускает агента: ACTIVE вместо STOPPED.
Это проверка сохранности блока при чтении, не сквозной restore-копии.

Нужно различать отсутствие файла и недоступное/некорректное состояние.
Во втором случае запуск должен закрываться с диагностикой. Повреждённый JSON
также теряет блок через ту же ветку кода, но отдельно не тестировался.

## P1: STOP во время close() оставляет разрешающий маркер

Место: `local_host/resume.py:233–250`.

close() сначала отписывает наблюдателя, затем получает ACTIVE-снимок и передаёт
запись маркера в asyncio.to_thread. Пока поток пишет, супервизор может принять
STOP. Маркер всё равно записывается по старому ACTIVE-снимку. Следующая загрузка
с пустым журналом незавершённых запусков принимает его и делает START.

Тест `test_stop_while_clean_marker_is_written_wins_on_the_next_boot`:
threading.Event удерживает writer; в это время настоящий Supervisor принимает
STOP, flush фиксирует его; после завершения writer новый процесс становится ACTIVE.
Нужен явный порядок закрытия/приёма команд, который не оставляет действующего
маркера после принятого STOP. Простая повторная проверка перед to_thread не
закрывает окно самой записи.

Граница доказательства: это воспроизведение на lifecycle/supervisor уровне.
HTTP-гонка с настоящим uvicorn shutdown не воспроизводилась: uvicorn может
успевать закрыть приём запросов до lifespan teardown. Тем не менее Resume.close
сам не обеспечивает заявленный приоритет STOP, и фоновые изменения состояния
во время записи отдельно не защищены.
