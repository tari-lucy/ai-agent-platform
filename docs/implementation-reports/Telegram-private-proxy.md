# Telegram: закрытый SSH-прокси и подключение канала

Дата: 2026-10-30. Ветка `codex/telegram-private-proxy`, база `af293c3`.
Пакет оператора: Telegram из рабочего места личности, без вмешательства в n8n.

## Выбор транспорта

На выделенном оператором Ubuntu 24.04 VPS доступны OpenSSH и HTTPS Telegram.
Кандидат Tinyproxy в apt: `1.11.1-3ubuntu0.1`. Проверены upstream releases и
Ubuntu CVE-2026-31842: статус noble `Needs evaluation`. Пакет не установлен.
Использован существующий OpenSSH: SOCKS5 на loopback Windows, удалённое разрешение
имени, проверяемый TLS от клиента до Telegram. Нового публичного listener на VPS
нет. IP, пароли, ключи, тексты и личные настройки в отчёт не включены.

## Изменения

- Root-скрипт создаёт отдельного системного пользователя и точечный sshd Match:
  только public key, только local forward к `api.telegram.org:443`, без shell,
  remote forward, Unix-сокетов, agent forwarding, TTY и X11. Сначала проверяет
  синтаксис и неизменность эффективной конфигурации оператора, затем reload SSH.
  Оператор выполнил скрипт в своей root-сессии и подтвердил успешное завершение.
- Отдельный приватный ключ — только Windows-пользователю и SYSTEM; в контейнере,
  VPS, Git, аргументах процесса и журнале ключа нет. На VPS только публичная часть.
- Отдельная задача Windows при входе пользователя, keepalive, повтор соединения.
  Unicode-путь читается явно как UTF-8; stderr SSH не обрывает цикл PowerShell 5.
- SOCKS настроен отдельно для Telegram, из явного локального `.env`; нет влияния
  на модель, глобальный HTTP-клиент, интернет агента или n8n. Прямого fallback нет.
  Добавлена только зависимость socksio 1.0.0 через существующий HTTPCore 1.0.9.
- При утрате подтверждения Telegram возвращается неизвестный исход и запрет
  слепого повтора. Ни транспорт, ни сервис публикации повторно не отправляют пост.
  Токен не попадает в HTTPX URL-логи: используется низкоуровневый HTTPCore.

## Реально проверено

- Реальный SSH: Telegram HTTPS разрешён, сертификат проверен; example.com и
  loopback-адрес VPS запрещены. Listener Windows только `127.0.0.1`.
- Отдельный ключ не даёт выполнить shell-команду. Reverse-forward отклонён;
  его цель в тесте — собственный пустой listener на случайном loopback-порту.
- Принудительный обрыв только собственного SSH-процесса: задача восстановила
  tunnel за 18,1 с, HTTPS Telegram после восстановления снова доступен.
- По настоящему токену через SOCKS: только getMe/getChat/getChatMember. Бот
  авторизован, указанный публичный канал найден, can_post_messages подтверждён.
  Значение токена не выводилось. Публикаций и LLM-вызовов не было.
- Локальный fake SOCKS/Telegram: **23 passed**, включая прежнюю модерацию/STOP,
  remote DNS, отказ, отсутствие URL/токена в debug-логах, запрет прямого fallback
  и повтора, честный неизвестный исход. Ruff чистый.
- Strict mypy затронутых модулей проверяется с явным MYPYPATH проекта. Первый
  запуск без путей application/contracts дал import-not-found и не считается
  проверкой кода; исправлена только команда проверки, конфиг проекта не ослаблен.
  Итог: no issues found in 6 source files.

## Локальное включение

Перед применением read-only проверкой подтверждён STOPPED. Сохранены защищённые
копии `.env`, host.json и launcher. Исходный deployment не переключался и не
перезаписывался: отдельный checkout и Python-окружение из locked offline-кеша,
прежняя собранная панель. Версии остальных библиотек и наличие optional recall
совпадают с прежним окружением; переиндексация и миграции не запускались.

В `.env` добавлен только proxy-параметр, равенство остальных значений проверено
в памяти без их вывода. Сохранён ACL файла. Канал привязан штатной offline-командой,
launcher указывает на новый Python. После перезапуска панель отвечает HTTP 200,
RunSession остаётся STOPPED, канал и proxy подтверждены штатным загрузчиком.
Проверка stdout команды configure-harness сначала выявила quoting PowerShell
для `@channel`; повтор с кавычками прошёл, прочие настройки не менялись.

После настройки n8n и его PostgreSQL, Qdrant, browserless и nginx-proxy по-прежнему
имеют прежний uptime (6 месяцев); слушающие порты VPS остались прежними. Выделенная
задача Windows — Running, автозапуск при входе пользователя, не при выключенном ПК.

Автопроверка отклонила первоначальную пробу reverse-forward к SSH-порту 22:
при ошибке ограничений она могла открыть ненужный доступ. Проба не выполнялась;
её заменила проверка на собственном безвредном тестовом listener.

## Ограничения

Не проверены реальная публикация поста, голосовые, длительный сетевой обрыв,
реальный reboot Windows и суточная стабильность. Перезагрузка VPS, обновление
всей системы и исправление старых watchdog-предупреждений не выполнялись.
Нулевой риск или бесперебойность не заявляются. Секреты и данные n8n не читались;
его службы, контейнеры, сети, firewall и порты не менялись.
