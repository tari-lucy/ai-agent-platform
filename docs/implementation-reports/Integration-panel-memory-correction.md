# M4-04: исправление памяти через владельца

База e649e71; координатор, codex/panel-memory-correction. Закрыт отдельный
стык, полная приёмка M4/M5 этим отчётом не объявляется.

## Результат

- Панель → memory.correct → MemoryService.correct → одна owner transaction.
  Канонический payload memory.correct-args, generated TS/JSON Schema/OpenAPI
  обновлены. Claim/Summary получили необязательную correction; старые записи
  читаются без миграции. Второго владельца/реестра операций нет: стандартная
  квитанция владельца атомарна с новой версией и основанием правки.
- Target ID, expected_version, вид записи и непустое основание обязательны.
  Уверенность Claim можно только снизить; для Summary её нет. Пустая/тождественная
  правка отклоняется. При новом тексте Claim получает interpretation: это явная
  правка оператора, а не исходное наблюдение. Конфликты/источники сохраняются.
- Operator ACL, scope, сессия, текущая версия каждого Source, права передачи и
  TTL проверяются. Запись защищена существующими transaction pins/fence.
  Исправление не продлевает TTL и не меняет источник/Permission/ACL.
  Audit наследует зависимости записи от источников, не копируется в отдельный
  бессрочный журнал; прежние редакции остаются в стандартной истории revisions.
- В первой версии исправлять можно только после STOPPED; ACTIVE/STOPPING
  не допускаются. STOP отзывает ранее начатые задания. Рестарт и команды
  исправления не запускают агента: после правки оператор явно нажимает START.
- Повтор request_id с тем же телом возвращает прежний результат; с другим
  телом — IDEMPOTENCY_CONFLICT. Внутренний ключ изолирован по operator_id.
  Панель сохраняет точную команду в RAM при неизвестном исходе, блокирует
  редактирование, предлагает «Проверить исход» без нового request_id. Обновление
  проекций не сбрасывает эту команду. После конфликта нужен явный пересмотр.
- Следующий private context получает новый текст, дату правки, пометку оператора
  и сниженную уверенность. Основание из audit не отправляется как prompt.

## Проверки

Вымышленные данные, настоящие SQLite/owners/HTTP; платных запросов нет.

- HTTP: Claim и Summary, предыдущая версия, replay, конфликт ключа/версии,
  запрет повышения уверенности, пустого ввода, чужой области, CSRF и отозванного
  основания. ACTIVE отклоняется без изменений; provider calls=0.
- Сбой перед сохранением квитанции откатывает новую версию и audit; повтор
  после устранения сбоя применяет ровно одну правку. Истёкший источник закрыт.
  Проверка выявила необходимость отдельно сверять текущие версии Source,
  одной видимости исторических ссылок недостаточно; проверка добавлена.
- Следующий синтетический ответ проходит настоящий диалоговый маршрут и видит
  исправленный текст/уверенность, не старый Claim и не текст основания правки.
- Реальный Edge + production local host: init/serve, login, исправление,
  потерянный после commit HTTP-ответ, точный повтор, версия 2 после reload;
  ошибок JavaScript нет. Отдельно проверен UI-конфликт версии.
- 17 Node memory tests; контрактный набор прошёл в затронутом прогоне.
  Typecheck/build/ESLint, Ruff и strict mypy (216 source files) чистые;
  generated exports совпадают с генератором. Перед сдачей устранена ошибка
  вывода типа union в pins.read; поведение маршрута не менялось.
  Полный suite и платный quality-прогон не запускались.

Промежуточные падения: START fixture сначала использовал неподдерживаемое
значение autonomy/не текущий scope, затем ожидал 409 вместо штатного 429
для RESOURCE_BUSY. Старый UI-тест выбирал все alert вместо нужного сообщения;
селектор уточнён. TTL fixture приведён к часам storage. Исправлены проверки,
политика этих ошибок не менялась.

Финальная сверка 2026-10-19: Edge/lost-response — 1 passed; отдельный
HTTP/следующий synthetic ответ — 1 passed (11.72 с). Их не следует запускать
в таком порядке в одном pytest-процессе: session sync-фикстура Playwright
удерживает asyncio loop; попытка дала ошибку harness, отдельный прогон прошёл.
Сборка/ESLint и mypy завершены после прежней остановки из-за лимита tools.

## Ограничения и следующий шаг

Нет автоматической переписи остальных claims/summaries или отправленных ответов,
нет отдельного экрана сравнения всех revisions. Источники не редактируются этим
маршрутом; их удаление/экспорт требуют собственного preview/execute стыка.
Поиск остаётся поиском источников; отдельного текстового индекса Claim/Summary
нет, поэтому изменённый текст не оставляет старой копии в таком индексе.
Unknown-команда не переживает закрытие формы/reload — оператор предупреждён
сначала проверить исход; приватный текст не сохраняется в localStorage.

Следующий шаг: memory.delete/export через план последствий и retention owner.
