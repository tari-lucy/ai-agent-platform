# Происхождение и выборочная очистка лабораторных отчётов

Дата: 2026-10-16. Координатор. Ветка codex/laboratory-report-lineage,
начальная база c56b063; во время реализации обновлена до main 325da2c
(принятый веб-диалог). Рабочие данные/секреты не использованы.

## Реализация

- ScenarioReport несёт source_ids и полные SourceRef (область/версия), а также
  область отчёта. None означает отсутствие доказанного provenance, пустой tuple
  — явно объявленный отчёт без исходников. Новое сохранение без provenance закрыто.
- Lab.episode пишет source_id в запись, source() фиксирует первоначальную ссылку;
  перед/после диалога и в конце сценария собирается консервативное множество
  доступных источников свежего TEST-мира. Ранее зафиксированные ссылки не теряются
  после удаления. Неизвестные изменённые источники привязываются к первой версии,
  чтобы новая редакция не легализовала прежний текст. Сбор ограничен 2000 записей.
- Logical replay digest сохраняет семантику сценария и исключает физические
  source_id из лога. Полная ArtifactRef.checksum охватывает байты отчёта,
  включая scope/SourceRef; отдельного sidecar или реестра связей нет.
- Штатные report_access передаются владельцам лаборатории для создаваемых записей;
  storage grants/Permission не расширены. Чтение проверяет реальный principal
  и purpose каждого источника, его версию, доступность и TTL. После предварительного
  проверенного чтения provenance основное файловое IO окружено повторной проверкой.
  Отзыв между проверками закрывает выдачу; после restart запрет сохраняется.
- Reports.purge_for_source удаляет тело, TTL и pending только зависимых отчётов.
  Inventory использует принятые публичные repositories, включая Source,
  зарегистрированный до записи тела (покрывает незавершённое сохранение Artifact).
  Неопознанные файлы и неверная checksum не объявляются чистыми. Чужие тела
  исключаются только после проверки scope/контрольной суммы по их owner reference.
- DerivedArtifactPurger использует новый порт; для старого binding сохраняет
  прежний безопасный отказ. Ошибка удаления/остаток файла оставляет
  blocked_pending_purge; повтор завершается через RetentionService.resume.
- Save публикует тело атомарно после fsync .pending, с повторным fence/source guard.
  holds/purge/sweep/restore inventory учитывают pending. Корень и файлы закрыты
  существующим native restrict_private; ссылки/junction не используются для IO.
- Старые тела не переписываются автоматически. Preview/decision-инвалидация области
  сохранена; неугаданные зависимости не превращаются в пустой список.

## Проверки

Windows, реальные временные initialise, LabRunner, Reports, MemoryService,
RetentionService и независимый ledger. 2 новых сквозных сценария прошли первыми:
удаление одного источника при двух отчётах той же области и отчёте другой области;
подмена lineage → blocked → восстановление файла → resume → purged.
Затем оставшийся affected-набор: 57 passed (120.50 с): revoke/restart, legacy shape,
local_artifacts, laboratory (включая replay), reports/settings. Последняя расширенная
legacy-проверка отдельно: 1 passed (7.22 с): историческое тело с правильной checksum
сохраняет блокировку до явной preview/decision-инвалидации.

Падения в ходе реализации исправлены без расширения прав: lifecycle inventory
изначально был ошибочно использован для Source (этот порт только GM Opportunity);
заменён обычными owner reads и консервативной проверкой неопознанных файлов.
Fixture скачивает от реально разрешённого оператора и отзывает право по полной
scope исходной записи. Отказ фикстуры отзыва не считается доказательством guard.
Ruff/mypy чистые; полный suite и платные вызовы не запускались.
HTTP download-набор: 15 passed (42.14 с). Отдельно inventory не считает
ошибку stat доказательством отсутствия тела; этот отрицательный случай проверен
адресно, без повторения прошедшего набора.

## Ограничения

Provenance консервативный: доступные источники TEST-мира могут сделать связь шире,
чем один фрагмент лога; это не поиск зависимостей по тексту. Источник без доказанной
первоначальной версии закрывает сохранение/скачивание, не подменяется новой редакцией.
Нестандартный доверенный автор ScenarioReport обязан полно объявить источники;
произвольный текст custom-сценария нельзя автоматически атрибутировать из строки.
Старый/повреждённый неизвестный файл может консервативно блокировать очистку,
включая соседнюю область, пока оператор явно не разберёт/инвалидирует его.

Restore сохраняет прежний offline preview/drop-reports gate: старые производные
тела из backup не восстанавливаются. Выборочная очистка обычного runtime не
равна полной disaster recovery. Безопасное стирание SSD/снимков ОС не заявляется.

Клод владеет GM и диалогом; их файлы этой задачей не меняются. Общие контракты,
миграции, зависимости, права, настройки, память и файлы отчётов рабочего
персонажа не изменялись.

После combined gate рабочий backend обновлён принятой ревизией 293fff4:
STOPPED, maintenance READY, память включена, общий лимит 300. HTTP панель отвечает.
Новых model calls нет; GM остаётся выключенным. Рабочие отчёты не удалялись.
