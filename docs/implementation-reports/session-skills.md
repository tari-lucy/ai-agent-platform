# Навыки в рабочей сессии через MCP

Исполнитель: Claude Code. Ветка `codex/session-skills-mcp`, base main `97df10d`. Поручение
оператора 2026-10-22; зона: `agent_skills/**`, новый `m3_composition/work_session_skills.py`,
тесты и отчёт; узкие окна Codex: подключение в `work_session_workspace.py`, список операций в
`sandbox/model_protocol.py`, описание в `agent_harness/workspace_mcp.py`.

## Результат

- Операции MCP `find_skills(query)`, `read_skill(skill_id)`, `save_skill(skill_id, title,
  applicability, method, limitations?, change_reason?, expected_version?)` — через
  существующие `SkillLibrary` и `ManagedFiles`, тем же bridge, что файлы/заметки/тикеты:
  результат + прочитанные SourceRef/ArtifactRef + записанные файлы; bridge (R1) записывает их
  в WorkAttempt (`extend_inputs`) **до** возврата текста модели и проверяет выдачу до/после.
- Право: область `skills` у текущего automatic Permission на capability попытки
  (`granted_areas`); чтение метода — у владельца файлов (`api_transfer`, версии, TTL, ledger).
  `find_skills` не показывает навык, чей метод или evidence закрыт; показанные методы и
  evidence становятся входами попытки.
- `save_skill`: новый или изменённый метод — **experimental**; операции подтверждения в сессии
  нет: `verified` требует подтверждённых оснований (`SkillLibrary.verify` с evidence), одного
  заявления модели недостаточно. Навык не выдаёт прав, не добавляет инструментов и ничего не
  запускает; `uses_capabilities` из сессии не принимается (описательное поле).
- **CAS и безопасный повтор** (`SkillLibrary.save`, исправление AW-03): ревизия строится от
  закреплённой `expected_version`, поэтому повтор того же запроса (ключ от `call_id`)
  воспроизводится у владельцев файла и навыка; другое изменение на устаревшей версии
  отклоняется **до** записи файла метода (раньше файл успевал продвинуться). STOP/потеря
  допуска закрывают поздние действия (`ex.verify`, владелец файлов).
- Найдено при проверке: `ContractError` наследует `ValueError`; перехват `ValueError` вокруг
  сохранения превращал конфликт версии в INVALID_ARGUMENTS — теперь ошибки владельцев
  пробрасываются как есть.

## Проверки

- `tests/workplace_skills/test_session_skills.py` — production composition (`build`, SQLite,
  ledger, файловый владелец), session driver R1 с синтетическим harness поверх общего gateway,
  операции вызываются внутри настоящих ходов сессии: ход 1 — сохранение (experimental, повтор
  тот же, второе сохранение на старой версии — VERSION_CONFLICT); ход 2 — find → read (метод
  в ответе) → улучшение v2 (CAS), устаревшее — конфликт; прочитанный метод во входах попытки,
  новый — в её результатах; отзыв основания метода (сообщения оператора) → в новом разговоре
  навык не найден и не читается; после STOP старый допуск ничего не сохраняет.
- `test_skills_and_knowledge.py` (+1): повтор того же запроса — та же ревизия без второй
  версии файла; устаревшее изменение отклонено, файл метода остался v2.
- Затронутые наборы и mypy — см. сдачу. Настоящий OpenCode на Windows проверит Codex.

## Ограничения

- Подтверждение навыка (`verified`) из сессии не выставляется; путь с подтверждёнными
  основаниями (результат с receipts) — отдельное решение.
- Helper-скрипты навыка не исполняются (helper execution — Codex).
- Наблюдение для R1: после отзыва основания сообщения оператора разговор остаётся `open`, но
  новых ходов в нём нет и состояние `invalidated` не выставляется — причина не видна.
