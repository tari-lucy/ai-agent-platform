Физическая модель: девять таблиц — scopes/grants, records/revisions,
exact keys, record ACL, source links, outbox и processed operations.
Тела сохраняются как ограниченный валидированный JSON контрактов schema 1.0;
идентичности, версии, права, ключи и зависимости индексируются отдельно.
Миграции — статические снимки 0001 → 0002; новых heads нет, destructive
downgrade не предлагается. Manifests/locks, contracts и Compose не менялись.

## Поведение и ограничения

Новый run продолжает ту же scope partition, но не может подменить содержание
старого request. Истечение квитанции (настраиваемые 30 суток по умолчанию)
возвращает OUTCOME_UNKNOWN без повторного исполнения. Cleanup ledger/outbox
и сроки recovery/redelivery реализуются владельцами M1-04/M5.

SQL чтение старой редакции учитывает текущие source rights/ACL и удаление.
Истёкший сырой текст не возвращается. Точное открытое обещание сохраняет
private state с SourceRef=expired; истечение текста не делает его fulfilled.
Explicit deleted source блокирует зависимое чтение и удаляет старые собственные
payloads из SQL; повторный импорт той же source identity запрещён.
Это **логическое удаление**, не доказательство физического стирания WAL/free pages
или backup. Полная purge/consolidation/index/cache/restore-after-deletion
согласуется и проверяется в M2/M5; чужие owner state здесь не переписываются.

Trusted core composition создаёт Principal/Grant и вызывает administrative
provision/upgrade. Это не HTTP authorization; доверять таким данным из client
JSON нельзя. Auth/CSRF/Origin/capability permissions — M1-05.
STOP/epochs/freshness/lease admission — M1-03/M1-04; Python ports не являются
sandbox против произвольного кода в core. Реальный worker handler/dispatcher
и API/UI wiring ещё отсутствуют.

Не выполнялись: live LLM/Redis jobs, игра/каналы/эфир, рабочая память,
полный runtime migration/upgrade рабочего deployment, restore из backup,
power-loss test накопителя и физическое стирание. Они не нужны для подтверждённых
критериев данной задачи и не объявляются проверенными.

## Следующие задачи и запрос общей правки

Для M1-03 storage interfaces и linear head 0002 приняты после интеграции.
Supervisor должен сначала закрывать допуски и отзывать epoch независимо от
SQLite/Redis/LLM; DB busy/failure не может задерживать direct STOP. Сохранённый
ACTIVE/FAULTED snapshot не даёт autorun и сохраняет active slot до reconciliation.

Конкретная packaging проблема: текущие .dockerignore и deploy/Dockerfile
не включают каталог migrations в core image. Linux acceptance использует
явный readonly bind этих файлов; готовность production image не заявляется.
Минимальное решение координатора перед runtime wiring M1-03: назначить владельца
двух shared files, разрешить migrations/versions в allowlist и COPY каталог
только в core stage, затем проверить собранный image offline. Копия миграций
в другом пакете и скрытый create_all не создавались.

M1-04 использует durable outbox/receipt metadata; dispatch/lease/retry/recovery
проходят отдельную приёмку. Следующий schema change — согласованная ревизия 0003.
