# AW-04 — ограниченный task runner и модельный мост

Дата: 2026-10-21. Исполнитель: Codex. Ветка `codex/aw-04-task-runner`,
base `805a225` (AW-00/01/02 integrated), отдельный checkout/venv.
Статус: первая реализация и physical adapter gate готовы; **полная AW-04
ещё не закрыта**: actual shared-model composition и узкий взаимный разбор
изоляции перед runtime enable остаются ниже. Никаких прав на рабочем host
не включалось, существующие serve/панель/личные данные не менялись.

## Что реализовано

`ai_agent_adapters.sandbox`: DockerTaskRunner реализует принятый TaskRunner,
RunnerTemplate выбирается trusted composition, не моделью. Immutable image ID,
фиксированный executable prefix и верхние пределы ресурсов. Нет shell на host,
автоскачивания image, bind/volume/host mounts, Docker socket, портов или секретов.
Входы owner WorkspaceFiles читает по точным ArtifactRef; только сохранённые
в WorkAttempt входы, тот же capability, scope/freshness/lease. Команда и данные
идут в stdin, не в metadata/CLI args. Generic filenames + manifest в task tmpfs.

- Non-root UID/GID, read-only rootfs, cap-drop ALL, no-new-privileges, private
  PID namespace/default IPC isolation, no network, no image healthcheck/restart.
  Image с VOLUME или неизвестным env name отклоняется. Image должен быть
  доверенным и содержать только публичный runtime; scan имён env не проверяет
  всё содержимое образа и не заменяет provenance/setup.
- Все обычные writable paths находятся в ограниченном /work tmpfs; закрыт
  /dev/shm. Disk/inodes ограничены ядром и для произвольного Python open,
  а не только файлового API. Memory/swap/PIDs/CPU hard ulimit и внешний wall
  watchdog. Логи Docker выключены, stdout и wire bounded; overflow закрывает
  результат. Результаты только обычные одно-ссылочные файлы с логическими именами.
- Child processes и detached descendants завершаются до сбора результата;
  затем контейнер удаляется, tmpfs исчезает. Полученный текст/файл — результат
  команды, а не автоматически подтверждённый опыт или проверенный skill.
- STOP/revoke проверяются до запуска/во время работы/при выдаче. API-transfer
  проверяется дополнительно перед/после каждого модельного запроса. Cleanup
  контейнера идёт до ожидания поздней технической LLM-квитанции.
- Неподтверждённый cleanup даёт unknown, блокирует новую задачу этого runner;
  reconcile только сверяет/удаляет свой container, не повторяет команду.
  Label + UUID защищают от удаления чужих контейнеров. Обязательный lifecycle
  callback регистрирует ресурс в существующем jobs/control, нового ledger нет.
- Bounded output cache только в памяти, одна задача, таймер не более 300 с,
  стандартно 30. staged проверяет тот же допуск/источники. purge/cancel ждут
  подтверждённого завершения, generation fence не даёт позднему результату
  наполнить cache после purge. AW-09 подключит hook в существующий retention.

## Модельный мост

`network=gateway` **не открывает Docker network**. В контейнере небольшой HTTP
loopback facade, а upstream — stdin/stdout RPC к переданному ModelGateway.
Конфигурационный template фиксирует одну роль, prompt/tokens/calls cap;
выбрать другой provider/endpoint/ключ, вызвать core routes или raw HTTP нельзя.
Адрес только task-local в AI_WORKPLACE_MODEL_BASE_URL, auth/secret отсутствуют.
Только /v1/chat/completions, текстовые system/user/assistant и завершённый ответ;
неполный ответ не отдаётся как выполненный. Есть buffered SSE после completion.

Нового gateway/счётчика/credential loader не создавал: в уже опубликованной
подготовке Claude AW-05 есть ExecutionModelGateway → Execution.generate →
существующий LLMGateway/journal/общий бюджет. Его нужно передать в `models=`
после фактической интеграции AW-05, не подменять permissive transport.
Broker сам не повторяет запросы; retry внутри shared gateway тоже обязан
проходить общий admission/usage. Per-task cap дополнительно ограничивает
инструмент, не заменяет суточный лимит.

## Важный открытый стык AW-08

Существующий AW-00 ModelRequest — текстовый ChatMessage; provider-neutral
LLMProvider явно не имеет исполняемых tool-call events. Поэтому tools/tool_choice/
multimodal/произвольные параметры SDK не отбрасываются молча: facade отвечает
TEXT_CHAT_ONLY. Настоящий OpenCode ещё не установлен/запущен. Совместимость
его полного SDK протокола, требуемые параметры и tool-call representation —
узкий gate владельца AW-08, совместимые изменения общего порта в его окне.
Не проксировать raw provider HTTP, не давать ключ и не открывать сеть ради demo.
Широкий второй harness здесь не строится. Существующий file/Python путь работает
без OpenCode; runtime права на него также остаются off до review/lifecycle.

## Проверки

Python 3.14.8, Windows launcher → настоящий Linux engine Docker Desktop,
локальный pinned image; без сети, downloads, платных API и личных данных.

- Affected gate tests/workplace_sandbox — **17 passed** (20.79 с): 11 real
  Docker cases + 6 policy cases. Включает kernel disk ENOSPC, PIDs EAGAIN,
  stdout overflow, timeout, non-root/read-only/no socket/no raw network,
  source/STOP cancellation, actual SQLite → input → result → provenance/revoke,
  модельный callback/отказ/запрет чужого route и purge/late-cache fence.
- Затем добавлены только три отсутствовавшие resource probes: **3 passed**,
  17 deselected (10.29 с): CPU hard limit, memory cgroup/OOM и внешний watchdog
  при намеренно зависшем PID 1. Старые проверки ради добавления не повторял.
- После перестановки cleanup перед technical receipt повторены только связанные
  revocation/watchdog/purge cases: **5 passed, 15 deselected** (13.10 с).
- Ruff и strict mypy новых 5 source modules чисты для Windows/Linux settings.
- Ошибки найдены и исправлены целевыми пробами: daemon stdin-reader удерживал
  buffered lock при Python finalisation — PID 1 теперь flush/exit без финализации
  daemon reader; поздний cache commit после purge закрыт generation fence;
  output-root symlink закрыт отдельно; шаблон должен совпадать с capability
  зарегистрированной попытки, а не только быть известным template.

Тест брокера использует synthetic ModelGateway с отказом, **не** настоящий
суточный usage ledger. Реальные retries/shared reserves требуется подтвердить
одним combined case после AW-05, его suite целиком повторять не нужно. Linux
CLI host отдельно не запускался: проверен Linux task внутри Windows Docker,
это не два разных platform gates. OpenCode/browser/рабочий host не проверены.

## Подключение владельцу activity/harness

Создать trusted RunnerTemplate с approved локальным image ID, executable_prefix,
ceiling и лимитами; совпадение template.id == WorkAttempt.capability_id обязательно.
DockerTaskRunner(..., files=WorkspaceFiles, attempts=AttemptContext,
guard=FileReleaseGuard, authorize=..., lifecycle=..., models=ModelGateway).
Authorize повторно проверяет текущее Permission/binding/manifest version данной
возможности; SQL grants service principal сами по себе этого не доказывают.
WorkAdmission.is_current — supervisor epoch/job lease/cancel, не постоянный True.

Lifecycle(admission, container_name, phase): register **до create** фиксирует
ресурс у существующего JobOwner/Control ResourceTicket; removed — только после
фактической сверки удаления; unknown держит reconciliation gate закрытым.
Callback — технический ресурсный путь, его завершение доступно после STOP.
Runner.cancel — hook контроллера, runner.purge — hook retention. При crash
старый owner journal хранит имя/lease; новый процесс сначала сверяет свои
labelled ресурсы, никакого повторного запуска из restart. Full host launcher/
recovery wiring — AW-05/09/10; изолированный адаптер не включает себя в serve.

stdout_tail и staged не печатать в технические логи: это task content. Сохранение
результата только WorkspaceFiles.write; scope/links берутся из настоящего
WorkAttempt, planned/unknown операция не становится независимым опытом.

## Оставшиеся gates

1. После AW-05: один combined broker → ExecutionModelGateway → общий реальный
   ledger, запрет лишнего вызова/резервов и STOP. Без обходного shared interface.
2. Узкий cross-review именно sandbox/STOP/release invariants другим исполнителем
   (doc27 §8.7); до него не регистрировать доступную runtime capability.
3. AW-09 purge/restore hooks и AW-10 production launcher/reconciliation; AW-08
   настоящий harness/SDK. Их не объявлять выполненными по этим тестам.

Источники механики ограничений:
[Docker run](https://docs.docker.com/engine/containers/run/),
[Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/).
Контейнер — механизм ограничения, не доказательство абсолютной безопасности;
квоты проверены настоящими отказами. Secure erase/pagefile гарантия не заявляется.
