## Причина и исправление

Одна accounting-роль activity обслуживает два разных вызова: планировщик ждёт
StepDecision, а OpenCode — обычный ответ или настоящие tool_calls. PrivateLiveProvider
выбирал протокол только по роли и дописывал требование StepDecision в каждый
OpenCode-запрос. Поэтому модель могла вернуть текстовый JSON use_capability:
OpenCode завершал ход и показывал JSON человеку, но инструмент из текста не вызывался.

ProviderCall теперь получает result_model из доверенного GenerationRequest.
Для activity с закрытой схемой сохранён прежний строгий протокол планировщика;
для рабочего вызова без result_model — текстовый ответ и объявленные tool_calls.
Выбор не зависит от текста сообщения, роль/assignment/journal/budget не меняются.
Фрагменты JSON не исполняются, права через ответ не выдаются. Финальные usage,
завершение провайдера и проверки gateway сохранены.

После успешного сохранения work.session.message сбрасывается только время
следующей проверки очереди. Сообщение не ждёт очередного 30-секундного опроса.
Это не START: foreground priority, STOP, бюджет, cooldown неудачных попыток и
проверки допуска остаются. Отклонённое сообщение очередь не будит.
Старт Docker и собственная задержка модели этим не устраняются.

## Локальное применение

Оператор попросил увеличить рабочую долю: выбран предел 200 вызовов за UTC-сутки
внутри общего 300; резерв памяти сохранён. Предел меняется штатной offline-командой
configure-activity --daily-calls N, а не новой константой в коде.

Перед обновлением выполнен штатный STOP. Применение на личном deployment и
итоговые read-only проверки фиксируются ниже после завершения.
Личные сообщения, идентификаторы host, пароли, ключи и endpoint в отчёт не входят.
