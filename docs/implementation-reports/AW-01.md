## Поставка 1: переписка

- Владелец `TICKETS` (`ai_agent_application/tickets`): одна транзакция владельца на
  ревизию тикета + сообщение; replay по `request_id`, другое содержимое с тем же ID —
  `IDEMPOTENCY_CONFLICT`; CAS по `expected_version`.
- Создание агентом/службой `raise_ticket`: ID тикета детерминирован из (kind, нормализованный
  basis) — повтор того же вопроса дополняет тот же тикет (occurrences, связанные задачи,
  материалы/источники объединяются), закрытый тикет переоткрывается. Ход — оператору.
- `agent_update`: ответ агента или отметка восстановления; `resolve` требует evidence,
  ссылки проверяются storage у владельца источника (выдуманный источник отклоняется).
- `note`: квитанция службы без смены хода (используется решением по праву).
- Оператор: `ticket.reply` (`answer` → в работе, ход агента; `resolve`/`close` → итог) и
  `ticket.read` (unread = `operator_read_version < version`). Автор определяется путём
  вызова, не payload: оператор не может писать от агента и наоборот.
- STOPPED: ответ принимается, run остаётся STOPPED, после restart — STOPPED; ответ ждёт
  агента (`pending_for_agent`), обработка — только после явного START (AW-05).
- HTTP: общие `/api/v1/commands` и generic reads `tickets`, `ticket-messages`; событие
  `ticket.changed`. Тикеты принадлежат стабильному partition (без run/session).
- Права: выключено по умолчанию. Offline `enable-tickets` добавляет только строки TICKETS
  (свои записи + чтение MEMORY для evidence) и чтение TICKETS оператором; `enable-social`
  сохраняет их. Рабочий host не менялся; команду на нём никто не запускал.
- Панель: раздел «Обращения» (08): «Нужен мой ответ» → «В работе» → «Завершённые», метка
  «новое», карточка (зачем/попробовано/нужное решение/задачи/запрос возможности),
  переписка, ответ с одним `request_id` на черновик (повтор после обрыва не дублирует),
  понятный конфликт версии, подсказка про STOPPED. Прямой STOP shell остаётся в шапке.

## Поставка 2: решение по праву (выключено до разбора)

`permission.decision.preview|execute` (`m3_composition/permission_decisions.py`):

- только операторская сессия (cookie + CSRF через `/api/v1/commands`); у worker/runner нет
  маршрута (`/internal/v1/jobs/*` принимает только claim/lease/result; Bearer на panel
  commands → 401/403, проверено);
- grant отвечает на точную версию тикета `capability_request` того же capability;
  потолок host (`workplace_permissions: {capability: {level, max_days}}`), области ⊆
  manifest, `public_output` никогда не `automatic`; revoke разрешён всегда для текущей версии;
- preview пишет `ConsequencePlan` + `PermissionDecisionProof` (WORKSPACE owner) с пинами
  manifest/binding/ticket/permission/policy; execute перепроверяет все пины и потолок,
  пишет `api.Permission` (holder `workplace-agent`, автор — оператор, conditions/limits
  расширения) с CAS, помечает proof исполненным (второй request_id → конфликт, тот же —
  replay), добавляет квитанцию службы в тикет;
- binding не становится `ready`, тикет остаётся открытым до фактической проверки
  подключения; агент не запускается.
- Панель: форма «Решение по праву» в карточке (подключение, уровень, срок, области,
  ограничения) → «Предпросмотр решения» → последствия от владельца → «Подтвердить»;
  текущие права с «Отозвать…».

Включение: только если host-конфигурация содержит `workplace_permissions` (требует
`workplace_tickets` и `operator_controls`). Команды, которая это пишет, нет намеренно.

**Запрос узкого разбора (doc27 §8 п.7), любой второй исполнитель:** инвариант
«агент/runner не может выдать себе право; выдача ≤ потолка; отзыв действует и поздний
результат не применяется». Что посмотреть: `permission_decisions.py` (`check`, `execute`),
`access.py` dispatch, отсутствие маршрута в `surface.service`. Открытый вопрос для AW-05/04:
workplace-исполнение должно пинить `Permission` версии так же, как `Policy.transaction_check`
для m3 (сейчас workplace-исполнителя ещё нет, поэтому отзыв ни на что не влияет).
