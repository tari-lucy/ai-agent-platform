Исполнитель: Claude Code. Ветка `codex/aw-05-activity`, checkout `../aw-05`, base `3ee735e`,
затем влиты integrated AW-03 (`265d0f8`, включая AW-02). Статус: **выполнено** без скриптов:
разрешённые tool calls библиотеки (`workplace.skills`, `workplace.knowledge`) работают;
скрипты/runner подключаются после integrated AW-04 тем же `rt.tool_executors`. Shared-окно (writer Claude): `state.ROLES`,
`schemas.TaskInput`, `service.py` (бюджет, DOMAIN_OWNERS, tick, dispatch), `access.py`,
`local_host/{cli,init,layout,live_budget,provider,rights,serve,social,tickets}`, contracts
(`agent_workplace.py`, `api.py`, `panel.py`, `catalogue.py`), панельные `events.ts`/`validation.ts`.

## Решения

- **Без второго контура исполнения.** Шаг задачи — m3-задание вида `activity` на
  существующих JobOwner/claim/lease, supervisor STOP/epoch, owner fences и
  `Policy.transaction_check`. Владельцы ACTIVITY/TICKETS/SKILLS добавлены в
  `DOMAIN_OWNERS`: их запись внутри задания проверяется так же, как запись памяти/GM.
- **ModelGateway (пункт 1).** `ExecutionModelGateway` → `Execution.generate` → `LLMGateway`:
  тот же журнал попыток, `PrivateAPIBudget`, отмена; своего ключа/счётчика нет. Исчерпание
  или запрет → `not_admitted` без вызова провайдера. Порт AW-00 расширен совместимо:
  `ModelRequest.call_id/result_model`, `ModelReply.parsed`.
- **Бюджет.** `activity_enabled/activity_daily_calls` — своя доля общего суточного лимита,
  как у GM: никогда не берёт резерв памяти и пол диалога; проверка в `Execution._begin`
  и в тике до решения (BUDGET → вызова нет). Минимум лимита в панели учитывает долю.
- **Роли.** `activity` (StepDecision) и `activity-goal` (GoalProposal) — закрытые схемы,
  протокол live-провайдера знает обе. Вид `activity` в `OPT_IN_KINDS`: init не создаёт
  его capability/permit — обновление само ничего нового не запускает.
- **Включение только offline:** `configure-activity --enable [--daily-calls N
  --cooldown-minutes M --own-goals --own-goal-daily K --max-open-tasks T]`. Требует
  `operator_controls` и `enable-tickets`; создаёт `m3.activity`/`permit-activity`,
  переводит обе роли на live, добавляет права ACTIVITY (`rights.host_grants` сохраняет
  все offline-флаги и при `enable-social`/`enable-tickets`). Рабочий host не менялся.

## Поведение

- Задачи (`WorkTask`) и попытки (`WorkAttempt`) — владелец ACTIVITY; попытка связана с
  `operation_id` задания и его freshness; ID детерминированы (`<task>.aNNNN`), повтор
  команды не дублирует записи.
- Тик (каждые `check_seconds`, по умолчанию 30 с): только ACTIVE/OPEN/autonomous/WORK,
  после диалога и памяти; сначала сверка отправленных попыток по статусу задания
  (нет задания → `unknown`, поверх живой попытки новая не начинается); затем порядок
  assignment → ticket_followup → commitment → own_goal; cooldown и `max_attempts_per_task`;
  ожидающая задача продолжается, когда на вопрос ответили или нужная возможность стала
  доступна (или в ней отказали). Нет работы → `NO_WORK` без вызова модели.
- Шаг: модель видит цель, ответы оператора, отказанные возможности и manifests со
  статусом available/not_available (доступно = automatic право `workplace-agent` + ready
  binding + зарегистрированный executor). Решения: complete (записывается как
  «Собственный вывод», не подтверждённый результат), use_capability (недоступная →
  тикет `capability_request`, ждёт только эта задача), ask_operator (тикет-вопрос),
  defer, abandon. Частичный/невалидный ответ ничего не делает (попытка failed).
  Учтённый ответ оператора закрывает вопрос агентом (основание — ответ оператора;
  запрос возможности так закрыть нельзя).
- Собственная цель: при `own_goals` и пустой очереди — не больше `own_goal_daily` вызовов в
  день с cooldown; «none» — допустимый спокойный период.
- Оператор: `work.assign` (CreateCommand) принимается и в STOPPED, исполняется после START;
  чтения `work-tasks`, `work-attempts`; событие `work.changed` (панель его принимает).
- Restart/STOP: после restart run STOPPED, вызовов нет; после STOP новых отправок нет.

## Инструменты (после AW-03)

- Executors `workplace.skills` (find/read/save) и `workplace.knowledge` (search/read/write)
  в `m3_composition/workplace_tools.py`; регистрируются, только если хост подготовлен
  `enable-workplace-files`. Доступность для модели прежняя: право + ready binding + executor.
- Перед IO шаг записывает выбранную capability в свою попытку (`ActivityBook.bind`);
  допуск шага ссылается на эту попытку (`WorkAdmission.attempt_id` = id `WorkAttempt`, не
  аренды задания). Файловый владелец проверяет право агента по capability попытки и
  области до и после IO; find/search executor проверяет область сам. Отказ → шаг failed
  с кодом, без расширения.
- Результат шага — `WorkTask.progress` (`WorkStep`: capability, статус, сводка, что прочитано,
  что записано; последние 20); следующие шаги видят последние 6 сводок. Всё, что задача
  прочитала, входит в `inputs/input_files` следующей попытки — файл, записанный после
  чтения, сохраняет lineage (`derived_from`), отзыв прочитанного закрывает запись.
  Записанные файлы — `WorkTask.result_files` (проверяемый результат); `complete` остаётся
  «Собственный вывод».
