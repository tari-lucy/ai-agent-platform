заявлением Claude «дерево совпадает с проверенным»). Разобраны диффы 5–8 по четырём
инвариантам поручения:

- **Обход bridge.** Новых сетевых путей нет: всё добавленное — рендеринг и одна
  повторная отправка `work.session.message` через тот же bridge-командный путь
  (patch 6). Повтор срабатывает только на настоящий HTTP 409 (атомарный отказ CAS,
  сообщение не сохранено), читает свежий транскрипт и при отсутствии сохранённого
  текста делает ровно одну повторную отправку с новым request_id
  (`<id>:v<version>`); потерянный ответ (не-409) ретрая не делает. Не-bridge origin
  и `/api/v1/*` по-прежнему 403, неизвестные маршруты 501 — неизменны.
- **Частные данные в браузере.** Единственное новое состояние — `clientIDs`
  (page-lifetime `Map` соответствия sequence→клиентский id, patch 5); localStorage/

- **Точный ACK.** Механика receipt не тронута: по-прежнему свежий draft владельца

  уведомления — `type:"assistant"` с пустым `content` и `error.type=PlatformNotice`,
  т.е. словами платформы, не личности, и не подтверждаются. Тест адаптера обновлён

- **Смешение личностей.** Уведомления несут `view.scope.persona_id` своей сессии;

  семантика intake из bridge-протокола. Каталог/директории не смешиваются.

## Часть 2 — OC-05: отложено до исправлений Claude

На момент сдачи исправлений после `09581ac`/`fe04cac` нет ни в одной ветке — по
условию поручения проверка части 2 не выполнялась, ветка автора не правилась.
Подтверждённое Codex замечание (replay после изменения состава даёт 503 вместо
прежней квитанции) и открытый вопрос commit-проверки (перепроверки
manifest/binding/policy до write-транзакции) соответствуют пунктам 1–2 моего
поручения. Подготовленные независимые проверки (выполняются на временном host/owners,
без модели; команды `workplace.access.preview/execute` через настоящий HTTP):

1. **Replay после изменения состава.** Успешный preview+execute, сохранить квитанцию;
   изменить потолок (удалить участника); повторить тот же execute с тем же
   request_id/телом → та же квитанция, ни одного нового/продлённого Permission.
2. **Устаревшее право.** Между preview и execute изменить версию manifest /
   состояние binding (не ready) / версию policy → execute отказывает
   (STALE/ACCESS_DENIED), Permission не записывается. Внутритранзакационное окно —
   через hook владельца, если он появится; иначе фиксирую как незакрытое.
3. **Откат набора.** Сорвать запись одного участника (конфликтная версия
   существующего Permission между проверкой и записью) → транзакция откатывается
   целиком: нет Permissions, нет InitialAccessProof, квитанция не success.
4. **Поздняя capability.** После успешного execute зарегистрировать новую
   capability+binding в автоматическом потолке → у неё нет Permission, прежний proof
   её не покрывает, replay прежнего request_id неизменен.
