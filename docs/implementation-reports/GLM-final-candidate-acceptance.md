## Часть 1 — серия патчей 5–8 на main `9e7f268`

Серия выросла с четырёх до восьми патчей; новые — `0005` (уведомления о ходе, id
клиента, скрытие git-деталей), `0006` (нумерованные ответы, остановка без истории,
одна безопасная повторная отправка при 409), `0007` (ссылка на точное ожидающее
обращение), `0008` (текст ожидания для любой личности). Применение всей серии 1–8 к
чистому тегу `e3c4eb2` воспроизведено независимо (`git am`, чисто; совпадает с
заявлением Claude «дерево совпадает с проверенным»). Разобраны диффы 5–8 по четырём
инвариантам поручения:

- **Обход bridge.** Новых сетевых путей нет: всё добавленное — рендеринг и одна
  повторная отправка `work.session.message` через тот же bridge-командный путь
  (patch 6). Повтор срабатывает только на настоящий HTTP 409 (атомарный отказ CAS,
  сообщение не сохранено), читает свежий транскрипт и при отсутствии сохранённого
  текста делает ровно одну повторную отправку с новым request_id
  (`<id>:v<version>`); потерянный ответ (не-409) ретрая не делает. Не-bridge origin
  и `/api/v1/*` по-прежнему 403, неизвестные маршруты 501 — неизменны.
- **Частные данные в браузере.** Единственное новое состояние — `clientIDs`
  (page-lifetime `Map` соответствия sequence→клиентский id, patch 5); localStorage/
  IndexedDB/service workers не появились ни в одном из диффов 5–8.
- **Точный ACK.** Механика receipt не тронута: по-прежнему свежий draft владельца
  (utterance/revision/version/полный текст), видимость вкладки и ≥60% компонента,
  одна автопопытка, идемпотентный `request_id`. Нумерация `reply-<seq>-<n>` (patch 6)
  согласована между рендером и `watchReceipt` (общий `next`); платформенные
  уведомления — `type:"assistant"` с пустым `content` и `error.type=PlatformNotice`,
  т.е. словами платформы, не личности, и не подтверждаются. Тест адаптера обновлён
  соответственно (`reply-1-2`).
- **Смешение личностей.** Уведомления несут `view.scope.persona_id` своей сессии;
  `open_ticket_ids` (patch 7) приходит из scoped-проекции транскрипта владельца и
  ссылается на карточку панели той же личности; патч 8 корректно обобщает текст
  ожидания на неактивные личности (сообщение хранится, активации нет) — ровно
  семантика intake из bridge-протокола. Каталог/директории не смешиваются.

**Нарушений инвариантов в патчах 5–8 не найдено.** Одно незначительное наблюдение
(улучшение, не блокер): дедупликация повтора в patch 6 (`stored.text === text`) может
лопожно сработать, если между устаревшим чтением и 409 другая вкладка сохранила
сообщение с тем же текстом — наше сообщение тогда не отправится (консервативно, без
дубля; чисто UX-край).

## Часть 2 — OC-05 на `f809a6a`: независимая проверка выполнена

Исправления Claude (`f809a6a`) прочитаны: replay исполненного плана теперь входит в
авторизованную транзакцию владельца до чтения участников; основания (Workspace,
manifest, binding, текущие/отсутствующие Permission) перепроверяются `_Bases.check`
внутри write-транзакции через штатный `authorize_writes`; ceiling перепроверяет fence.
Повторный просмотр Codex (`d40fec4`) закрывает оба прежних замечания.

Моя независимая проверка — `tests/opencode_acceptance/test_glm_initial_access.py`
(production init/build/ASGI, временный host, `enable-recovery` +
`enable-workplace_files --ceiling-days 7`, без модели; пути намеренно отличаются от
авторских регрессий): **1 passed, 19.47 s**. Проверено по пунктам поручения:

1. **Replay после изменения состава.** После успешной выдачи (оба права v1) потолок
   снят целиком (`rt.permission_ceiling = {}` — исходный сценарий дефекта `09581ac`):
   тот же execute с тем же request_id возвращает **ту же квитанцию**; версии и
   `expires_at` обоих прав не изменились — ни новой выдачи, ни продления.
2. **Устаревшее право.** Три отдельные мутации между preview и execute — версия
   manifest (+1), `policy_version` Workspace (+1), binding skills → `disabled`/без
   `verified_at` — каждая даёт **409**, ни одного нового/изменённого Permission.
   (Внутритранзакационное окно закрыто механизмом `_Bases` + SQLite write
   reservation по просмотру Codex; детерминированная конкурентная проба не
   выполнялась — внешние мутации между командами покрыты.)
3. **Откат набора.** Инъекция сбоя записи второго участника (`Permission` skills)
   внутрь транзакции: первый участник уже записан → **весь набор откатывается**
   (оба права прежние v1, proof остался неисполненным), чистый повтор тем же планом
   с новым request_id успешен (оба права v2, срок от нового решения).
4. **Поздняя capability.** Зарегистрированы manifest + ready binding + запись ceiling
   для `workplace.extra` после выдачи: права у неё нет; replay прежней квитанции
   выполняется без выдачи extra; статус показывает её в настроенном наборе.

Агент всё время STOPPED, вызовов модели нет. Ruff изменённых файлов чистый; полный
suite не запускался (поручение — один затронутый прогон).

**TS2741.** На момент сдачи этой части исправление Claude всё ещё не опубликовано
