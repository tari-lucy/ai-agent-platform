# M2-02 — жизненный цикл источников/эпизодов и recall-адаптер

Дата: 2026-10-13. Исполнитель: Claude Code. Ветка: codex/m2-02-memory-recall, отдельный worktree.
База: 7abe59c (`origin/main` после интеграции M2-01). Зависимости M1-02 и M0-05 интегрированы.
Статус: **готово в ветке для review; runtime-интеграция не выполнена и не проверена.**
Задача выдана оператором напрямую; файловую зону я выбрал по аналогии с M2-01 (см. ниже) —
координатору подтвердить её и внести назначение в doc24.

## Что сделано

- `application/memory`: порты (`RecallIndex`, `Embedder`), дословное разбиение на куски,
  `MemoryService` (источники, эпизоды, конфликтные утверждения, обслуживание индекса),
  `RecallService` (recall с перепроверкой авторитета), `IndexHealth` (видимое отставание индекса).
- `adapters/recall`: `SQLiteRecallIndex` — производный FTS5 + sqlite-vec в **отдельном** SQLite-файле.
- Файлы: `packages/application/.../memory/*`, `packages/adapters/.../recall/*`, `tests/memory/*`,
  этот отчёт. Contracts, storage, migrations, зависимости/lock, Compose, API/UI, jobs, supervisor
  не менялись; dev-пакеты `sqlite-vec==0.1.9` и `numpy==2.5.4` взяты из extra `recall` в `uv.lock`.

## Приёмка

| Критерий M2-02 | Результат (тесты на реальных SQLite/FTS5/sqlite-vec) |
| --- | --- |
| Access перед контекстом | Каждый кандидат индекса перечитывается через repository **для запрошенной цели**; `read=False` / запрет API / запрет публикации отсекают фрагмент; отзыв прав и удаление при устаревшем индексе, смена версии, просрочка TTL, ACL читателя — не выдаются; чужие scope/persona/workspace/work-test недостижимы; текст сверяется по хешу байт |
| Дедуп по исходному опыту | Источники одного эпизода — один фрагмент (группа сохраняется после полной пересборки); одинаковый текст у разных внешних событий **не** объединяется; один внешний event — один Source, правка текста — `VERSION_CONFLICT`; один operation — один эпизод |
| FTS fallback | Без embedder / при ошибке embedder / при другой модели / при неполных векторах recall лексический, `index_state="degraded"`, `complete=False`; восстановление эмбеддингов возвращает `ready`; сломанный индекс — `unavailable`, а не пустой «успех» |
| Происхождение / конфликты | `attribution` = provenance + тип + автор + уверенность идентификации + дата; противоречащие `Claim` сохраняют обе позиции, связи с двух сторон в одной транзакции; ID конфликтов показываются только читателю, который видит эти `Claim` |
| Жизненный цикл | TTL от времени события (не от регистрации); просроченное при регистрации отклоняется; права/expire/delete по `expected_version`; удалённая identity не импортируется повторно; сбой индекса не откатывает авторитет и виден как `lagging`; reconcile/reindex чинят missing/stale/extra |

Мутационные проверки recall (группа, хеш/версия, отсутствие источника, цель доступа, видимость
claim, пометка degraded) — каждая ломает тест; один выживший мутант (видимость claim) закрыт
новым тестом.

**Качество лексической ветки**: на корпусе M0-05 (48 положительных запросов) `SQLiteRecallIndex`
даёт Recall@8 **0.8125** на 1k и на 10k — совпадает с замеренным baseline FTS fallback (M0-05),
p95 1.8 / 6.3 мс. Это измерение только лексической ветки на синтетическом корпусе (скрипт не
коммитился); гибрид с реальной MiniLM в этой ветке **не** запускался.

## Решения и допущения

1. **Индекс в отдельном файле**, таблицы не в Alembic: он производный и перестраиваемый (doc20),
   а миграции — зона M1-02. Основная БД и индекс не смешиваются (проверено тестом).
2. Права источника в `SourceDraft` без значений по умолчанию: ни один путь по умолчанию не
   открывает источник API или публике.
3. ID источника детерминирован (внешняя identity либо `request_id`) — отсюда идемпотентность и
   запрет повторного импорта удалённого; ID эпизода — от `operation_id`.
4. `Source` с внешним ID после TTL/удаления: повтор регистрации → `ACCESS_DENIED` (identity занята).
5. Иерархию «сводка → фрагмент → эпизод» (консолидация) и экстракцию (M3-01) не реализовывал:
   индексируются только `Source`.

## Не проверено / ограничения

- **Runtime-интеграция** (bootstrap, HTTP, jobs, M2-06 контекст) — не выполнялась.
- Реальный embedder (FastEmbed/MiniLM) — адаптера нет; Recall@8 гибрида на моём коде не измерен.
  Доверять M0-05 можно только для baseline-логики, не для этой реализации.
- Windows, Linux-контейнер изоляции M1-02, SQLite 3.40.1 образа (использованы только старые
  возможности FTS5), нагрузка >10k, конкурентные процессы, power-loss, блокировка потоков под нагрузкой.
- Точные открытые обещания «вне top-k» — M2-03, не здесь. Черновые/внутренние `Claim` без источников
  невозможны по контракту.
- Index хранит производную копию текста (FTS); включён `secure_delete`, но физическое стирание
  WAL/бэкапов и «удалённое не оживает после restore» — M5.

## Запросы координатору (shared changes, не обходились)

1. **Просроченные (TTL) Source недоступны даже владельцу**: repository скрывает их, поэтому
   авторитетную очистку payload/revisions после TTL (и переход в `expired` по факту) сделать нельзя.
   Нужен API storage (чтение просроченных владельцем / retention sweep) — M1-02-владелец или M5-01.
   Сейчас `expire_source` работает только до истечения срока; индекс чистится `purge_index`.
2. **Реальный embedder**: отдельная задача на FastEmbed-адаптер (pinned revision/хеши из M0-03,
   ограничения CPU/RAM) и упаковка extra `recall` в core/worker image (Dockerfile/lock — владелец).
3. **Синхронизация индекса**: пока inline после коммита + reconcile. Когда M1-04 даст dispatcher,
   переключить на события outbox (Source/Claim/Episode) — методы `RecallIndex` готовы.
4. **Grants**: memory-owner — `read/write` + `api_transfer`/`public_disclosure` на `Owner.MEMORY`
   (эти флаги определяют допустимые цели recall); другим читателям нужны grant и `RecordAccess`
   (`reader_access`). Доверенная композиция ядра.
5. Подтвердить зону файлов M2-02 и статус в doc24.
