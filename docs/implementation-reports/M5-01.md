# M5-01 — retention, удаление с tombstone, restore gate, жизненный цикл метаданных

Дата: 2026-10-14. Исполнитель: Claude Code. Ветка: codex/m5-01-retention, отдельный worktree.
База: 6755f43 (main с M4-01). Зависимости M2-02, M2-03, M2-05 интегрированы.
Статус: **готово в ветке для review; runtime-интеграция не выполнена, реальный провайдер/Windows/контейнер не проверялись.**
Зона: `application/retention`, `adapters/retention`, `tests/retention`, этот отчёт. Contracts, storage, migrations,
зависимости, Compose, API/UI, jobs не менялись (запросы владельцам — ниже).

## Что сделано

- `RetentionService`: `preview_delete` → `delete` (по digest предпросмотра), `sweep` (истечение + метаданные),
  `apply_ledger` (restore gate), `resume` (завершить прерванное).
- `SQLiteDeletionLedger`: отдельный SQLite-файл (ID, версия, причина, время; без содержимого), причина не ослабляется.
- `SQLitePhysicalStore`: стирание текста во всех ревизиях, флаги, зависимые записи, агрегаты расхода,
  `finalize` (secure_delete + checkpoint TRUNCATE + VACUUM).
- Порядок: ledger → блокировка (`revoke`) → tombstone → индекс/кэши → физическое стирание → purged.

## Приёмка

| Критерий M5-01 | Результат (реальные SQLite/FTS5/sqlite-vec, виртуальное время) |
| --- | --- |
| 30 дней | текст уходит с истечением срока и не раньше (29 дн. 23 ч — ещё есть); защищённый не истекает; срок не продлевается: источник без долговременного следа попадает в `unconsolidated`; тестовые — предел неактивности, не длиннее срока |
| 14/90 дней, метаданные | LLM-попытки и расчёты старше 90 дн. сначала сводятся в месячный агрегат (токены, сумма Decimal; неизвестное считается отдельно и не нулём), затем стираются, повтор не удваивает; агрегаты старше 12 мес. стираются; завершённые job-записи >30 дн. стираются, `OUTCOME_UNKNOWN` остаётся; текст просроченных квитанций удалён, повтор запроса даёт `OUTCOME_UNKNOWN`, а не исполнение |
| Удалённое не выдаётся до физической очистки | при сбое любого шага источник остаётся заблокированным (в т.ч. по самому авторитету), отчёт `blocked_pending_purge` + шаг; `resume` завершает; recall его не отдаёт |
| Физическое отсутствие | тест читает байты файлов БД, WAL, SHM и индекса: перед удалением текст найден (детектор работает), после — нигде; то же для зависимого claim и старых ревизий |
| Версии не хранят raw | текст стёрт из всех ревизий источника; зависимые записи с единственным основанием стёрты, с другими основаниями остаются |
| Restore | копия БД до удаления + независимый ledger: `apply_ledger` повторно стирает удалённое и истёкшее; идемпотентно; неизвестные ledger-записи отчитываются, а не выдумываются; повторный импорт удалённой identity запрещён |
| Изоляция | sweep/delete действуют на одну область; другая persona и work/test не затрагиваются |

## Решения и допущения

1. Физический слой работает рядом с owner API: storage скрывает просроченные записи даже от владельца. Это новый
   файл адаптера; существующие файлы storage не менялись. Отдельный запрос ниже.
2. `DeletionTombstone` не версионирован → два неизменяемых события (`blocked`, `purged`).
3. Зависимые записи других владельцев (Person, Promise, Relationship, Topic) не стираются, а показываются как
   `detached`: решение за владельцем.
4. Служебные записи пишутся командой `dialogue.message` с target `retention` (типа служебной команды нет).
5. «Последнее использование» тестового источника не отслеживается — берётся последнее изменение.

## Не проверено / ограничения

- Runtime-интеграция (bootstrap, расписание sweep, HTTP/панель M4-04), Windows (VACUUM, файловые блокировки),
  контейнерные тома, SQLite 3.40.1 образа, нагрузка, конкурентные процессы с открытыми читателями при `finalize`
  (возвращает `RESOURCE_BUSY`, удаление остаётся pending).
- Стирание из внешних копий и **backup** — M5-02 (здесь только независимый ledger и `apply_ledger`).
- Экспорт и кэши контекста: порт `DerivedPurger` есть, реальных кэшей/экспорта в репозитории пока нет.
- Физическое стирание на SSD/журналируемой ФС и шифрование диска не гарантируются приложением.
