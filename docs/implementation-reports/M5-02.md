# M5-02 — backup, restore gate и защита миграций

Дата: 2026-10-14. Исполнитель: Claude Code. Ветка: codex/m5-02-backup, отдельный worktree.
База: 263430e (main с M5-01). Зависимости M5-01, M1-04 интегрированы.
Статус: **готово в ветке для review; runtime-интеграция не выполнена, Windows/контейнер/реальные тома не проверялись.**
Зона: `application/backup`, `adapters/backup`, `tests/backup`, этот отчёт. Малая правка вне зоны, но в моей зоне M5-01:
`adapters/retention/ledger.py` (идентичность ledger и счётчик изменений, `snapshot_to`). Contracts, storage, migrations,
зависимости, Compose, API/UI, jobs не менялись.

## Что сделано

- `BackupService`: `create(kind)`, `verify`, `copies`, `preview_restore`, `restore`, `guarded_migration`, `rehearse_migration`.
- Адаптеры: `SQLiteSnapshotter` (backup API SQLite, не копия файла), `DirectoryBackupStore` (копия появляется целиком или
  никак; права 0700/0600; удаление с перезаписью), `SQLiteStagingFactory`/`SQLiteRestoreTarget` (восстановленная БД в staging),
  `FileSwitcher` (переключение файлов с откатом; старые файлы остаются в `replaced/`).
- `SQLiteDeletionLedger`: `ledger_id` + счётчик изменений + `snapshot_to` — потерянный, подменённый или откатанный ledger виден.

## Приёмка

| Критерий M5-02 | Результат (реальные файлы SQLite/индекса/ledger, виртуальное время) |
| --- | --- |
| Консистентный snapshot | при активной записи копия проходит `integrity_check`/`foreign_key_check`, у каждой записи есть ревизия; контрольный «наивный» копирование файла теряет коммиты из `-wal` (хуже снимка) |
| 7 ежедневных + перед миграцией | остаются 7 новейших daily; pre-migration/pre-restore считаются отдельно (по 2); копия старше 30 дней удаляется (сырой текст не живёт в копиях бессрочно); квота: предупреждения 80%/90%, при заполнении новая копия не создаётся и ничего не стирается |
| Restore + deletion ledger | старая копия + позднейшее удаление и истечение: после restore текст отсутствует в БД, WAL и пересобранном индексе (чтение байт), recall его не отдаёт, остальное восстановлено; запись после копии в копию не попадает |
| Ledger gate | другой/новый ledger → `LEDGER_UNAVAILABLE`, откатанный (меньший счётчик) → `LEDGER_OLDER_THAN_COPY`, нечитаемый ledger → блок; копия не допускается |
| Agent stopped | restore и миграция отказывают, если агент не `STOPPED` (проверка в предпросмотре и ещё раз перед действием); restore агента не запускает |
| Целостность | подмена байта в копии → `CHECKSUM_MISMATCH`, restore отказ; изменение копии между проверкой и staging → отказ; сбой любого шага staging оставляет живую БД нетронутой |
| Нет повторного исполнения | события outbox (`pending`/`delivered`) замораживаются; незавершённые операции из копии показываются в предпросмотре (исход после копии неизвестен) |
| Миграции | схема новее ПО — блок; старее — миграция в staging до переключения; `guarded_migration`: проверенная копия существует до upgrade, при сбое отчёт называет копию (только тип ошибки); `rehearse_migration` на снимке не трогает живую БД |
| Решение оператора | restore требует `operator_decision_id` и неизменённый предпросмотр (digest) |

## Решения и допущения

1. Копия — снимок через backup API; индекс не копируется (пересобирается при restore из очищенного авторитета).
2. Страховочная копия `pre_restore` создаётся до любых изменений; замещённые файлы остаются в `replaced/`, оператор стирает их
   (`FileSwitcher.discard`) после проверки. Они содержат данные до восстановления.
3. Состояния запусков (`RunSession`) из копии не изменяются: supervisor при `recover` сам оставит занятый слот FAULTED, пока
   исполнители не сверены (M1-03). Агент после restore остаётся остановленным.
4. Незавершённые задания не переписываются (их владелец — jobs): restore лишь замораживает outbox и сообщает число.
5. Копия ledger для каждого backup кладётся в отдельный `ledger_dir`; это минимум (ID, версии, причины, времена).

## Не проверено / ограничения

- Runtime-интеграция (расписание ежедневной копии, кнопки панели M4-07, bootstrap), Windows (блокировки файлов при
  `os.replace`, права), контейнерные тома, SQLite 3.40.1 образа, большие БД и время снимка под нагрузкой.
- Копия на другом носителе/шифрование — отдельная настройка оператора, приложение их не обещает.
- Перезапись удаляемых копий — best effort, на SSD/CoW/снимках ФС физическое стирание не гарантируется.
- Реальный `FastEmbed`-индекс не использовался (пересборка с mock-embedder); медиа-каталог не копируется (нет реализации).
- Восстановление отказоустойчивости при падении процесса между `close_live` и `switch`: живые файлы целы до `switch`
  (откат при ошибке), но сценарий kill -9 в этот момент не проверялся.

## Запросы координатору / владельцам

1. **Composition**: `BackupService` с реальными `SQLiteSnapshotter`/`DirectoryBackupStore`/`FileSwitcher`, `AgentGate` на
   `Supervisor.snapshot`, staging-фабрика с теми же extensions/principals/embedder, `ledger_dir` вне тома основной БД,
   ежедневное расписание; после restore — только явное возобновление.
2. **Jobs-владелец**: операции, не завершённые на момент копии, после restore должны получить `OUTCOME_UNKNOWN`/сверку через
   владельца; сейчас восстановление только замораживает outbox.
3. **Storage/migrations-владелец**: публичный способ закрытия хранилища и чтения `HEAD` (сейчас `close_live` и head
   приходят из композиции); миграции staging — через `SQLiteStore.upgrade`.
4. **M4-07**: panel должна показывать preview (issues, at-risk операции, число замороженных событий) и требовать явного решения.
