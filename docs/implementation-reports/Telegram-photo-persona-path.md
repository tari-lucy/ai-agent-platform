# Telegram: фото из файлового пространства личности

Дата: 2026-10-31. База: main `d6f3222`.
Ветка: `codex/telegram-photo-ticket`.

## Причина и исправление

Агент сохранял корректные JPEG в `/workspace/shots`, но channel() искал файл
в `<files_dir>/shots` вместо `<files_dir>/<persona_id>/shots` — каталог,
который HarnessHost.folders() монтирует как /workspace. Поэтому возвращалось
«нет такого файла», хотя файл существовал в контейнере.

Композиция channel() теперь использует persona_id переданного scope.
install() передаёт scope и при выключенных комментариях: доступ к фото от
настройки комментариев не зависит. Если scope не передан, папка фото не
назначается; общей папки или запасного поиска у другой личности нет.

Границы загрузки JPEG, проверка содержимого моделью перед публикацией,
дневной лимит, STOP и Telegram-транспорт не менялись. Образы, панель и
конфигурацию пересобирать/изменять для этой правки не нужно.

Диагностика на работающем Linux host: прочитаны обращение и метаданные
соответствующих файлов (размер, права, JPEG-сигнатура); личные изображения
и тексты публикаций в репозиторий не копировались. Старый Windows host —
историческая копия, сервис там не запускался. n8n и настройки VPS не менялись.

## Проверки

- Новый регрессионный тест перед исправлением: 2 failed — неверная папка
  при включённых и выключенных комментариях.
- После исправления на Linux VPS, отдельная временная копия исходников,
  работающий сервис не менялся:
  `test_channel_format_photo.py`, `test_channel.py`, `test_comments.py` —
  **29 passed**, 1,99 с.
- Регрессия создаёт одинаковое имя JPEG у двух вымышленных личностей и
  в общей папке. Читается только файл выбранной личности; после его удаления
  соседний и общий файлы не используются.
- На Windows эти наборы: **28 passed, 1 failed**. Единственное падение —
  существующая проверка запрета симлинка в ChannelPost._photo: O_NOFOLLOW
  отсутствует на Windows. Этот загрузчик в пакете не менялся; Linux-тест
  запрета симлинка проходит. Отдельный переносимый механизм запрета ссылок
  на Windows этой правкой не реализован.
- Ruff check, ruff format --check и mypy для изменённого production-модуля
  проходят. Полный gate не запускался.
- Платных вызовов и реальной публикации в канал во время проверки не было.
- Дополнительная read-only проба кандидата на настоящем JPEG из обращения:
  выбран каталог нужной личности, файл успешно прочитан (около 70 КБ),
  сетевых вызовов нет. Содержимое фото не сохранялось в артефакты проверки.

## Применение

Для подключения нужна обычная выкладка Python-кода и перезапуск платформы
после STOP оператора. Пока агент ACTIVE, работающий release не изменяется.
Первый прямой push в main остановила автоматическая проверка разрешений.
После явного ответа оператора «Да, влить в main» выполнен обычный
fast-forward `d6f3222..ff219d3`; обхода первоначального отказа не было.
После выкладки агент может повторить собственный вызов platform_channel_post
с именем JPEG из /workspace/shots; повторно загружать или переносить фото
не нужно. Реальная публикация и успешное сообщение агента подтверждают
полный внешний путь отдельно от тестов.

## Выкладка на VPS после STOP оператора

Оператор подтвердил STOP на сервере. Перед обновлением проверены STOPPED
и пустой unconfirmed_resource_ids. Установлен отдельный release
`~/ai-platform/releases/ff219d3-photos`, current переключён на него;
предыдущий `d6f3222` сохранён для отката.

Панель взята из прежнего release: frontend не менялся. Lock-файлы
семантически равны (различались байты представления), версии зависимостей
не изменены. Установочный node_modules-симлинк из Git-архива не извлекался:
он ведёт на абсолютный путь и для готовой панели не нужен.

Offline-sync сначала отказал из-за .python-version=3.14.8 при установленном
на VPS 3.14.10; версия возвращена на предыдущую. Повтор с явным
`uv sync --python <существующий venv/bin/python> --locked --offline`
успешен. Путь импорта production-модуля проверен: новый release. Новый
интерпретатор не скачивался.

При быстром перезапуске проявился известный PORT_UNAVAILABLE: после
освобождения 8765 штатный systemd retry запустил сервис. Сеть, файрвол,
sshd и Docker не менялись; n8n не затронут.

Финальная проверка: панель HTTP 200, последний RunSession STOPPED,
неподтверждённых ресурсов нет. Уже установленный код прочитал настоящий
JPEG из обращения (около 70 КБ); модель и Telegram не вызывались.
START за оператора не выполнялся; реальная публикация остаётся проверкой
Опечатки после её запуска.
