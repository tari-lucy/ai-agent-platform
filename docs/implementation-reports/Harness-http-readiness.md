# Doc33: фактическая HTTP-готовность OpenCode

2026-10-29. Ветка `codex/harness-ready-health`, база `3df61e4`.

## Дефект и изменение

На Windows первая живая проба получила `RemoteProtocolError` при создании
новой native-сессии сразу после `harness-status.ready=true`. Вызова модели
в этой попытке не было. После ожидания `/global/health` тот же штатный путь
работает: контейнер уже получил адрес, но OpenCode ещё не слушал HTTP.

`HarnessHost` теперь публикует `ready` только после `healthy=true` от
аутентифицированного loopback `/global/health`. Общее ожидание ограничено
60 секундами, отдельный запрос — двумя секундами wall-time; между запросами
пауза 250 мс. Проверки ACTIVE, epoch и закрытия выполняются до и после
запроса. STOP не ждёт модель; отмена проходит в прежний `finally` удаления
ресурсов. Контекст, память, права, модель и тариф не меняются.

## Проверки

- `tests/harness/test_readiness.py`: **5 passed**. Отказ соединения, ложный
  health, STOP/смена эпохи/закрытие при получении health, зависший health.
- Ruff: чисто по двум изменённым Python-файлам.
- Strict mypy: чисто по изменённому модулю (зависимые импорты без повторной
  проверки всего проекта).
- Независимый read-only review: замечание об ограничении wall-time исправлено,
  повторный просмотр без блокеров. Ревьюер тесты и личный host не запускал.

Длинный живой сценарий начат на исходной базе с явным ожиданием HTTP в
приёмочном клиенте. Сам по себе он не доказывает выкладку этой правки.
Итог включения и Windows-сценария — в `Harness-acceptance.md`.
