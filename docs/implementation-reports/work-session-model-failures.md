# Рабочий ход: точная диагностика и окончательный отказ без 429

2026-10-23, Codex. База 278891e, ветка codex/work-session-gateway-diagnostics.
UI/progress и контракты WorkSessionTranscript остаются в окне Claude.

## Проверенные факты

Пользовательский ход был принят, имел несколько model attempts и завершился FAILED
примерно на границе 120 s; результата и нового файла нет. Последние два ответа
incomplete, выход 184 и 207 токенов при лимите 1024: нехватка токенов не доказана.
Журнал LLMAttempt хранит статус и usage, но не подробную причину отказа gateway.
Агент остановлен штатным STOP, слепой повтор не запускался.

В sandbox найден отдельный дефект: любой неуспешный model reply превращался
в not_admitted и HTTP 429. OpenCode воспринимал окончательный отказ как временную
перегрузку, продолжая retry/backoff до лимитов контейнера. Это установленный дефект
передачи ошибки, а не доказательство причины первого некорректного ответа модели.

## Изменения

- Docker runner сохраняет неуспешный terminal status gateway в ответе facade.
- Facade возвращает 403 для not_admitted/cancelled, 400 для остальных неуспешных
  результатов. Реальный конкурентный MODEL_BUSY остаётся 429; окончательный
  отказ больше не выдаётся за rate limit. Bounded retries провайдера остаются
  у существующего LLMGateway. Unknown не превращается в успех или новый запрос.
- Валидация tool proposals сохраняется строгой. ToolProtocolError несёт закрытый
  enum причины: индексы, структура, JSON аргументов, необъявленное имя, дубликат id.
- Gateway пишет только фиксированные коды отказа и status/failure enum в технический
  журнал. Имена/ids модели и инструментов, аргументы, сообщения, endpoint и исключения
  с исходным текстом не логируются. Отдельный код отмечает несовместимый terminal
  event при наличии tool fragments.
- Новых wire-полей, migrations, зависимостей, прав или инструментов нет.
  Существующие DB/статусы/истории не переписываются. Container bridge передаётся
  доверенным runner из host; пересборка закреплённого OpenCode image не требуется.

## Персональная диагностика и совместимый режим tools

После обновления b3eca99 проведена одна повторная попытка уже выданного поручения
через обычный START, с прежними правами, общим дневным лимитом и без новых сообщений.
Проверено: предыдущий исход failed, cooldown истёк, других неопределённых попыток
нет. Потрачено 1 model call; gateway сообщил TOOL_INDICES/MALFORMED_RESULT.
Ход завершился failed без нового файла, затем выполнен STOP. Это точный код
новой попытки, не восстановленная причина предыдущих двух ответов.

Потоковую сборку tool_calls нельзя принимать по догадке. Добавлен альтернативный
режим того же Chat Completions: при объявленных tools запрашивается stream=false,
а gateway получает целый message.tool_calls array. Индексы берутся из позиций
полного массива, не перенумеровываются в неполном SSE. Проверки завершения,
объявленных имён, id, JSON, дублей, квот и STOP остаются прежними.
Пустой tool result теперь различим кодом TOOL_MISSING_CALLS.

Режим задаётся данными activity.stream_tools; у существующего/нового config по
умолчанию true. Штатная offline-команда configure-activity --complete-tools
выбирает полный ответ; --stream-tools возвращает прежний SSE. Вызовы без tools
по-прежнему потоковые. Endpoint, ключ, модель и роль activity не меняются.
Никакого автоматического платного fallback complete→SSE нет. Тело полного ответа
ограничено 256 KiB, таймаутом той же assignment, redirect запрещён; сырые ошибки
не выводятся. Знакомые stream indices не нормализуются и не допускаются слабее.
