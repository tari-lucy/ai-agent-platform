# Doc33, этап 3 — память из native OpenCode и самостоятельная работа

Дата: 2026-10-29. Ветка: `codex/harness-stage3`. База поручения —
`claude/harness-stage1` (`3bb91b6`), затем приняты стыки Claude `036dc90` и
`8b68843` обычным merge. Статус: **review в ветке; личное включение и полная
приёмка этапа 3 ещё не выполнены**. В main исполнитель ничего не вливал.

## Что сделано

- `harness_learning.py`: только через `HarnessHost.opencode` читаются `/session`
  и `/session/{id}/message`. Сбор — завершённый обычный текст пользователя и
  законченных ответов агента; не reasoning, файлы, tool parts, synthetic context,
  ошибочные ответы или черновики. Исходный возраст текста сохраняется для TTL.
- Запись через `MemoryService`: типы из опубликованного `harness_memory`,
  стабильные внешние идентификаторы источников и `Episode.operation_id` с
  `harness-`. Повторный проход и потеря курсора не создают вторую память.
  Фиктивных Job/Utterance/ACK старого пути нет.
- Слова пользователя — `third_party_message`, слова модели — `model_proposal`;
  TEST — `simulation`. Название типа `harness-operator-message` не подтверждает
  личность автора и не выдаёт прав. Эпизод подтверждает факт сохранённого
  разговора, **не получение ответа человеком и не выполнение названных моделью
  действий**. Его описание явно сохраняет это ограничение.
- Флаги источника: читать можно; `public_disclosure=False`; передача в API
  определяется существующим явным `private_api_budget.memory_processing`,
  не текстом разговора. Без этого согласия источник не становится входом модели.
- Курсор в `data/harness/learning/<partition-digest>.json`: ID, SourceRef, версии,
  хэши, исходы и пометки; текста беседы в нём нет. Память остаётся у владельца
  SQLite и его индекса. Независимый deletion ledger обязателен. Удалённые
  идентификаторы не регистрируются заново после потери курсора.
- `LearningPart.notices(scope)` возвращает
  `{native_session_id: SessionNotice(reason, sources, complete)}`. Причины:
  `source_unavailable`, `message_changed`. До 200 точных исходных SourceRef;
  при неполном списке `complete=False`. Read-only сверка источников/версий/прав,
  TTL и ledger работает и при STOPPED, без обращения к API OpenCode.
- `harness_autonomy.py`: будильник из существующего `HarnessWakes` направляется
  в native-сессию. Если адресат не задан, выбирается последняя неархивная сессия
  данной личности; помеченные LearningPart сессии для нового вызова исключены.
  Если подходящей сессии нет, будильник ждёт — разговор сам не создаётся.
- Есть проверки ACTIVE, OPEN, автономного режима, WORK, тихих часов, денежного
  остатка и числа пробуждений в час. Окончательный денежный отказ — у шлюза;
  нового цикла вокруг модели, Job lease или покомандного допуска нет.
- До POST владелец атомарно закрепляет partition, native session и message ID.
  После timeout/обрыва — только GET с проверкой того же user message ID в той же
  сессии, **без повторного POST**. Запись `done` означает наличие сообщения в
  истории, а не успешное завершение работы или прочтение результата.
- Оба модуля подключены через `HarnessHost.attach`. Синхронный tick не ожидает
  I/O: запускается одна async-задача с ограниченной частотой. Close отменяет и
  дожидается её; новый START создаёт свежую привязку к эпохе. Сам START модули
  не вызывают. Для этого пути отключён старый `runtime.autonomous_wake`.

## Почему изменён опубликованный порт Claude

Изначально эти файлы оставались у Claude. После первых запросов стыка оператор
явно поручил Codex сделать недостающие правки самостоятельно, затем объяснить
их Claude. Изменены `harness_wakes.py` и только ветка `wake_me`/её описание в
`harness_mcp.py`; `harness_host.py`, шлюз, runner и старый мост не исправлялись.

1. Общий `wakes.json` без partition позволял отправить напоминание A после
   переключения на B или в другой памяти. Все чтения и переходы теперь scoped.
2. Выбор «последнего разговора» должен закрепляться до POST: после рестарта
   последним может быть уже другой разговор. Session и message ID пишутся вместе
   с переходом `new → pending`; повтор не меняет адресата.
3. `set` тоже требует commit-guard под замком. MCP закрепляет исходную эпоху:
   старый вызов, ждавший замок, не проходит через STOP→START той же личности.
4. Критическое сохранение `pending` использует tempfile, flush/fsync, atomic
   replace (на Linux также fsync каталога). Сбой flush не меняет старое состояние.
   Это не доказательство аппаратной устойчивости при отключении питания.
5. UTF-8 размер проверяется **до** замены: владелец не записывает файл, который
   превышает его собственный предел чтения 4 МиБ.

Сигнатуры `set/due/pending/recent_count/get/reserve/delivered` требуют `scope`;
`set` требует `guard`, `reserve` — ещё native session и message ID.
Все production-вызовы этого порта в данной ветке обновлены. Старые записи без
partition сохранены, но не исполняются: их принадлежность нельзя угадать.
Автоматической миграции личных напоминаний не выполнялось.

## Проверки

Только короткий затронутый набор на Windows, Python 3.14, вымышленные данные:

- `pytest -q tests/harness`: **27 passed**, примерно 11 секунд.
- Ruff по пяти затронутым production-модулям и harness-тестам — чисто.
- Strict mypy по пяти production-модулям с `--follow-imports=silent` и явным
  MYPYPATH текущего checkout — чисто. Это не полный typecheck проекта.
- Настоящие SQLite/MemoryService: источники, один эпизод при повторе/утрате
  курсора; новые сообщения после STOP→START; вход в существующий
  `memory_cycles.pairs` без Job; отзыв права закрывает этот вход.
- Длинная/старая запись не выдаётся за полный импорт и не задерживает другие
  свежие сообщения/сессии. Нет импорта reasoning/tool/file частей.
- Настоящий HarnessWakes на локальном файле: A/B и WORK/TEST изолированы,
  зафиксированный адресат переживает перечитывание, гонка STOP под замком,
  STOP→START у старого MCP-вызова, отказ oversized save/flush без порчи файла.
- Неизвестный POST, смена последней сессии и повторный сбор/доставка проверены
  синтетическим native API. Бюджет, тихие часы и hourly cap проверены без модели.
- Узкое независимое ревью STOP/replay/retention проведено; выявленные замечания
  исправлены и получили регрессии. Полного gate не запускалось.

Первый запуск SQLite-тестов в ограниченной среде завис; остановлен. Короткий
набор затем запускался с доступом к отдельным синтетическим каталогам runtime.
Также исправлены два первоначальных падения: краткий Windows sharing violation
при replace (ограниченный повтор до 60 мс) и неверное ожидание теста о видимости
уже удалённого Source. Личная БД, сообщения и `.env` не читались.

## Честные ограничения и следующий шаг

1. **Проекция/панель пометок остаётся за Claude.** Вызвать опубликованный
   `LearningPart.notices(scope)` и показать предупреждение с предложением нового
   разговора. Готового UI в этой ветке нет. Пометки покрывают импортированные
   сообщения. Источники, ранее выданные MCP в контекст модели, без привязки их
   выдачи к native session автоматически сопоставить нельзя — нужен следующий
   стык MCP/контекста. Не заявлять, что удалённое исчезло из истории OpenCode.
2. **Обновление брифа:** существующий `platform_persona_brief(topic)` проверяет
   актуальную память при вызове; prompt уже рекомендует его в начале новой
   задачи. Принудительный refresh для каждой native-сессии не реализован и не
   доказан поведением настоящей модели. Это согласовать при интеграции с Claude.
3. **Живая приёмка Windows/Docker не выполнялась.** Ни контейнеры, ни API модели
   в рамках этой задачи не запускались. Перед личным включением нужен короткий
   сценарий на отдельном root: native-текст → память, повтор без дублей,
   `wake_me` → сообщение → STOP → START, отзыв источника → предупреждение.
   Платные вызовы требуют отдельного разрешения/бюджета.
4. Не проверялся полный extract/consolidate/reflect с моделью. Проверен доступ
   к обычному входу цикла памяти через `pairs`; качество извлечения/развития и
   реальное чтение брифа моделью этим не доказаны.
5. Пределы первого сборщика: до 200 сессий, 2000 сообщений за ответ API,
   10000 импортированных ID и 10000 помеченных пропусков. Текст сообщения свыше
   16000 символов не обрезается: metadata `skipped=text_limit`, фиксированный
   код в журнале; последующие записи продолжают собираться. Курсор до 8 МиБ.
6. Проверялся рестарт процесса/неопределённый POST, **не восстановление старого
   backup** и не аппаратное отключение питания. Restore не должен откатывать
   подтверждённую резервацию в `new`; сверка receipt с историей native-харнеса
   и политика устаревших будильников — отдельный gate до такой эксплуатации.
7. Личный deployment, launcher, образы и host-конфиг не менялись. Развёртывание
   только после STOP оператора и его «обновляй»; после запуска — STOPPED.
