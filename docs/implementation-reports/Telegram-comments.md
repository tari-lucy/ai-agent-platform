# Комментарии собственного Telegram-канала

2026-10-31. Назначение оператора: дать личности читать комментарии и отвечать.
База main `be605f6`; ветка `codex/telegram-comments`.

## Поставка

- `platform_channel_comments(after=0, limit=20)` получает комментарии с привязкой
  к посту: comment_id, post_id, дата, текст и Telegram-идентификатор автора.
  next_after используется при следующем чтении. more_updates означает, что
  в Telegram может оставаться следующая порция; more_cached — локальная страница.
- `platform_channel_reply(comment_id, text)` отвечает на конкретный комментарий
  в связанной группе, через reply_parameters и allow_sending_without_reply=false.
- Включение отдельно от публикаций: configure-harness --channel-comments;
  выключение — --no-channel-comments. По умолчанию выключено. Удаление канала
  также выключает комментарии. Инструменты не требуют новой сборки контейнера.
- В описании рабочего места объяснены инструменты, курсор, недоверенный характер
  слов аудитории и возможность самой поставить wake_me для следующего чтения.
  Новых принудительных циклов модели и автоматических ответов на каждый комментарий нет.

## Границы

- Только настроенный канал и его взаимно связанная supergroup. Проверяются
  getChat, getMe и getChatMember. Бот должен быть администратором группы либо
  участником с выключенным privacy mode. Права проверяются ещё раз после
  модерации перед отправкой. Другие группы, личные сообщения и боты не выдаются.
- Сервис закреплён за partition личности при установке; другая личность/TEST
  не получает его данных. Имена пользователей не склеиваются с другими людьми.
- Запросы идут через уже настроенный Telegram SOCKS. Новых сетевых портов,
  прокси и передач секретов в контейнер нет.
- При существующем webhook отказ TELEGRAM_WEBHOOK_IN_USE. Webhook не удаляется;
  allowed_updates не меняется. Этот бот должен иметь одного получателя updates:
  нельзя параллельно запускать getUpdates в n8n или другом приложении.
- Получение по запросу инструмента, порциями до 20 Telegram updates. Бот не
  предоставляет полного архива прошлых комментариев. Ветки, для которых бот
  не получил корневую пересылку или связь с постом, не угадываются.
- Один локальный владелец operational inbox, cursor и receipts в
  data/harness/comments-<partition+channel hash>.json. Порция сохраняется атомарно
  до подтверждения Telegram на следующем чтении. Повторы update_id не дублируются.
- До 1000 комментариев за 7 дней и 1000 корней. До 5000 квитанций ответов; по
  исчерпании отказ RESOURCE_BUSY, квитанции не выбрасываются ради повторной отправки.
  Это не новый реестр долговременной памяти. Тексты и авторы в Git не попадают.
- Перед публичным ответом работает прежний модератор и общий бюджет. Он видит
  комментарий как контекст и точный ответ. Отказ закрывает отправку.
- Epoch/STOP проверяются перед чтением, сохранением и отправкой, а также после
  получения данных. Сначала сохраняется pending-квитанция; после неизвестного
  исхода она блокирует даже перефразированный повтор. Успех сохраняет message_id.
  Рестарт не повторяет публикации. Telegram не сообщает об обычных удалениях:
  перед отправкой существование цели дополнительно проверяет сам sendMessage;
  незаметно отправить ответ без удалённой цели запрещено.

## Включение на личном host

Нужен STOP и остановленный сервер. Сохранить host.json, обновить checkout и выполнить:

```powershell
python -m ai_agent_core.local_host configure-harness --root C:/abs/host --channel-comments
```

Запустить сервер, проверить STOPPED. После START личность сама выбирает момент
чтения/ответа. Для первой пробы оператор оставляет новый комментарий под постом
и просит личность прочитать его. Историю до добавления бота не обещать.

Не проверено на этой поставке: платный ответ модели, публичная отправка нового
комментария, долгий live soak. Ни один тест этого не требует.

## Личное включение — 2026-10-31

После подтверждения оператора проверен STOPPED, сохранены прежний SHA,
launcher и host.json в локальном каталоге operations. Deployment обновлён до
`c3f8562`; штатной командой включён только channel_comments. Сравнение нормализованных
конфигураций подтвердило, что остальные настройки, включая текущий бюджет,
не изменились. Образы, панель и зависимости не пересобирались.

Сервер перезапущен: панель и вход отвечают 200, состояние STOPPED. Проверка
настоящим ботом подтвердила доступ к связанной группе и отсутствие webhook.
Операторский getUpdates без offset прочитал 3 обновления; подходящих комментариев
в этой порции — 0. Очередь не подтверждалась и не очищалась, тексты и авторы
не выводились. Guard агента для этой диагностики не подменялся.

Отправка реального ответа и полный путь с новым комментарием аудитории остаются
для первого использования после явного START. Платных вызовов и публичных
тестовых сообщений при включении не было.

## Исправление потока владельца — 2026-10-31

Первый живой вызов вернул MCP -32603. Технический traceback подтвердил
CONTROL_OWNER_THREAD_REQUIRED: дополнительная проверка current() внутри poll/send
выполнялась в asyncio.to_thread и обращалась к Supervisor.snapshot не из потока
его владельца. Повторный START это не исправляет. Прежние синтетические проверки
с простым snapshot не воспроизводили требование потока.

Проверка перед worker I/O теперь передаётся основному event loop через
run_coroutine_threadsafe. Сама сеть остаётся в worker; проверка не отключалась
и не заменялась снимком устаревшей эпохи. При недоступном/закрытом loop или
отмене вызова действие не запускается. Ожидание допуска ограничено 5 секундами;
при таймауте сеть не вызывается, возвращается RESOURCE_BUSY.

Новая регрессия заставляет current() отклонять чужой поток и проверяет оба
маршрута, чтение и отправку. Комментарии + публикации: **19 passed, 1.21 с**;
Ruff и strict mypy изменённого модуля — чисто. Платных вызовов и публичных
проверочных ответов не было. Включение требует штатного перезапуска после STOP.
