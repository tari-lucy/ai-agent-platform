# OC: заранее подготовленная одноразовая песочница

Дата: 2026-10-25. База: `5d8d395`. Поручение оператора: попробовать прогретый OpenCode, сохранив память, безопасность и STOP; экономные affected-проверки, commit/push. Ветка: `codex/opencode-prewarmed-sandbox`.

## Реализация

Подготовка одного пустого headless OpenCode в существующем pinned-образе, без новых зависимостей и пересборки image. Это не сохранение старого native-разговора: готовый backend принимает ровно один ход и удаляется целиком. Между ходами контекст заново выпускают владельцы личности, памяти, файлов и тикетов платформы.

Прогрев opt-in: host `work_sessions.prewarm_enabled=false` по умолчанию, `prewarm_idle_seconds=120` (10–300). Offline enable-work-sessions принимает `--prewarm` / `--no-prewarm` и `--prewarm-idle-seconds`; при отсутствии этих флагов текущие значения сохраняются. Права не выдаются, модель и публичные схемы контрактов не меняются.

После START и при готовой capability/automatic Permission idle runtime запускает пустую песочницу. Внутри — только configuration, loopback facade, MCP и пустые рабочие каталоги. В ней нет канона, памяти, текста разговора, host mounts, внешней сети, портов хоста и ключей. До activation host не обслуживает модельные запросы: подготовка не может создать оплаченный вызов. После готовности следующий ход получает обычный свежий допуск, inputs и инструкцию. Запросы модели/инструментов идут через прежние stdio gateway и бюджет; native HTTP server остаётся только внутри network=none контейнера.

После хода backend/MCP/потомки уничтожаются, output проходит прежнюю проверку и временный staged-кэш с release guards. Для cold и warm используется один collector файлов (symlink/hardlink/size/count/path guards), выделенный из прежнего ENTRY без изменения правил. К модели/инструментам и результату остаются свежие проверки версии, ACL, TTL, ledger и epoch.

Если готовой песочницы нет, не ждём окончания загрузки: отменяем подготовку, подтверждаем удаление и идём холодным путём. Новый прогрев не запускается во время `_active`; cold не стартует рядом с недоготовленным warm. Ожидающий процесс занимает RAM в уже заданном memory_mb; это не дополнительный безлимитный pool.

## STOP и cleanup

Warm зарегистрирован отдельным ресурсом Supervisor под observation admission. Дешёвый fence проверяется каждые 100 мс независимо от медленного readiness/refresh. Обновление Admission берётся по текущему id/scope/freshness, не по устаревшему объекту. STOP, смена epoch/области, завершение serve, истечение idle и ошибка подготовки требуют реального удаления. После claim ресурсы прогрева и конкретного задания закрываются только своими receipt.

Claim отвергает умерший процесс, чужой template, другие limits/network и почти истёкший idle. Перед передачей inputs повторно сверяются реальные параметры задачи и срок handoff (5 секунд). После claim очередь не переиспользуется.

Docker create исполняется отдельной shielded task. При отмене нужно дождаться её завершения перед remove: убитый CLI сам по себе не отменяет запрос daemon. Неопределённость отмечается ДО отправки create и снимается только подтверждённым успехом. При неизвестном исходе первое отсутствие в ps не закрывает ресурс; требуется exact-label instance для удаления, иначе OUTCOME_UNKNOWN. Повторная отмена также fail-closed.

Узкий независимый read-only review второго исполнителя по doc27 §8.7 выявил гонки STOP/refresh, лишний параллельный контейнер, claim/handoff и поздний create. Они исправлены; reviewer после повторного просмотра не нашёл другого конкретного обхода в затронутой цепочке. Это не сертификация всей системы. Детерминированные тесты проверяют выявленные порядки.

## Проверки и замеры

Все данные вымышленные, API синтетический; Docker Desktop и OpenCode 1.19.3 настоящие. Личная память не использовалась в проверках, платных вызовов нет.

- Реальные normal/STOP/revoke-пробы warm backend и production launcher с двумя ходами, ACK, STOP и restart: **4 passed**, 81,78 с на промежуточной ревизии. Поздний ответ после STOP отвергается ContractError, после отзыва не выпускается. До activation каталог inputs пуст и вызовов модели нет.
- Итоговый affected-набор: lifecycle, harness parser, launcher/permission, холодная sandbox isolation и production warm launcher: **16 passed**, 219,92 с. После второго ACK дополнительно готовится idle sandbox; STOP подтверждает её удаление. В запросе второго хода есть прежние вопрос/подтверждённый ответ и новая реплика. После restart — STOPPED и новых вызовов нет.
- Отдельная финальная проверка настоящего workspace MCP через warm backend и быстрые lifecycle-регрессии: **7 passed**, 10,57 с. После последней правки fail-closed create отдельно повторён весь быстрый lifecycle-файл: **7 passed**, 1,73 с, включая двойной cancel. Ruff всех изменённых Python-файлов и strict mypy **297 source files** чистые. Diff проверен.
- Первый warm setup упёрся в 35-секундный deadline: ожидание health ограничено отдельной короткой пробой, не полным временем хода. Диагностика проводилась только по техническим данным пустого временного контейнера. Первые тестовые ожидания STOP исправлены под существующий fail-closed ContractError; enforcement не менялся.
- Полный pytest/браузерный gate не повторялся: native UI и web contracts не менялись. Нет новых платных проб, зависимостей, образов или расширения Permission.

Парное измерение внутри одного production-host сценария, мгновенная синтетическая модель:

| Интервал | Время |
| --- | ---: |
| Холодный runner первого хода | 9,372 с |
| Готовый warm runner второго хода | 5,109 с |
| Новая реплика → готовый draft (второй ход) | 13,996 с |

Runner в этой паре быстрее примерно на **45,5%**; это один диагностический запуск, разные по размеру контексты и не SLA. Остальное время — работа платформы вокруг runner. Реальная модель добавляет свою задержку. В отдельных минимальных warm-пробах activation → первый модельный запрос: 1,2–1,8 с. Эти интервалы не складываются с таблицей.

Подготовка по-прежнему требует времени и ресурсов, но выполняется до реплики. Первый ход после START, реплика раньше готовности или после idle TTL могут пройти холодно; отмена подготовки/подтверждение удаления также стоят времени. Отказ Docker остаётся честным отказом/unknown, а не обходом изоляции. Более долгоживущий процесс с приватными сессиями не реализован.


## Границы поставки

Сборка UI/образа не требуется, используется тот же доверенный pinned image.
Windows/Docker проверены; Linux-прогон этой новой ветки не повторялся. Сбой всего
процесса/daemon с неопределёнными ресурсами требует существующей сверки исхода;
не утверждается автоматическое восстановление из любого crash. Прогрев не
разрешает START после restart и не обходит неподтверждённые ресурсы Supervisor.

Один запуск affected был отклонён автоматической проверкой разрешений из-за
лимита сервиса — команда не выполнялась. После возобновления оператором набор
запущен штатно, без обхода review. Дополнительных платных действий нет.
