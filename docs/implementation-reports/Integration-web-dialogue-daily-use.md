# Веб-диалог для повседневного использования

Дата: 2026-10-15. Исполнитель: Claude Code. Ветка `codex/web-dialogue-daily-use`, база
`origin/main` f375e66 (после приёмки private-dialogue-memory-quality). Старая feature-ветка не
продолжалась. В main ничего не сливалось.

## Что выяснено про API (важно)

Список `GET /api/v1/{sources,utterances,deliveries,operations,briefings}` идёт **по id записи**
(`repository.list(after_id=cursor)`), а `next_cursor` — это последний id страницы. Ids — хэши
(`derived_id`), поэтому первая страница **не** «последние сообщения», а курсор не «ранее/позже по
времени». Панель этого не предполагает: она читает страницы по курсору до выбранного бюджета,
собирает хронологию по `occurred_at`/`created_at` и сообщает, полна ли история. Прямой SQL, второй
журнал и подмена маршрута не использовались.

## Что сделано (`apps/panel/src/ui/dialogue/**`, `shared/api.ts`)

- `shared/api.ts`: только необязательный `cursor` у `inbound/utterances/deliveries/operations/
  briefings`, через прежний `#read` с прежним валидатором и сигналом.
- `history.ts`: `walk()` читает до 4 страниц (по 50) автоматически, дальше — по кнопке до жёсткого
  предела 40 страниц. Повторяющиеся id считаются одной записью; курсор, который не продвигается,
  и ошибка страницы после первой дают явную ошибку, а не «конец истории». Первая страница с
  ошибкой отклоняет чтение целиком. Каждый проход идёт от начала, поэтому запись, добавленная
  между страницами, попадёт в следующий проход; пропуск постоянным не бывает.
- `Timeline.tsx` + `scroll.ts`: прокручиваемая лента, которая удерживает якорную запись на
  прежнем расстоянии от верха (подгрузка старых записей вставляет их в любое место хронологии),
  следует за концом только если читатель внизу, иначе показывает «Новые сообщения: N ↓». Одна
  временная строка потока в конце ленты; скрывается, когда окончательный ответ уже в ленте.
- `Dialogue.tsx`: статус истории («вся загружена» / «загружено до N страниц, более ранние есть» /
  «часть не загрузилась — это не конец»), баннеры «Нет связи» и «Данные могут быть устаревшими»,
  перечитывание (только чтение) при `online` и возврате во вкладку, опрос только пока у ядра есть
  открытая операция или 60 с после отправки. START автоматически не выполняется.
- Путь сообщения (`messageProgress`): принято → обрабатывается → ответ готов, либо ошибка /
  отмена / исход неизвестен — только из квитанции, проекции операции и сохранённого ответа.
  Отсутствие строки проекции означает «статус уточняется», а не ошибку.
- Потеря сети при отправке: прежняя логика сохранена и проверена — поле ввода не теряется, новый
  `request_id` не создаётся, «Проверить исход» повторяет ту же команду (ядро возвращает
  квитанцию), автоматических повторов нет. Ничего не пишется в localStorage.
- ACK: единственная чистая функция `mayAcknowledge` — видимая вкладка, ≥60 % записи в
  viewport ленты, WORK, ACTIVE/OPEN, тот же run, финальная точная редакция, новейшая revision, ещё
  не доставлено, чтения здоровы (включая полную загрузку deliveries). Одна автоматическая
  попытка на (id, revision); при ошибке остаётся ручная кнопка.

## Не проверено / ограничения

- **До меня падают на чистом origin/main** в этом окружении: `test_private_runtime.py::
  test_real_private_message_receipt_and_stop` и `test_local_host_runtime.py::test_local_host_
  browser_login_dialogue_stop_and_restart` (таймауты ожидания; причину не исследовал). Их
  сценарий с «ответом за краем экрана» (`margin-top: 200vh`) теперь иначе взаимодействует с лентой,
  которая следует за концом: в моём сценарии «вне экрана» достигается прокруткой вверх.
- Лента показывает не более 40 страниц × 50 записей на ресурс. Для действительно длинной истории
  нужен API «последние → более ранние» (запрос ниже).
- Потоковая строка и поздний stream после STOP проверены чтением кода и прежними тестами
  `appendPreview`, браузерной проверки stream в этой задаче нет.
- Незавершённая отправка после **перезагрузки** страницы не восстанавливается (черновик и команда
  намеренно не сохраняются): пользователь видит в ленте, дошло ли сообщение, и решает сам.
- Windows и мобильная ширина не проверялись. Если автоматическое подтверждение прервано обрывом
  связи, задание в ядре остаётся открытым, пока не придёт ACK (ручная кнопка), и STOP показывает
  «Останавливается» до его завершения — это поведение ядра, не панели.

## Запросы владельцам

1. **Координатору / backend (маршрут чтения, самый важный).** Нужны «последние записи, затем более
   старые». Минимум: `GET /api/v1/{sources|utterances|deliveries}?order=desc&limit=50&cursor=…`
   с сортировкой `(occurred_at|created_at DESC, id DESC)` и курсором — непрозрачной парой
   `(время, id)` последней записи; новая запись не сдвигает уже отданные страницы (строгое
   сравнение по паре); `complete=true` только когда страниц больше нет. Проверка: вставить запись
   между страницами и получить каждую ровно один раз; перемешанные id/время.
2. **Координатору.** Поиск доставки по `utterance_id` (`GET /deliveries?utterance_id=…`), чтобы
   автоматический ACK не зависел от полной загрузки всех доставок в длинной истории.
3. **Координатору (shell, `Workspace.tsx`).** Передавать состояние WS-соединения в экран диалога
   (сейчас оно только в шапке), чтобы статус «связь потеряна» показывался и в самом диалоге
   без собственной эвристики `navigator.onLine`.
