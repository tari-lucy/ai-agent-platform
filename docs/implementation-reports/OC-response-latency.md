# OC: задержки рабочего ответа

Дата: 2026-10-25. База: `47e49ec`. Ветка: `codex/opencode-latency`.
Поручение оператора — ускорить общение, не менять модель, память и права.

## Диагностика

У двух последних наблюдавшихся личных ходов было около 59 и 106 секунд между
созданием и завершением WorkAttempt. В этих временных интервалах модельные
запросы занимали суммарно около 17 и 54 секунд (2 и 5 вызовов). Это интервальное
сопоставление, а не сквозная трасса; подробности — OC-session-list-and-title.md.

Для отделения платформы от сети использован существующий сценарий
`tests/workplace_harness/test_workspace_host.py`, параметр True: настоящий
OpenCode/Docker, production owners/SQLite/ledger, синтетический мгновенный
HTTP-провайдер. Четыре ответа модели, запись/чтение заметки, обращение, lineage
и ACK. Личная память и настоящий провайдер не используются.

Временная инструментальная обёртка измеряла elapsed time методов; времена
вложенных/параллельных методов нельзя складывать. Контроль до правки дошёл
только до одного вызова модели и одного инструмента: sandbox исчерпал свои
45 секунд, runner с очисткой занял 49,4 секунды. За это время фоновые и
граничные `_verify` вместе выполнялись 89 раз, занимая суммарно 44,2 секунды;
`tools` — 155 раз, 51,1 секунды (эти интервалы перекрываются).

С паузой между фоновыми проверками весь исходный сценарий проходит: runner
40,8 секунды, четыре вызова, три инструмента, ACK и чистые ресурсы. После
параллельных чтений — 33,8 секунды, то есть ещё примерно на 17% быстрее.
Полный тест с созданием/настройкой хоста — 71 и 61 секунда соответственно;
это не время ответа пользователю. До/после — одиночные прогоны на одной машине,
не статистический SLA. Нельзя сравнивать оборванный контроль с полным сценарием
как доказательство фиксированного кратного ускорения.

Отдельный сценарий обычного ответа
`tests/workplace_launcher/test_real_launcher.py` также прошёл: настоящий
launcher/OpenCode, один мгновенный модельный ответ без инструментов,
ACK/STOP/restart. Runner — 10,7 секунды. Это часть пути ответа, а не полная
live-задержка; время настоящего провайдера добавляется отдельно.

## Изменение

- Монитор sandbox больше не запускает полное чтение прав/источников сразу
  после завершения предыдущего. Пауза по умолчанию 1 секунда; настраивается
  `work_sessions.monitor_interval_seconds`, диапазон 0,1–1 секунда, и аргументом
  offline `enable-work-sessions --monitor-interval-seconds`.
- Дешёвая проверка epoch/STOP и deadline остаётся в цикле 100 мс, в том числе
  во время медленного доказательства. Время самой полной проверки не входит
  в паузу; это не обещание отмены прав за строго одну секунду.
- Перед моделью, инструментами, файлами и выдачей результата прежние полные
  проверки выполняются свежими, независимо от интервала монитора. Нет кэша
  Permission, TTL, ledger или успешного доказательства для следующего действия.
- Независимые чтения manifests/bindings/permissions и контекста допуска идут
  параллельно через прежние repository/ACL-проверки. Для не-GM задач убрано
  второе чтение GM, которое использовалось только условием kind == gm;
  версия правил по-прежнему проверяется в контексте любого допуска.
- Проверки нескольких источников в release и Execution.verify читают их
  ограниченными порциями по четыре. Сохраняются все источники и проверки
  владельцев; нет сокращения истории, кэша, пропуска версий/TTL/ledger или
  неограниченного числа фоновых задач. Это сокращает последовательное ожидание
  IO при росте истории, отдельно от частоты монитора.

Меняются host config/composition и sandbox adapter. Нет новых зависимостей,
миграций, API-контрактов, ослабления прав или сокращения памяти/характера.
Образ Docker и native UI пересобирать не нужно.

## Проверки и ограничения

Новые тесты контролируют частоту фоновых доказательств, независимый STOP,
повторную проверку отзыва без действий, свежий отказ на границе действия
внутри интервала и границы настройки. Тест на девяти настоящих источниках
проверяет ограничение параллельности, повторное чтение без кэша и отказ по ledger.
Strict mypy десяти изменённых модулей и Ruff прошли.

В затронутом наборе сначала 27 passed, 1 failed: тест восстановления/отзыва
контекста получил 403 в конце TTL-сценария. На чистом main `47e49ec` этот
длинный тест отдельно прошёл за 69 секунд. Исследование выявило гонку чтения:
между первым get(session) и entries() владелец мог перевести session в invalidated;
entries() тогда правильно отказывал, а API возвращал 403 вместо терминального
состояния. Новый тест принудительно воспроизвёл этот порядок и упал до исправления.

API теперь перечитывает session только при таком отказе: если тот же владелец
вернул invalidated, отдаёт актуальные метаданные без сообщений/черновика.
Любой иной отказ/чужая область остаётся отказом. Это не выдаёт текст закрытых
источников, не меняет owner-состояние и не запускает модель. После этой правки
повторён только файл отзыва контекста: 3 passed (90 секунд), включая новую
детерминированную гонку, полный TTL-сценарий и отзыв во время ответа модели.
Дополнительный strict mypy изменённой API-проекции также чистый.
Полный gate не повторялся.

Живых платных запросов в диагностике нет. Влияние на реальную переписку с
API Token ещё оценивается оператором: модель и количество выбранных ею
инструментальных шагов могут оставаться главным временем ответа. Полученные
33,8 секунды относятся к сложному ходу с тремя инструментами и мгновенной
моделью, не к короткому приветствию и не к гарантированному времени live.

Вспомогательная CPU-проба чтений отработала, но её TemporaryDirectory cleanup
получил Windows file-lock на закрываемой synthetic SQLite. Она не используется
как успешная приёмка; личный host и файлы других процессов не удалялись.
