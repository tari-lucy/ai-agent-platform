# Windows: live API, длинный ход и финальный STOP

Дата: 2026-10-28. База платформы `d7600ed`, отдельный checkout и новые test host.
Продолжение [синтетической проверки lease](Windows-long-turn-lease-d7600ed.md).
Оператор разрешил сначала до трёх paid calls, затем отдельный повтор до двух
дополнительных (общий предел до четырёх). Выполнено **четыре**, по два на host.

Код платформы, личный deployment, его память, права и настройки не менялись.
API-конфигурация используется обычным provider_factory из существующего локального
env-файла; значения ключа/endpoint не просматривались и не выводились. Провайдер
настоящий, модель текущего запуска `claude-sonnet-4-6`. Профиль — публичный пример
из Git, все сообщения и данные вымышленные. Личной истории в запросах нет.

## Метод

Новый init → tickets/activity/recovery/files → home+resident+internet с pinned
hands-образом → initial access через обычные preview/execute на test scope →
один рабочий разговор → START → один foreground bash `sleep 240` с маленьким
файлом-маркером → ответ → чтение точного маркера → ACK → STOP → закрытие app.
Интернет-заданий модели нет. Нет браузера, загрузки архивов или иных аккаунтов.

Ограничение запросов — в AsyncBaseTransport до обращения к сети, а не только
в prompt/role budget. Redirects и транспортные retry выключены. Unit-тесты
подтверждают caps 2/3: следующий запрос не достигает даже MockTransport.
В отчёты идут только счётчики, HTTP status/время заголовков, фиксированные
диагностические коды и наличие маркера. Тексты ответов не включены.

## Результаты

| Проба | stream_tools | HTTP timeout | Paid calls | Длинный ход | HTTP headers, с |
| --- | --- | ---: | ---: | --- | --- |
| A, предварительная | true | 120 с | 2 | reply_ready, 283.804 с | 5.354 / 5.487 |
| B, как текущий запуск | false | 300 с | 2 | reply_ready, 287.990 с | 13.294 / 4.401 |

В обеих пробах выполнен один tool step, проверено точное содержимое собственного
файла-маркера после ожидания 240 секунд. В пробе B явно установлен keep-alive
120 с. Проба A использовала default stream_tools=true и не копировала все
параметры HTTP текущего host: различие обнаружено после неё, оператор уведомлён,
повтор B отдельно согласован. Выдавать A за точное повторение личного режима нельзя.

**JOB_LEASE_EXPIRED / JOB_RENEW_FAILED не воспроизвелись.** В live-логах обеих
проб нет Slow job lease renewal, Slow runtime tick step, Job admission lost,
Resource lease cancelled, Event loop blocked или Runtime tick failed.

Однако обе пробы дали одинаковую другую диагностику:

```text
LIVE_LOG Run faulted: STOP deadline with 1 unconfirmed resources
```

После закрытия app на каждом test host Job — SUCCEEDED, RunSession — FAULTED,
unconfirmed_resource_ids — пуст. Последний ранее неподтверждённый warm-aw-task
контейнер проверен через docker ps --all с точным именем: его уже нет.
Ресурсы освобождены, но FAULTED остаётся. Это отдельный воспроизводимый случай
завершения STOP, а не исходная потеря lease во время работы.

Первый вариант пробника оценивал success только по ответу и маркеру, поэтому
в raw result A success=true. Этот вердикт не учитывал финальное состояние.
Критерий исправлен только в пробнике: turn_success отдельно, общий success
требует STOPPED и ноль неподтверждённых ресурсов. Проба B честно завершилась
exit 2, turn_success=true, success=false, final_state=FAULTED. Платформа не правилась.

## Ограничения и следующий узкий эксперимент

Пробы подтверждают маршрут реального API, длинный tool wait, ACK и работу lease
на новых небольших host. Они не повторяют личную БД (~21.7 МиБ), старый разговор,
объёмные материалы, фоновую память и чтения панели. Polling live-пробника — 0.5 с;
синтетический исходный until — 0.05 с. Длительности разных проб нельзя напрямую
приписывать провайдеру либо режиму stream.

Следующая бесплатная проверка для Claude: синтетический транспорт с задержкой
первых headers/чанков более 20 с и длинным stream, отдельно от bash sleep.
Тест LONG_SLEEP=20 задерживает инструмент, но отвечает моделью сразу; это разные
участки. Также нужны раздельные тайминги jobs-lock/proof/refresh/SQL save/post-check
на большой синтетической истории. Замеры headers 4.4–13.3 с не доказывают
корректность пути при более медленном настоящем ответе или большой БД.

## Поставка и проверки

- `scripts/probes/live_long_turn_lease.py`: opt-in, новый абсолютный workdir,
  обязательные consent flag и --stream-tools on|off, hard max-calls <=3 на запуск.
- `tests/windows_workspace/test_live_lease_probe_guard.py`: 5 passed без сети:
  два cap cases и три verdict cases STOPPED/FAULTED/STOPPING.
- Ruff и strict mypy по пробнику чистые. Полный suite не запускался.
- Raw logs/results хранятся только в игнорируемом runtime/checks, не в Git.

Повторять paid-пробу автоматически нельзя: два разрешённых запуска завершены,
общий согласованный бюджет четырёх запросов израсходован.
