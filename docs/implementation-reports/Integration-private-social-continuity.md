# Постоянный собеседник и точные обещания (этап 2 пула памяти)

Дата: 2026-10-19. Исполнитель: Claude Code. Ветка `codex/private-social-continuity`,
отдельный worktree от `origin/main` `638162c`. Этап 1 (`codex/long-term-memory-retention`)
ещё не принят и **не** использован: эта ветка от него не зависит. В `main` не вливалось,
рабочий host не обновлялся, платных вызовов не было.

Расширение прав SOCIAL авторизовано оператором в сессии 2026-10-19 (вариант «А»).

## Что было (проверено кодом и тестом)

1. Входной `Signal` приватного диалога не нёс ни `platform_id`, ни `account_id`. Поэтому
   `person_id = None`, а предложение обещания контроллер отбрасывал
   (`PROMISE:NO_REPLY_OR_PERSON`).
2. В приватном пути `DialogueController.settle()` не вызывается вообще. ACK пишет
   Delivery и Episode, но обещание доставленного ответа никуда не попадало, даже если бы
   `person_id` был.
3. Матрица прав хоста (`local_host/rights.py`) не давала SOCIAL ничего, а
   `record_readers()` не включал social-принципала. Поэтому `observe_account` без
   новых прав отменяет сообщение (`ACCESS_DENIED`), это воспроизведено.
4. **Дефект social-владельца:** запись хранит scope с `agent/run/session` того
   запуска, где создана, а `SocialService._write` не переносил ревизию в scope текущей
   команды. Закрыть обещание или обновить Person в **следующем** запуске было
   невозможно (`ACCESS_DENIED`). Memory- и development-владельцы делают перенос
   (`correct`, `_revised(scope)`), social — нет. Воспроизведено тестом, мутационная
   проверка: без исправления тест падает.

## Что изменено

- `m3_composition/dialogue.py`: собеседник приватного диалога — аутентифицированный
  вход панели, аккаунт `private-panel/operator`, а не имя из текста. Дальше работает
  существующий путь контроллера: `observe_account` → `record_encounter` → `person_id` →
  точные обязательства и `<person returning=…>` в контексте. Обещание ответа ждёт
  ACK этой же редакции; после `DELIVERED` его записывает `social.record_promise`
  (идемпотентно по utterance + key, в том числе при повторе ACK).
- `m3_composition/service.py`: `Runtime.pending_promises` — черновики обещаний до ACK, в
  памяти процесса, не больше 64, как `_pending` самого контроллера. Флаг
  `private_social`.
- `social/service.py`: `_write` переносит запись того же partition в scope команды.
  Чужой partition по-прежнему отклоняет storage.
- `local_host/rights.py`: SOCIAL пишет свои записи (Person/Encounter/Promise), читает
  MEMORY (основания) и CHANNEL (`DELIVERED` для обещания). В `record_readers()` добавлен
  social-принципал только на чтение. API transfer и доступа оператора к SOCIAL нет.
- `local_host/layout.py`, `init.py`, `serve.py`, `social.py`, `cli.py`: флаг
  `HostConfig.private_social`. Новый `init` выдаёт права и включает флаг. Для старого
  хоста — офлайн `enable-social`: переприменяет текущую матрицу work scope (других
  грантов там нет: их выдаёт только `init`), затем ставит флаг. Пока флаг выключен,
  приватный диалог идёт анонимно, как раньше. Обновление кода не ломает рабочий хост.

## Доработки по решению оператора (те же сутки)

Оператор попросил закрыть открытые вопросы. Каждая доработка — отдельный коммит:

1. **Отмена ответа на долгой сессии (`67cd515`).** Причина воспроизведена
   сценарием из 14 реплик (падал 5 из 5 прогонов): доказательство политики при продлении
   аренды живёт 2 с (`policy.py`, `elapsed() + 2`). Медленная запись продления в SQLite
   его «просрочивала», и `Execution.renew` отменял здоровый ответ (`STALE_CONTEXT`).
   Теперь тот же запрос продления повторяется со свежей проверкой до 3 раз (ветка
   идемпотентности по квитанции возвращает уже сохранённую аренду). Другие отказы и STOP
   отменяют как прежде: `guard()` проверяет супервизора каждые 50 мс. Unit-тест на
   подставном runtime; сценарий из 14 реплик после правки прошёл 2 из 2.
2. **Межзапусковый scope у memory-владельца (`6448ae8`).** Тот же дефект, что был у
   social. `set_rights`/`expire`/`delete` источника и, главное, ссылка противоречия на
   claim **прошлого запуска** падали `ACCESS_DENIED`, то есть извлечение не могло
   записать противоречие между днями работы. Исправлено как в `correct()`; тест
   и мутационная проверка.
3. **Связи claim→источник в индексе (`4682364`).** Фоновые задачи памяти получают
   индекс, recall видит противоречия у извлечённых claims без restore. Проверено
   в `test_private_pipeline.py` (3 связанных claim после цикла).
4. **Поле `Utterance.promise` не понадобилось.** Перед изменением контракта выяснилось:
   ACK ответа из остановленного запуска отклоняется по правилу проекта (существующий
   тест: после STOP подтверждение → 409). Неподтверждённый до STOP ответ никогда не станет
   доставленным, значит и обещания из него быть не может, где бы черновик ни хранился.
   Хранение в памяти процесса этого же запуска эквивалентно. Контракт не менял.
5. **Закрытие обещания из панели (`a7938d3`, `bbef6dd`).** Shared change с разрешения
   оператора: `EditCommand` `promise.close` + `PromiseCloseArguments`
   (`withdrawn|fulfilled|unknown`, `closure_result`), перегенерированы
   schema/OpenAPI/TS (`export --check` проходит). Обработчик через social-владельца с
   CAS версии. «Выполнено» опирается на собственные слова оператора: они становятся
   новым источником (`promise-closure`), ответ персонажа сам себя не подтверждает.
   Повторное или устаревшее закрытие отклоняется. Оператор читает people/promises:
   OPERATOR получил чтение SOCIAL, social-записи пишутся с ACL читателей. Во вкладке
   «Люди» у открытого обещания есть форма: исход, итог, сохранение; у закрытого формы нет.
   `PeopleTab` проверен в Chromium на настоящем хосте (`tests/panel/test_promise_close.py`);
   panel tsc/eslint чисто, 179 node-тестов проходят. Node 22.22.3 из nvm и
   `node_modules` соседнего worktree с идентичным lockfile подключены симлинком, ничего
   не устанавливалось.

## Ограничения и запросы владельцам

- Старые сообщения (до `enable-social`) не имеют ACL для SOCIAL и не могут быть
  основанием обещания; новые могут. Старые social-записи (если были) не видны оператору.
- Связь аккаунтов во вкладке «Люди» (`person.link/unlink`) по-прежнему UI-only: на сервере
  этих команд нет (так было с M4-03), я их не включал.
- Исправить **текст** обещания нельзя: владелец поддерживает только закрытие с итогом.
  Правильный путь — снять с причиной; модель может дать новое.
- Повторная отправка той же команды `promise.close` после потери ответа сети вернёт
  ошибку (обещание уже закрыто), хотя закрытие состоялось. Список обновится и покажет итог.
- Один оператор на хост: идентичность — логин `operator`. Для нескольких операторов
  принципал нужно передавать в `TaskInput`.
