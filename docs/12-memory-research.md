# Исследование памяти и ресурсного бюджета

Статус: исследование первичных источников и рекомендация для обсуждения.
Пакеты не установлены, локальные сравнительные тесты не запускались.
Документация проектов меняется; перед экспериментом фиксируем версии библиотек,
моделей и параметры. Результат исследования не является согласием пользователя
на реализацию или окончательным результатом проверки производительности.

## Исходные ограничения

Проверенная машина: Windows 11, Intel Core i5-12450H, 8 ядер / 12 потоков,
около 16 ГиБ установленной ОЗУ (система сообщает 15,7 ГиБ), RTX 3050 Laptop
с 4 ГиБ VRAM. Свободная память и ресурсы в совместном эфирном режиме не измерены.

Требование пользователя: память и агент не должны требовать мощного GPU.
Предлагаем базовый режим: LLM через API; память и поиск на CPU; компактная
многоязычная embedding-модель; голос через API либо измеренную CPU-альтернативу.
GPU остаётся доступен игре, аватару и кодированию. CUDA не является обязательной
зависимостью текстовой версии платформы.

## Что именно выбираем

«Память» включает разные задачи, а проекты ниже решают их в разных сочетаниях:

1. Хранение исходных событий, разговоров и ссылок на медиа.
2. Точные данные: личность, обещания, отношения, журнал вопросов, версии развития.
3. Поиск подходящих эпизодов: структурированные фильтры, слова, смысл.
4. Интерпретация и консолидация: предложения фактов и выводов по источникам.

Поиск не заменяет точный учёт обязательств. Иначе обещание может существовать
в архиве, но не попасть в top-k и не повлиять на поведение. Любой готовый движок
потребует наших правил происхождения, доступа, развития и подтверждения записи.

## Сравнение кандидатов

Оценка пригодности — вывод для нашего проекта, а не результаты собственного
бенчмарка. «Без GPU» предполагает CPU embeddings и API для необходимых LLM.

| Вариант | Основная функция | Работа без GPU / инфраструктура | Вывод для платформы |
| --- | --- | --- | --- |
| MemPalace | Архив исходных текстов, поиск, организация памяти, временные связи | Локальный CPU-режим; embedded backend, в том числе Chroma и SQLite exact | Сильный кандидат для архива разговоров; отдельный пилот, если нужен готовый слой recall |
| LightRAG | RAG по документам с извлечением сущностей и связей | GPU необязателен при API-моделях; индексация использует LLM, несколько логических хранилищ | Поздний подключаемый инструмент базы знаний, а не основной владелец личности |
| Mem0 OSS как библиотека | Извлечение и поиск полезных воспоминаний из общения | API LLM/embeddings либо настроенные альтернативы; можно без отдельного серверного стека | Кандидат на готовую консолидацию; требуется проверка качества и сохранение источников |
| Graphiti | Временной граф знаний из событий | API-модели и графовый backend; GPU не обязателен | Полезен при доказанной необходимости сложных связей, стартовая сложность выше |
| Qdrant | Векторный поиск и фильтры | CPU; embedded local или отдельный сервер | Вариант замены поискового индекса при росте; не полная система памяти |
| SQLite + FTS5 + sqlite-vec | Структурированные данные, поиск по словам и векторам | Embedded на CPU; нет отдельного сервера БД | Предпочтительная основа MVP; правила памяти остаются в нашем сервисе |

Letta также рассмотрена: это более широкий runtime агентов с памятью.
Для независимой платформы такой выбор затрагивает всю оркестрацию, поэтому
он не включён в короткий список сменных хранилищ.
Основание: [официальный репозиторий Letta](https://github.com/letta-ai/letta).

### MemPalace

Текущий официальный репозиторий описывает сохранение текстов без пересказа,
структуру wings/rooms/drawers и заменяемые backend, включая `sqlite_exact`.
Есть отдельный граф временных связей на SQLite. Это полезные механизмы recall;
они не определяют допустимое развитие нашего персонажа.
Источник: [MemPalace](https://github.com/MemPalace/mempalace).

В embedding-модуле предусмотрен принудительный CPU-режим. Англоязычный
`minilm` нельзя принимать за проверенный выбор для русского персонажа;
многоязычная EmbeddingGemma предусмотрена отдельно. Маленький файл модели
не означает такой же размер RAM: исходники отдельно учитывают batching,
число потоков и память ONNX-операций.
Источник: [embedding-модуль](https://github.com/MemPalace/mempalace/blob/develop/mempalace/embedding.py).

Python API предоставляет поиск с областью и операции временного графа.
Наш адаптер всё равно должен принудительно ограничивать личность, workspace,
тестовый режим и права, сохранять устойчивые ID источников и корректно удалять
производные данные. Возможности навигации между областями не выдаются агенту
как автоматическое право читать чужую память.
Источник: [Python API](https://mempalaceofficial.com/reference/python-api.html).

Мой вывод: стоит проверить как готовый модуль архива. Не делаем его обязательным
ядром только по рекламе качества. Опубликованные показатели retrieval recall
не доказывают правильность ответа, изоляцию персонажей, русский recall или
устойчивость личности; сам README различает несопоставимые метрики.
Это ограничение интерпретации результатов, а не наш негативный тест.

### LightRAG

LightRAG строит представление документов с сущностями и отношениями.
Извлечение использует LLM; запрос может сочетать граф и текстовые фрагменты.
Текущий README указывает, что стандартные хранилища держат набор в памяти
процесса и предназначены для небольших испытаний. API-модели снимают нужду
в локальном GPU, но не стоимость индексации и нагрузку RAM.
Источник: [LightRAG](https://github.com/HKUDS/LightRAG).

Мой вывод: подходит для библиотек описаний миров, документов и связи находок.
Предпочтительнее подключать как инструмент знания после проверки обычного
recall. Для каждого кадра или игрового тика графовую индексацию не планируем.
Локальные тяжёлые LLM, reranker и парсеры мультимедиа не входят в базовый режим.

### Mem0

OSS можно встроить библиотекой; полный self-hosted сервер — иной вариант
развёртывания. В документированной библиотечной конфигурации используются
LLM/embedding API, local Qdrant и SQLite для истории; компоненты заменяемы.
Источник: [OSS overview](https://docs.mem0.ai/open-source/overview).

Стандартная операция добавления может извлекать воспоминания через LLM;
`infer=False` сохраняет предоставленный материал без такого извлечения.
Разделение и фильтры задаются идентификаторами/metadata. Это не автоматическое
доказательство фактов и не гарантия корректного совпадения двух игроков.
Источник: [операция добавления](https://docs.mem0.ai/core-concepts/memory-operations/add).

Мой вывод: полезный кандидат, если готовая консолидация заметно улучшит наш
тестовый набор. Проверяем фактическое поведение выбранной OSS-версии, затраты
вызовов, привязку к исходным событиям и отсутствие потери важных деталей.
Сервисные defaults не переносим в проект: все провайдеры и пути задаём явно.

### Graphiti и Qdrant

Graphiti имеет временной граф, эпизоды и поиск связей. Официальный проект
поддерживает несколько графовых backend; Kuzu отмечен как устаревающий вариант.
Это не основание считать любой граф «тяжёлым GPU-решением», но его backend,
извлечение и сопровождение добавляют работу.
Источник: [Graphiti](https://github.com/getzep/graphiti).

Qdrant Python Client имеет local-режим с сохранением на диск без сервера,
но разработчики позиционируют его для прототипов и небольших наборов.
В исходниках есть предупреждение при коллекциях более 20 000 точек; это
ориентир реализации, не универсальный физический предел. Серверный режим
рассматриваем при росте и требованиях к параллельному поиску.
Источники: [клиент](https://github.com/qdrant/qdrant-client),
[local implementation](https://github.com/qdrant/qdrant-client/blob/master/qdrant_client/local/qdrant_local.py).

## Рекомендуемый выбор для MVP

**SQLite + FTS5 + sqlite-vec; CPU embeddings через FastEmbed.**
Это выбранная рекомендация по результатам исследования, ещё не подтверждённое
пользователем техническое решение. Ранее предложенный PostgreSQL/pgvector
перестаёт быть основным кандидатом первой локальной версии.

SQLite хранит события, память, версии, ссылки на источники, отношения,
обязательства и историю развития. FTS5 даёт лексический поиск.
`sqlite-vec` добавляет векторные операции в ту же среду без отдельного
сервера. Расширение написано на C, поддерживает Windows, но остаётся pre-v1:
нужны фиксированная версия и проверка совместимости.
Источники: [SQLite](https://www.sqlite.org/whentouse.html),
[FTS5](https://www.sqlite.org/fts5.html),
[sqlite-vec](https://github.com/asg017/sqlite-vec).

Один сервис памяти владеет записью; агенты, гейммастер и панель обращаются к
нему через контракт. SQLite допускает одного писателя одновременно; очереди
записи и короткие транзакции входят в проект. Для нескольких машин/большой
параллельности оценим серверную БД, а не обещаем масштабирование без изменений.
Источник: [ограничения SQLite WAL](https://www.sqlite.org/wal.html).

Индекс — производный. Основные тексты и доказательства сохраняются в обычных
таблицах, поэтому смена расширения или embedding-модели требует пересборки
индекса, а не создания биографии заново. Для MVP реализуем один backend;
заранее определённый контракт не означает поддержку всех вариантов сразу.

Связи «персонаж — обещание — эпизод — изменение отношения» тоже храним явно.
Для первых сценариев достаточно таблиц связей с временем и источниками,
ограниченного обхода и точного поиска. Отдельная графовая БД не нужна для
самого факта наличия связей; Graphiti/LightRAG подключаем, если измерения
покажут пользу более сложного графового поиска.

Собственными остаются схема предметной памяти и правила её записи/поиска;
БД, векторные операции и вычисление embeddings берём готовыми. Пересоздавать
полноценный фреймворк памяти не требуется. Вкладка «Память» и «Сюжет и развитие»
читают эти данные независимо от выбранного поискового движка.

### Embeddings и русский язык

Первый кандидат: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
через FastEmbed/ONNX на CPU. Он есть в списке FastEmbed и выдаёт 384-мерные
векторы. FastEmbed использует ONNX Runtime и не требует PyTorch для обычного
пути inference. Размер файла модели в каталоге не считаем оценкой RAM.
Источники: [FastEmbed](https://github.com/qdrant/fastembed),
[список моделей](https://qdrant.github.io/fastembed/examples/Supported_Models/).

У MiniLM в model card указан контекст 128 токенов. Длинный эпизод сохраняем
полностью, а поисковые фрагменты делаем короткими со ссылкой на исходник:
нельзя незаметно обрезать конец обещания при индексации.
Источник: [model card](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2).

Второй кандидат сравнительного опыта: `intfloat/multilingual-e5-small`.
У него 384-мерный выход; нужны предусмотренные моделью префиксы запроса и
документа, в том числе для русского языка. ONNX-артефакт, квантование и
совместимость выбранного runtime проверяются отдельно.
Источник: [E5 model card](https://huggingface.co/intfloat/multilingual-e5-small).

Фразы с ником, координатами и названиями блоков дополнительно ищутся по точным
полям и тексту. FTS5 unicode61 не решает русскую морфологию сам по себе;
нормализацию и алиасы оцениваем вместе с семантическим поиском, не включаем
английский stemmer как универсальную поддержку русского языка.

## Как сохраняем развитие и отношения

Первичное событие записывается сразу. Важные обещания и заданные вопросы
обновляют структурированный журнал в проверенной транзакции; ожидание
embedding/рефлексии не позволяет забыть уже совершённое действие.

Извлечение факта и рефлексия дают предложения с ID источников. Наш валидатор
проверяет происхождение, область, конфликт и полномочия. Гейммастер не может
записать запланированное испытание как произошедший эпизод. Изменения личности
попадают в версионируемую историю только после контроля развития.

Для общего workspace поиск сначала ограничивает личность, доступную область,
реальную/тестовую среду, время и источник. Доступ проверяется до включения
записи в контекст, а не только после глобального top-k. Сводки, векторы,
кэши, экспорт и резервные копии имеют явные правила удаления/хранения.

## Предлагаемый бюджет всего агента

Это цели проектирования, а не уже измеренная производительность:

| Компонент | Базовый режим |
| --- | --- |
| Персонаж, гейммастер, рефлексия | API; роли вызываются по событиям и расписанию с cooldown |
| Независимый модератор | Другая API-модель; приоритет проверки готового публичного контента |
| Память и embeddings | CPU; один загруженный embedder, небольшие batch, ограничение потоков |
| Игровые движение и навигация | Локальные контроллеры; LLM не вызывается на каждый шаг |
| Голос | API либо отдельно измеренная CPU-модель; один маршрут воспроизведения |
| Медиа и монтаж | Файлы и фоновые задания; рендер отложен или ограничен во время эфира |

Стартовый ориентир памяти+индексации — до 1,5 ГиБ RAM на тестовом корпусе
10 000 поисковых фрагментов; уточняем метод измерения, холодный/тёплый запуск
и пики. Векторы float32 размерности 384 сами занимают `N × 384 × 4` байта:
10 000 ≈ 14,6 МиБ; 100 000 ≈ 146,5 МиБ. Это только арифметика полезных
данных, без текстов, runtime, модели, индексов, копий и временных буферов.

Для первого эксперимента предлагаем 1 worker embeddings, 2 вычислительных
потока и batch 4 коротких фрагмента, с изменяемыми лимитами. Не держим отдельную
копию модели у каждой личности. У API — ограниченная очередь и приоритеты:
диалог и модерация опережают фоновую консолидацию/гейммастера. Частоты и
параллельность выбираем по задержкам и бюджету, а не по количеству ролей.

Локальное хранение не означает, что все данные остаются на компьютере:
выбранные воспоминания уходят в API-контекст персонажа/служебных моделей.
Нужны минимизация, разрешённые поля и правила retention провайдера. При API
embeddings передаются также индексируемые тексты; CPU-вариант избегает этого
дополнительного отправления, но не отключает остальные API-вызовы.

Нельзя обещать, что Minecraft, VTS, OBS и CPU STT одновременно уложатся в
16 ГиБ без прогона с конкретными настройками. Нагрузочный тест включает их
совместную работу; резерв ОЗУ для ОС и ручного управления сохраняем отдельно.

## Следующий эксперимент после согласования планирования

1. Зафиксировать Windows/Python/SQLite/пакеты/модель и проверить загрузку
   расширения, FTS5, сохранение после перезапуска, удаление и восстановление.
2. Сравнить рекомендованную базу и MemPalace на одном русском корпусе:
   1 000 / 10 000 фрагментов; 100 000 — только как последующая проверка роста.
3. Подготовить вопросы о людях, обещаниях, местах, противоречиях, хронологии,
   забытых/удалённых фактах и изоляции личностей. Добавить ники и перефразировки.
4. Измерить recall и точность итоговых ответов отдельно; время поиска и
   формирования query embedding отдельно; RAM/CPU/диск/пиковые batch.
5. Для извлечения/рефлексии посчитать API-вызовы и токены на сессию, проверить
   потери и неверные выводы. Mem0 добавлять в опыт только для этой задачи.
6. Проверить общую нагрузку перед игровым/эфирным этапом; при недостатке
   ресурсов ограничить фоновые задачи, выбрать другой embedder или API.

Предлагаемый ориентир recall p95 ≤ 500 мс для тёплого поиска вместе с query
embedding на 10 000 фрагментов, без генерации ответа. Это критерий для
обсуждения; данных о его достижении на этой машине пока нет.

Если sqlite-vec не пройдёт совместимость/стабильность, первая альтернатива —
MemPalace с проверенным embedded backend; при росте корпуса — серверный
Qdrant или PostgreSQL/pgvector по измерениям. Миграция требует явного экспорта
и восстановления индекса, не обещаем её одним переключателем без проверки.

## Оставшиеся решения

Подтверждаем стек совместно. До реализации уточняем сроки хранения исходных
диалогов, API-бюджет, допустимую задержку, объём корпуса, языки и работу без
интернета. Сначала выбираем надёжную память одного персонажа; автоматический
граф всей биографии и локальные большие модели не становятся обязательными.
