# Независимая модерация и выходной шлюз (M2-07)

`ModerationGate` проверяет точную редакцию `Utterance` **другой моделью** (роль `moderator`, свой
контекст, версионированная `Policy` оператора) и выпускает её только по подходящей `ModerationCheck`.

- `check`: нет допуска → `unavailable` (модель не вызывается). Модель-модератор (и все её резервы) не
  равна модели реплики; если провайдер сообщил модель реплики — `unavailable`. Локальный фильтр
  (секреты, e-mail/телефон, управляющие символы) блокирует до отправки даже модератору. Лимит
  редакций (`max_revisions + 1`). Ответ — закрытая схема `Verdict` (approve/revise/block/review,
  rule_ids из политики, fragments в границах текста). Любой сбой, timeout, отмена, невалидный или
  противоречивый ответ → `unavailable`, это никогда не «да». Жёсткое правило политики сильнее мягкого
  `revise` модели. STOP/смена поколения во время проверки → одобрения нет (`STALE_CONTEXT`).
  Результат сохраняется как `ModerationCheck`: hash/редакция/аудитория/контекст/версия политики/
  поколение управления/срок/модели.
- `verify`/`release` (единственный путь к `Publisher`): статус approved и существующая проверка с
  решением approved, та же реплика и редакция, тот же hash текста, аудитория, каналы и контекст
  (через `context_hash` вместе с digest политики), та же версия политики, срок не истёк, то же
  поколение управления (`Freshness`), независимые модели. Иначе выпуска нет, причина возвращается.
- Исправление: `revise` → новая редакция → новая проверка (старая не покрывает новый текст);
  заблокированное не становится одобренным.
- Текст черновика и предыдущая реплика — данные в тегах (разделители нейтрализуются); модератор не
  получает ни профиль персонажа, ни секреты, ни полномочия публикации.

Не здесь: Utterance/Delivery (владелец gateway), очередь ручного разбора и журнал инцидентов, изображения/
звук/видео, юридическая матрица, калибровка классификатора и реальные политики; реальная модель-модератор.
