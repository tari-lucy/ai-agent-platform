# Social memory: люди, встречи, отношения, темы и обещания (M2-03)

Модуль **не подключён к runtime**. Вызывается доверенной композицией ядра с
`Principal(core_owner, social)`.

## Композиция

1. Один `ExtensionRegistry` для store и сервиса; один раз `register_social_extensions(registry)`
   (схема `social.relationship-aspects`: значения аспектов по профилю + пожелание о контакте).
2. Grants social-владельцу: `read/write` на `Owner.SOCIAL`, `read` на `Owner.MEMORY` (проверка
   ссылок на источники в транзакции) и на `Owner.CHANNEL` (проверка доставки перед обещанием).
3. Записи MemoryService и канала, на которые ссылается social, должны иметь `RecordAccess` для
   social-владельца (`reader_access` / `access=` при записи).
4. `SocialService(store, principal, registry, clock=..., policy=SocialPolicy(...), reader_access=...)`.

## Правила

| Область | Правило |
| --- | --- |
| Личность | Только подтверждённая пара `(platform_id, account_id)` внутри области. Ник, слово, голос, тот же account_id на другой площадке/сервере (`minecraft:server-a` ≠ `server-b`) — другой человек. Нет account_id (аноним, бот) → нет `Person` и истории. Гипотеза не идентифицирует; подтверждение аккаунта, у которого уже есть свой человек, отклонено (слияние в M2-03 не реализовано). Единственную личность человека отклонить нельзя. |
| Области | Персонаж и work/test — разные партиции: те же аккаунты дают разных `Person`, отношения не смешиваются. |
| Встречи | Одна логическая встреча на `key` (сессия+человек): голос/чат одной реплики и повторная доставка не умножают её; `first_meeting`/`previous_meetings` для приветствия. |
| Отношения | Одно на пару персонаж—человек; стартуют с умолчаний профиля; `apply_aspects` версионирован (`expected_version`), идемпотентен по `change_id`, требует основание (SourceRef) и проверяет имена/диапазон. Лимиты скорости развития — M3-03. |
| Вопросы | `reserve_question`: известный ответ / ожидание ответа / чужой резерв / cooldown / закрытая тема / «не обращайся» → отказ без записи; иначе атомарный резерв (гонка задач — ровно один победитель). Ключ темы нормализуется, переформулировка не создаёт новую тему. `settle_question`: delivered → ожидание ответа + cooldown; not_delivered → тема свободна (блокированный черновик не вопрос); unknown → удержание без немедленного повтора; голос+чат одной реплики один раз. Смысловое сходство (эмбеддинги) не реализовано — только ключ. |
| Обещания | Создаются только по `Delivery` со статусом DELIVERED той же реплики; черновик/QUEUED/FAILED/UNKNOWN/чужая реплика → отказ. Одно обещание на реплику+ключ (второй канал — дубликат). Закрытие `fulfilled` требует собственного подтверждения и результата; `withdrawn` — причины; завершённые необратимы; `unknown` остаётся обязательством. Истечение 30 дней исходного текста не закрывает и не стирает обещание (SourceRef помечается expired). |
| Обязательства | `obligations()` читает хранилище целиком по страницам: полный, точный, без top-k и без recall. |
| Сбой записи | Исключение при записи не оставляет частичных записей; успех не сообщается. |

`context_for(scope, person_id)` собирает для повторной встречи: человека, отношение, пожелание о
контакте, число/даты встреч, открытые темы, известные ответы, обязательства.

## Ограничения

Поиск «аккаунт → человек» и «человек → встречи» делает сканирование записей владельца с кэшем
на область (достаточно для одного процесса MVP); см. запрос к storage в отчёте M2-03.
