# Retention owner — M5-01

Сроки хранения, удаление с tombstone, независимый ledger, restore gate и жизненный цикл
метаданных. Не подключено к composition; агент не запускает, модель не вызывает.

## Порядок любого удаления/истечения

1. Независимый ledger (отдельный файл; ID, версия, причина, время — без содержимого).
2. `revoke`: запись перестаёт выдаваться (флаги), tombstone «blocked».
3. Производные копии: индекс recall, зарегистрированные `DerivedPurger` (кэши, экспорт).
4. Физическое стирание: текст из текущей и старых ревизий, зависимые записи с единственным
   основанием, `finalize` (secure_delete, WAL checkpoint TRUNCATE, VACUUM).
5. `mark_purged` в ledger и tombstone «purged».

Сбой на шагах 3–5 оставляет источник заблокированным и `blocked_pending_purge`; `resume`
или `apply_ledger` завершают работу. Заблокированное не выдаётся ни recall, ни восстановлением.

## API

- `preview_delete(scope, source_ids)` → `DeletionPreview` (источники; производные, которые
  стираются; производные, которые остаются на других основаниях; что есть в индексе; digest).
- `delete(scope, preview)` — только если область не изменилась (иначе `VERSION_CONFLICT`).
- `sweep(scope)` — истечение сырого текста по политике (30 дн.; тестовые — предел неактивности),
  защищённые не трогает, срок не продлевает: источник без долговременного следа попадает в
  `unconsolidated` (ошибка видна). Затем метаданные: LLM 90 дн. (сначала агрегат), агрегаты
  12 мес., завершённые job-записи 30 дн. (OUTCOME_UNKNOWN остаётся), текст просроченных квитанций.
- `apply_ledger(scope)` — после restore: ledger сильнее восстановленной БД. Идемпотентно.
- `resume(scope)` — завершить прерванные удаления.

## Решения

1. Физический слой работает рядом с owner API: storage скрывает просроченные записи даже от
   владельца, поэтому retention читает/стирает их напрямую (`SQLitePhysicalStore`, только
   стирание текста, флаги и удаление целых записей-метаданных; бизнес-записей не создаёт).
2. `DeletionTombstone` не версионирован — пишутся два неизменяемых события (blocked, purged).
3. Агрегаты расхода лежат в таблицах `retention_*` той же БД (создаются явным `install()`);
   нужна миграция владельца (см. отчёт).
4. Зависимые социальные записи (обещания, отношения, темы) не стираются: решение за их владельцем.
5. «Последнее использование» тестового источника не отслеживается: берётся последнее изменение.
